> 写作条件：本文写于工具层故障期间（v2 shell/adb 均不可用），全程只用 Read/Write，
> 未碰设备、未跑代码、未验证任何"当下"状态。所有判断基于对既有代码/规格的重读与
> 领域推理，是**操作预案**，不是本次要执行的动作——回核本身要等首批真实语音语料到位。

## 0. 先说清楚在回核什么、不回核什么

`M7_MAX_GAP` 五个锚点 `[0,100][60,85][150,70][400,40][1000,0]` 里，**只有 1000 这一点
是 PROVISIONAL**，前四点各有仓内出处（60=`VoiceRunner.CODEC_JB_BUDGET_MS`；150/400=
`PROFILE_FRAMEWORK §4.1` 口到耳自然度红线的第一/第三档，其中 400 与硬否决阈值
`M1_VETO_THRESHOLD_MS` 复用同一个数）。**本预案只回核 1000 这一个点**，不因为拿到了
真实数据就连带重新怀疑前四点——那四点的出处不会因为语音语料出现而改变，重新怀疑它们
是范围蔓延。

## 1. 数据量门槛：为什么不能照抄 `n≥15` 那套

`M3_EXPANSION_ROUND_PROPOSAL` 定的 `n≥15` 是给**CV（变异系数）驱动的中心趋势判断**用的
——判断的是"这批样本的均值/中位数稳不稳"。**M7 是 max 统计量，不是中心趋势统计量**，
这不是同一类问题：

- M7 存在的**全部理由**是抓住"罕见但致命"的长静默（`anchors.yaml` 注释里那次 4.55 秒
  冻结在 599 个间隔里只占 0.67%，P95 完全看不见它）。这意味着**M7 的分布天然是重尾的**，
  用中心趋势统计的样本量经验（n≥15 让均值稳定）来判断"够不够回核一个尾部锚点"，
  会系统性低估所需样本量——n=15 通常连一次真正的尾部事件都不一定遇得到。
- 遇不到尾部事件本身**不是"1000 太宽松"的证据**，是**幸存者偏差**——不能因为 15 次
  会话都没触发过 1000ms 就断言这个门槛该往下调；也不能因为 15 次里恰好有一次冲到了
  1200ms 就断言该往上调。极值统计量需要的是"看过足够多次、足够久"，不是"看过足够多个"。

**据此提两级门槛，而不是一刀切**：

| 级别 | 门槛 | 允许做什么 |
|---|---|---|
| **登记级**（随时触发，无门槛） | 任意一次真实语音会话产出 M7 值 | 只登记这个数字，不据此改锚——`spec §7` 的持续登记义务本就覆盖这个 |
| **回核级**（正式启动回核流程的最低条件） | **≥30 个独立真实语音会话**，且**覆盖至少两种网络条件**（如 WiFi + 蜂窝，或忙时+闲时——理由见下） | 可以开始写描述性分布报告（§2），但**不等于可以立刻改锚**（见 §3 的双门槛） |
| **改锚级**（真正修改 1000 这个数） | 回核级基础上，**分布报告结论清晰**（见 §2 的判据），且经**大脑/PO 复核批准** | 走 §3 的落地流程 |

**为什么是 30 不是 15**：没有更精确的依据可引——如实说明这是"至少是 n≥15 的两倍"这个
保守系数，不是算出来的最优值。理由是重尾分布下样本量需求通常比中心趋势判断高一个量级，
而"高一个量级"在没有先验分布形状的情况下无法精确定出，只能定性地要求"明显更多"。
**如果谁在拿到真实语料后有更好的依据（比如观察到的极值出现频率），应该用那个依据
重新定门槛，不要死守 30 这个数**——这条本身也要写进回核报告里，不能悄悄漂移成
"30 是标定过的科学门槛"。

**为什么要覆盖至少两种网络条件**：M7 的物理含义是"网络/系统级的长静默"，如果 30 个
会话全来自同一种网络条件（比如全是 WiFi），观测到的分布形状是那一种条件下的形状，
不能代表"语音场景"整体——这与 `M3_EXPANSION_ROUND` 里"制式与出口不能共线"是同一个
形状的警惕（D-374/D-393 反复踩过的坑：单一条件下的样本，看着像总体规律，实为条件本身
在说话）。

## 2. 分布检验法：只做能站得住脚的那种，不发明假精度

**不提议做拟合优度检验、不提议用极值理论（GEV/GPD）拟合尾部分布**——三十来个会话的
样本量不足以支撑这类方法给出可信区间，硬套只会产出一个看起来精确、实则脆弱的数字，
这与"发明常量"是同一类错误（`M3_EXPANSION_ROUND_PROPOSAL` §8 已明确拒绝过这个思路：
"只有一个点估计，拿它当门限就是发明常量"）。

**改用简单、可核对的描述性方法**——把每个会话的 M7（该会话内最长帧间静默）取出，
汇成一张分布表：

| 统计量 | 报告什么 |
|---|---|
| 会话数 n | 独立会话数（不是帧数、不是间隔数——M7 是每会话一个数，参照 D-340 的
「条数冒充重复数」教训，n 必须数会话不数原始间隔行） |
| p50 / p90 / p95 / p99 / max（跨会话） | M7 值本身的分布，而不是"帧间隔"的分布——
这是"每次会话最坏一下有多坏"的分布，与 M2 那种"帧间隔本身的 P95"是完全不同的统计对象 |
| 落在各锚区间的会话占比 | `<60ms` / `60–150ms` / `150–400ms` / `400–1000ms` / `≥1000ms`
五档各占多少会话——这张表直接对应五个锚点分段，读者不需要额外换算就能看出锚点是否
把真实分布切在了合理的位置 |
| `≥1000ms` 的具体案例 | 若有会话触及或超过 1000，逐条列出该会话的场景描述（不只是数字）——
极值本身的可解释性（是不是网络切换瞬间、是不是 App 冷启动）比它的数值更重要 |

**判据（供参考，不是强制公式）**：

- 若 30+ 会话里**从未出现**过 `≥400ms` 的 M7 值：说明 400→1000 这段斜坡在实践中几乎
  用不到——这本身不是"1000 错了"的证据（M7 存在正是为了兜住那种"几乎用不到但一旦
  发生就很严重"的情形），但值得在报告里如实写"1000 这一点目前缺乏真实分布支撑，
  保留是出于保守，不是出于观测"。
- 若 30+ 会话里**反复出现**明显超过 1000 的值（比如多个会话落在 1500–3000ms 区间）：
  这是"1000 作为末点太低"的信号——极端严重的静默会被 clamp 到 0 分，与刚过 1000 的
  情形同分，丢失了严重度的区分度，这正是当初拒绝用 400 作末点的同一条理由（D-404：
  "400 末点会让 500ms 与 5s 静默同分，丢掉 M7 存在的意义"）现在反过来适用于 1000
  本身——如果真实数据显示严重情形普遍超过 1000 很多，末点应该继续外推，而不是
  停在当初拍脑袋定的数上。
- **中间地带（大多数会话在 60–400ms 之间，偶尔触及 1000 附近但很少远超）**：这是
  "1000 大致合理"的信号，报告应如实写"未发现需要调整的证据"，**不因为拿到了数据就
  必须找出一个改动**——诚实的确认与诚实的异议同样是本次预案要求的产出（呼应大脑
  这次派单给我的两件任务共用的措辞）。

## 3. 改锚流程：分两种情形，取决于有没有真实分数已经盖上 v0.2 的戳

这是本预案里最容易被漏掉的一步，先把架构现状点名：

**当前代码不支持"M7 在不同版本下用不同锚点"**——`AqsScorer.scoreWith()` 内部的
`anchorMaps`（`"M7" to M7_MAX_GAP_ANCHORS` 那一行）是一个**版本无关的扁平字典**，
不管调用方传的 `version` 是 `aqs-voice-v0.2` 还是将来的 `v0.3`，"M7"这个键永远查到
同一个 `M7_MAX_GAP_ANCHORS` 常量。这与权重表的架构不同——权重表（`WEIGHTS_VOICE`
vs `WEIGHTS_VOICE_V02`）天然按版本分表，锚点表目前没有这层区分。

**这个架构现状决定了两条不同的路**：

### 情形 A：回核发生在任何真实会话被按 `aqs-voice-v0.2` 打分之前

若到回核那天，`aqsVersion="aqs-voice-v0.2"` 还没有任何真实（非合成）分数被落库或
对外引用过——**直接原地改** `spec/scoring/anchors.yaml` 的 `M7_MAX_GAP` 与
`AqsScorer.kt` 的 `M7_MAX_GAP_ANCHORS` 是安全的，不违反 `spec/README.md §3` 的
"只增不改不删"纪律，因为那条纪律要保护的是"已经盖着这个版本戳的历史分数可重算"——
如果压根没有历史分数存在，就没有东西需要被保护。**这是当前最可能出现的情形**：
M7 v0.2 是今天（2026-08-02）才落地的，全仓零语音语料，短期内不太可能有真实分数
先于回核完成而产生。

### 情形 B：回核发生在已有真实会话被按 `aqs-voice-v0.2` 打分之后

这时原地改锚点会让**已经盖着 v0.2 戳的历史分数**在新代码下重算出不同的数字——
版本戳本该保证"同一戳=同一算法"，原地改锚点破坏这个保证，是与 D-404 处理权重表
问题时**完全相同的理由**。此时正确流程是：

1. **不改 `M7_MAX_GAP_ANCHORS`**（v0.2 的锚点原样保留，供任何需要重算 v0.2 历史分
   的场景使用）。
2. **新增 `M7_MAX_GAP_ANCHORS_V03`**（或届时约定的版本号），新锚点写在
   `anchors.yaml` 里作为**并列条目**，不是覆盖。
3. **`anchorMaps` 需要改成按版本查表**——这是当前架构缺的那一步，需要在这个情形
   实际发生时补上（比如把 `scoreWith` 的 `anchorMaps` 参数化为按 `version` 选择，
   或者更小的改法：只让 M7 这一项按版本查，其余 KPI 保持不变，因为目前只有 M7
   有"锚点本身标了 PROVISIONAL、预期会改"这个特殊状态，其余锚点没有这个预期）。
4. **同时新增 `AQS_VERSION_VOICE_V03`**（比照 D-404 新增 v0.2 时的先例，锚点语义
   变化=版本号跳级，即使权重表本身没有变化也要跳级——因为"同一版本戳下同一 KPI
   算出不同分数"同样违反版本戳的语义，不只权重表变化才算"语义变化"）。
5. 配对拍守卫更新：`SpecScoringParityTest.anchors_full_parity` 目前按 `AqsScorer`
   的 `*_ANCHORS` 字段反射枚举、与 `anchors.yaml` 的键集比对——新增
   `M7_MAX_GAP_ANCHORS_V03` 后这道门会自动要求 `anchors.yaml` 同步新增对应条目，
   不需要额外手写清单（这道对拍已经是"清单从产物导出"的形状，无需重新设计）。

**这一步的实现工作量比听起来大**——不是简单地"加一个常量"，是要先给 `anchorMaps`
的查表机制加一维（按版本）。**这个工作量应该在动手改锚点数字之前就规划进去**，
不要等到写代码时才发现"加个新表"没有那么简单。

## 4. 明确不做的事（防止回核变成范围蔓延）

- **不因为回核 M7 而重新审视 60/150/400 三个有仓内出处的锚点**——那三点的出处来自
  `PROFILE_FRAMEWORK` 与 `VoiceRunner` 常量，不是靠语音语料标定出来的，语音语料再多
  也不该动它们（除非那些出处本身被证明错了，这是另一件事，不在本预案范围内）。
- **不用回核 M7 顺带调整 M7 的权重（`0.10`/`0.05`）**——权重的确定依据是"从 M2/M3
  匀出多少"这个内部分配逻辑（D-404），与锚点的分布形状是两件独立的事；除非真实数据
  显示 M7 与 M2/M3 的相关性判断本身错了（那也是另一件事）。
- **不用一次"惊人"的单一会话数据就启动改锚**——§1 的门槛存在正是为了防止这个；
  一个极端案例应该被记录、被讨论，但不该单独触发正式改锚流程。
- **不在回核报告里补一个"标定过的"字样掩盖门槛数字（如 n≥30）本身是拍出来的**——
  §1 已经写明这一点，本条重复强调，因为这类"事后包装成科学"的措辞正是这个项目
  反复咬住过的形状（D-264：常量单一来源问题；措辞精度问题同族）。
