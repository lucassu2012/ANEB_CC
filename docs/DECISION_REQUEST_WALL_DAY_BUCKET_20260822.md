> `run.started_at_epoch_ms`；D-506 已裁定 E-01 服务端钟为基准（NTP 同步生产节点，
> D-547 实测 skew=26ms、余量约 2300 倍）。要不要把分桶键改为
> `started_at_epoch_ms − clock.wall_skew_ms`（即服务端时刻）？

> 一页决策请求——**并带一个改变风险判断的新实测事实**。

## 1. 新事实：改键对**全部现存语料**是零影响

```bash
for f in $(find evidence -name "*.jsonl" | grep -viE "screencap|mark_rtt|index"); do
  grep -c wall_skew_ms "$f"; done   # 48 个文件全部为 0（2026-08-22 实测）
```

**48 个真实语料文件、`wall_skew_ms` 零命中**——含最新的 `acceptance_20260820`。
现存全部已发布报告（M2 复跑在内）都出自 EchoWire 接线前的生产者，**改键后逐字节不变**
（无该字段 ⇒ 回退设备钟 + 既有警示，行为与今天完全一致）。

> 订正自指：我此前 5 次提问时都附带「会移动已发布报告的行/日期归属」的顾虑——
> 这句**当时没有实测支撑，现在被证伪**。没有任何现存行会动；会动的只有**未来**
> 带证据且 skew 恰好跨日界的 run，而那正是想让它动的情形。

## 2. 两个可选方案（推荐 B2）

| 方案 | 语义 | 代价 |
|---|---|---|
| A（现状） | 设备钟分桶 + D-541 警示行（印可执行公式，声明「本表未做该校正」） | 未来带证据语料的跨日 run 归错日，靠人读警示自救 |
| **B2（推荐）** | **语料内 100% run 带墙钟证据才换服务端键；否则整表仍设备键+警示** | 需一次实现 + 守卫；避免 B1 的同表混键 |
| B1（不推荐） | 逐 run 最优证据（带证据的用服务端、不带的用设备） | **同一张表两把钟**：同一物理时刻可落两天，表内自相矛盾 |

campaign_report 库存与 trend 时序复核在读）——第三个消费方接上即可，不新造算法。
