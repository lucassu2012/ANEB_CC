## 1. 背景与目标

诊断结论有两条落在本 lane：①"进展"缺一个客观度量——561 条决策对 73 run 语料，没人能一眼说出数据资产有多少；②verify_all 全链触发过频（峰值一天 51 次、274 份日志全入库），是流程开销的大头之一。本单做四件事：**语料台账成为进展的单一事实源、verify_all 分层减负、战役报告 T+1、热力卡 v1**。

## 2. 范围与文件边界

- **可写**：`scripts/`（本 lane 属主）、`docs/` 报告与台账产物、`evidence/` 报告归档。
- **只读**：`app/`（v2 lane）、`spec/` 契约（v4 lane；报告只消费）。
- **非目标**：不新增守卫层级；不做新审计轮；不改 19 门的语义与门数。

## 3. 任务分解

### 3.1 语料台账：进展的单一事实源（无前置，D1 启动）
新增 `scripts/corpus_ledger.py`：自动盘点全部真实语料（evidence/ 各战役目录的 jsonl + 已拉取的 Room 库），输出两面：
- `docs/CORPUS_LEDGER.md`（自动生成，文件头标"勿手编"）：总 run 数、按战役/点位/运营商/RAT/时窗/low_confidence 比例分桶；
- 同名 CSV 供报告链引用。
判据从既有 `campaign_common` 的读法派生，**不自创解析**；合成语料（`is_synthetic()`）单列不混入。配一条守卫：台账数字与 `campaign_report` 对同一语料的 `输入记录：N` 行对拍。
**验收**：一条命令重算全量台账；当前基线数字（73 run 族）与 t46 报告对得上；此后任何"进展"声明必须引用台账增量（写进文件头的使用规则）。**预计 1 天。**

### 3.2 verify_all 分层触发改造（无前置，D1 启动）
- 给 `scripts/verify_all.ps1` 加 `-Scope server|app|scripts|spec|all` 参数（或按 `git status` 改动路径自动推荐层），既有 19 门按层映射；**全链（all）保留给收官/入册/交接点**。
- 归档策略改两类：只归档"收官全绿"与"红门样本"日志；日常分层跑不落 evidence。
- **19 门语义、门数、gate-integrity（守卫的守卫）一律不动**——减频不减门；`-Strict`（NOT_EXECUTED 不折算 PASS）建议设为默认。
**验收**：各层实测耗时对比全链入册一行；分层跑与全链跑对同一改动结论一致（抽一例证明）；改造自身过全链 19 门。**预计 1 天。**

### 3.3 战役报告 T+1（前置：SPEC-2 语料到货）
豆包首批（2.1）与 wave-1（2.2）落库后，各在 **T+1 个工作日**内出 `campaign_report` 三面（md+HTML+CSV）+ 发布门。s4 首批（2.3）到货后吞吐面纳入。
**验收**：每批报告过 publish_check；结论句只说数据支持的话（low_confidence 如实标注）；报告链引用 3.1 台账数字而非手抄。

### 3.4 《城市热力卡与归因报告》v1（前置：3.3 的 wave-1 报告）
用 wave-1 真实多点位语料首次渲染热力卡与归因链（`campaign_report`+`attribution` 既有能力，此前只喂过单点位）。这是 v1.0 计划里唯一对 PO 强感知的交付物。
**验收**：热力卡 v1 过发布门归档 `evidence/`；显式声明覆盖边界（点位数/运营商数/置信）；交 PO 的一页摘要随附。**预计 1 天。**

### 3.5 周报模板《业务进展视图》（无前置）
一页模板 + 首期：只有三节——**本周新增数据（引台账增量）/ 回答了什么业务问题 / 离热力卡还差几步**。与决策台账分离，供 PO 每周一读。
**验收**：模板落 `docs/BIZ_PROGRESS_VIEW_TEMPLATE.md`；首期用当周真实数字发出。**预计 0.5 天。**
