## 0. 先说一件动手前就查出来的事：①的"匹配规则"已经存在，且不是朴素最近匹配

大脑派单里问"t_A 事件与 t_C 帧怎么配对（时间最近？窗口内唯一？）"——**这个问题在
`e2_analyze.py` 里已经有答案，而且答案不是"最近匹配"**。逐字读过 `analyze()`
（:90-107）后确认：

- 配对的**单位不是单个事件/帧，是"轮"**（`turns`，来自 `es.segment_turns`）。
- 每一轮内，**两个通道的时间戳各自独立聚类**（`v3_anchors`，`e234_common.py:122-131`），
  取各自"第二簇首事件"作为该通道的 A2 锚点，然后**两个标量相减**——不是拿 A 的某个
  事件去 C 的帧序列里找最近的那一帧。
- 文件自己的 docstring（:28-30）已经写明**为什么不用最近匹配**："用『commit 之后
  最近的一帧』去定通道 C 的 A2 是循环论证：那样算出来的差恒非负、且恒小于一帧，
  门必然 PASS。" ——这正是大脑担心的"匹配规则本身若有偏，测出的 `|t_A−t_C|` 会
  说谎"这条风险，**已经被现有设计规避掉了**，不是需要我重新设计的空白。
- 配对失败**已经**被非静默计数：`drop_reasons` 字典分两种原因（"通道 A 该轮不足
  两簇"/"通道 C 该轮不足两簇"），逐条打印进报告（:174-178），汇总进 `gate_caveat`
  （:117-118）。

**顺带查清一件我原本担心的事，结论是不用担心**：轮次窗口（`t_start_ns`/`t_end_ns`）
由**独立的标记流** `marks`（`answer_complete`/`turn_start` 等，`e234_session.py:80-105`）
定义，**不是**从通道 A 或通道 C 的事件流本身派生的——所以"窗口本身循环论证"这层
担忧不成立，两个通道的聚类窗口来自第三方标记，对两侧公平。

**故本文对①的定位改为**：不是从零设计匹配规则，是**审计既有规则在 T27 真实数据下
是否还成立**，并指出现有设计里**尚未被验证**（不是"有 bug"，是"没数据测过"）的
几处假设。见 §1。

## 1. ① 对拍匹配规则：审计既有设计 + 三处待 T27 数据验证的假设

### 1.1 既有设计的三层防护，逐条确认成立

| 防护 | 位置 | 防的是什么 |
|---|---|---|
| 聚类而非最近匹配 | `v3_anchors` | 循环论证偏差（docstring 明确论证过） |
| 独立聚类窗口（第三方标记） | `segment_turns` | 窗口本身从任一被比较通道派生的偏差 |
| 配对失败非静默计数 | `drop_reasons` | 静默丢样本、门看起来比实际更"干净" |
| 有符号分布单独报告 | `res["signed"]` | 单边门覆辙（T14 §2.1③ 那个"同一滞后 C 报 FAIL、A 报 PASS"的坑） |

这四层不需要本预案重新设计，**T27 交付后应先跑一遍，确认这四层在真实数据下仍然
按预期工作**，而不是假定"代码逻辑对，数据自然就对"。

### 1.2 三处待验证的假设（不是缺陷，是"没有真实数据测过"）

1. **共享聚类阈值是否对两个通道都合适**。`gap = ec.cluster_gap_nanos()`
   （`e234_common.py:65-78`，从 `ObsStats.kt` 读，当前 400ms）对通道 A 和通道 C
   的聚类**用的是同一个数**。这个阈值的原始出处是通道 A 的簇分割门限（D-52/D-53），
   通道 C 借用它做帧序列的"思考静默"分割是否合适——**没有独立论证过**。若通道 C
   的帧序列在"渲染中"与"思考静默"之间的间隔特征与通道 A 的事件间隔特征系统性
   不同，共享阈值可能让某一侧的聚类系统性偏松或偏紧。**待 T27 数据到手后**，
   应各自画一次帧间隔/事件间隔的分布，核对 400ms 是否落在两侧都合理的分割点上，
   而不是继续默认共享合适。

2. **超过两簇时"取第二簇"是否仍是想要的语义**。`v3_anchors` 在簇数 >2 时
   仍然只取 `cl[1][0]`（第二簇首事件），**没有对"为什么是第二簇、第三簇算不算"
   做过说明**——这在今天（通道 A 只有零星 click 事件、簇数很少）大概率不构成
   问题，但 T27 若把内容变化事件也计入通道 A 的聚类输入（当前实现已扩展到
   `TYPE_WINDOW_CONTENT_CHANGED`/`TYPE_VIEW_TEXT_CHANGED`，见
   `AnebAccessibilityService.kt`），事件密度会显著上升，**簇数可能从"最多两三簇"
   变成"经常三簇以上"**——届时"取第二簇"这个语义要不要改成"取最后一簇"或别的
   判据，需要用 T27 真实数据先看一遍簇数分布再决定，本预案不预先选边。

3. **`nearest_after`（`e234_common.py:135-152`）这套带去重的最近匹配工具，
   E2 至今没有用它**——它是 E1 通道 C 判读用的（防"一次物理上屏被算成三个样本"，
   D-335 同形）。E2 目前完全靠聚类锚点比较，不需要逐事件配对，所以不用它是对的；
   **但若 T27 之后有人考虑给 E2 加一层"逐事件级"的交叉验证**（比如除了锚点差，
   也想看看单个事件层面对不对得上），`nearest_after` 是现成可复用的工具，不必
   重新发明——本预案先记下这条指针，供以后决定要不要加这层时用。

## 2. ② 样本量门槛：区分双峰判别与 M7 的极值判别，两者是不同的统计问题

### 2.1 为什么不能照抄 M7 预案的 n≥30

M7 预案的问题是**极值统计**（罕见尾部事件，样本量不够会系统性错过尾部）。
E2 的双峰判别是**另一类问题**：不是"会不会错过罕见事件"，是"能不能稳定估计
两个已知簇各占多少比例"。二者需要的 n 不共享同一个理由，不能把 M7 那个数字
原样搬过来。

### 2.2 D-417 的双峰结构是机制性的，不是从噪声数据里统计推断出来的

这一点决定了本预案**不需要**上重的多峰检测统计工具（如 Hartigan's dip test 一类）
——那类工具是用来**从数据本身推断**是否存在多个峰、事先不知道机制的情况下用的。
E2 的双峰有物理机制支撑（D-417 §2.1：Android vsync 对齐是离散的"赶上/错过"结果，
不是连续噪声），**结构已知，要估计的只是那两个已知桶各自的占比**——这是一个
标准的**二项分布比例估计**问题，用简单、可核对的方法就够，符合本仓一贯"拒绝
假精度、不用比数据能撑住的更复杂的工具"的纪律（M7 预案 §2 同一条纪律）。

### 2.3 用二项比例的标准误差算，不发明新公式

D-417 用 n=53 测得 72%/26% 的分桶比例（"1 帧" 38/53、"2 帧" 14/53）。**把这个数
当作规划用的工作估计（不是"真实比例就是 72/26"的断言）**，代入二项比例标准误差
`SE = sqrt(p(1-p)/n)`：

| 目标精度（±1 SE） | 所需 n（按 p=0.72 估算） |
|---|---|
| ±6%（n=53 时的现状） | 53（已有） |
| ±5% | ≈81 |
| ±3% | ≈224 |

**这三个数字是用已观测比例反推的规划参考，不是承诺"真实比例正是 72/26"**——
真实比例只有拿到更多真实数据才知道，这张表只回答"要把当前这个粗略估计的置信
区间收窄到多少，大概需要多少样本"，与 D-417 §2.2 明确拒绝给"残余抖动=X.XXXms"
假精度是同一条纪律的另一次应用。

**如实标注一层假设**：上面这套推算把 D-417 观测到的"通道 C 自身 t_commit→t_present
的双峰"直接当作"E2 的 `|t_A−t_C|` 也会是双峰"的工作假设——这是**投射**，不是
E2 自己测出来的。E2 至今零真实 A-vs-C 数据（`e2_result.json` 恒
`channel_a_vs_c: NOT_EXECUTED`），一旦通道 A 自身的观测误差（`E_transport⊕E_quant`，
这正是 M3 门本来要测的量）叠加进来，`|t_A−t_C|` 的实际形状可能是双峰、可能因为
通道 A 自身噪声把两个峰糊成单峰、也可能是别的形状——**T27 数据落地、E2 真正跑
出第一批结果后，第一件事应是先画一次 `|t_A−t_C|` 的直方图看它长什么样，
不能默认它继承通道 C 的双峰**。

### 2.4 样本单位：轮 vs 会话，汇池要交代汇了什么

E2 现有代码的 `n` 是**单次会话内的轮数**（`turns`，`analyze()` 对单个 `run_dir`
操作）。§2.3 表格算出的 n≈81/224 大概率超过单次会话能提供的轮数——D-417 的
n=53 本身就来自单次 run3 会话的全部轮，接近现有真机窗一次能给出的上限量级。
**这意味着达到 ±5%/±3% 精度大概率需要跨多个会话汇池**。若走这条路，按本仓
既有纪律（§2.15：一个汇池统计量必须交代汇了什么、各部分多大），**报告里必须
逐会话列出各贡献了多少轮**，不能只报一个汇总 n——这条不是本预案新定的规矩，
是既有纪律在新对象上的应用。

## 3. ③ 候选 B「校正后误差」：D-417 §2.2 已经指出"扣基线"这个动词本身是错的，
以下是重述提案

### 3.1 为什么"扣基线"对双峰分布不成立

D-417 §2.2 的算术已经说清楚了：对落在第二峰（约 2 帧，26% 的样本）的翻转，
扣掉"1 帧"这个系统性基线后，**残余仍约等于 1 帧，不会收敛到 0**。"扣基线"这个
操作隐含的假设是"误差=一个连续的加性偏移量"（像固定的时钟偏差），而这里的
"误差"实际是一个**离散的分类结果**（这一帧命中了哪一次 vsync），两者不是同一
类量，减法对分类结果没有意义——2 帧减 1 帧基线，剩下的"1 帧"不是"还没扣干净
的连续残差"，是"这一次分类结果本身就是 2 而不是 1"。

### 3.2 重述提案：把候选 B 从"量级门"改写为"分类占比门"

**建议候选 B 的语义从**"E1 测出的量，扣除 E2/G-3 标定的系统性管线延迟之后
（`≤1 帧`）"**改写为**："落在『多命中一次 vsync』这一类的样本占比，不超过
某个阈值"——即把连续量的减法-判门限，换成离散分类的计数-判占比。这个改写
方向直接对应本仓已有的先例：**T4 一票否决用的正是"比率超门"而非"量级超门"**
（severe-stall rate > 1% 触发否决，不是对停顿时长本身设减法门限）——E2 的
"多命中一次 vsync 的比例"与 T4 的"严重卡顿比例"是同一种判据结构，候选 B 改写
后与既有设计哲学一致，不是新发明一套判据类型。

**这个重述比 D-418 记录的候选 B 描述更具体一步**：D-418 只写"改写门为『校正后
误差』"，没有说改写成什么样；本预案的贡献是指出减法本身是错的动词，并提出
"改成比率门"这个具体方向——**这是本预案的提案，不是已经拍板的决定**，仍需
大脑/PO 按 spec 治理规则走"先改 spec、后动代码"的既定流程（`spec/README.md`
治理规则 2，D-418 已引用同一条）。

### 3.3 重述后仍然不发明的东西

- **不在本预案里定阈值数字**（"占比不超过多少"）——这与 M7 预案的态度一致：
  阈值要有出处，T27/E2 真实数据落地前发明一个百分比就是又一次假精度。
- **不假定这个比率门能完全替代候选 C（标注不确定度带）**——两者可以并存：
  候选 C 是"现在先给个保守带、不等 E2"，候选 B（改写后）是"E2 跑起来之后，
  用比率门取代那个保守带"，先后关系不是互斥关系，D-418 的"候选 C 现在+
  候选 B 以后"这个建议本身已经是这个意思，本预案只是把候选 B 到时候具体
  长什么样想清楚了一层。
