## 0. 先说三个决策的**代价不在一个量级**（这决定先拍哪个）

| 决策 | 动什么 | 是否触发版本号跳级 | 是否需重新采集 | 代价量级 |
|---|---|---|---|---|
| ①T3 权重再分配 | **评分语义**（权重表） | **是**（D-404 先例：语义变化即跳级） | 否 | 高 |
| ②短板惩罚 | **总分公式** | **是**（同上，且改的是总分本身） | 否 | 高 |
| ③置信门槛 | 门槛常量 / profile 结构 | 门槛改否；**改相位数是** | **改相位数则是** | 中～高 |

**三者都不是"改个数字"**。而 D-493 曾提到的"短板旗标"若走**不改总分**的路线
（只在契约/UI 多印一个已可推导的判词），代价会低一个量级——这条路线单列在 §2.4。

## 1. 决策①：T3 权重再分配

### 1.1 前置问题的答案：**既不是"门槛过松"，也不是"真无区分度"，是第三种**

派单要求"先判 T3 恒 100 是门槛过松还是真无区分度"。独立核实后，**两个选项都不对**：

- **不是"真无区分度"**：T3 的锚点很陡——`T3_ANCHORS = (0→100, 0.005→85, 0.02→70,
  0.05→55, 0.15→0)`（`AqsScorer.kt:254`）。**0.5% 的卡顿率就掉 15 分**，指标本身
  的分辨力很强；计算逻辑也正确（`KpiCalculator.kt:412` + `:584-588` 的 `rateKpi`
  = `count{it > threshold}/size`，能算出非零）。
- **不是"门槛过松"**（那意味着门槛该收紧）：门槛 `STALL_THRESHOLD_MS = 200.0`
  （`KpiCalculator.kt:319`）**有出处**——注释写明"KPI 文档 5.1 T3（Eloquent 定义）"。
- **真正的答案**：**被测对象让这个指标没有分辨空间**。T3 = ITL 样本中 >200ms 的占比，
  而全语料 489 场景实测 **ITL p95 = min 11.2 / p50 28.9 / p95 39.9 / max 40.4 ms**
  —— **最大值离门槛差 5 倍**。根因是自建仿真服务端按固定速率吐字：
  s1/s3 `rate_tps=40`（理论 ITL 25ms）、s2 `rate_tps=60`（16.7ms），
  实测 p50 28.9ms 与"理论值+网络抖动"完全吻合。
  **要触发 T3 需要单次 token 间隔膨胀 5–12 倍**，在当前被测对象下不会发生。

> **这与 T1/U1 的「结构性低置信」是同族形状**：不是指标坏了，是**场景/被测对象的
> 设计压掉了指标的分辨空间**。T3 要有分辨力，前提是被测对象换成**真实 LLM 服务端**
> （吐字会真卡顿）——那时这 20% 权重正是它该起作用的地方。

**由此排除一个选项**：「调低 200ms 门槛让它在仿真下有分辨力」——门槛有出处，
按 M7 预案 §4 同族纪律（不动有出处的锚/门限）不应因"我们测不到"而改它。

### 1.2 三案与档位迁移矩阵（73 run 全语料重算）

释放的权重按其余项**现有比例**分摊，Σ 恒为 1（模拟器 `redistribute()`）。

**主赛道**（基线 72 excellent + 1 good）：

| 案 | T3 权重 | 分数区间 | 中位 | 档位分布 | 迁移 |
|---|---|---|---|---|---|
| A0 基线 | 0.200 | 84.824–91.683 | 89.068 | 72E + 1G | — |
| A1 T3 减半 | 0.100 | 82.927–90.644 | 87.701 | 63E + 10G | **excellent→good 9** |
| A2 T3 降至保险位 | 0.050 | 81.978–90.124 | 87.018 | 55E + 18G | **excellent→good 17** |

**Token 赛道**（基线 56 excellent + 17 good）：

| 案 | T3 权重 | 分数区间 | 中位 | 档位分布 | 迁移 |
|---|---|---|---|---|---|
| A0 基线 | 0.150 | 82.312–91.100 | 86.662 | 56E + 17G | — |
| A1 T3 减半 | 0.075 | 80.751–90.314 | 85.485 | 46E + 27G | excellent→good 10 |
| A2 T3 降至保险位 | 0.050 | 80.231–90.053 | 85.093 | 38E + 35G | excellent→good 18 |

**必须看懂的一点**：T3 恒为**满分 100**，所以**降低它的权重必然拉低总分**——
把权重从满分项挪到非满分项。上表的迁移全部是单向下行，这不是"分数变准了"，
而是"把一个恒满分项的托举撤掉了"。**降 T3 权重的真实效果 = 总分整体下移**，
它并不会让分数更有分辨力（方差贡献仍主要来自 U1/N1/N2/D1）。

### 1.3 我的推荐（建议，非决定）

**建议 A0 维持现状**，理由三条：
1. T3 不是坏指标，是**当前被测对象**触发不到它。为"我们现在测不到"而削弱一个
   **对真实 LLM 服务端有强分辨力**的保护项，是拿未来的保护换当下的数字好看。
2. 降权重的实际效果只是总分整体下移（A2 让 17 条掉出 excellent），**并不提升分辨力**
   ——想提升分辨力应该动的是"被测对象"（换真实服务端）而不是权重表。
3. 改权重触发版本号跳级（D-404 先例），代价与收益不匹配。

**若一定要动**，A1（减半）优于 A2：迁移 9 条 vs 17 条，且保留一半保护力。
**另一条更对症但更大的路**：按被测对象分权重表（仿真 vs 真实服务端两张表），
比照已有的 `WEIGHTS_TOKEN_MM`/`WEIGHTS_TOKEN_TXT`"按负载分表"先例——本包不展开，
因为它需要先有真实服务端语料才谈得上标定。

## 2. 决策②：短板惩罚函数形式

### 2.1 先摆一个 D-493 没提到的既有事实：**短板机制已经存在，只是不在分数层**

- **报告层早有**"拖累维度"：`scripts/subscore_rollup.py:38,71,77-78` 的 `dragging_dim`
  = 该格子分中位数最低的维度（argmin），已导出到 `campaign_report_subscores.csv`
  的 `dragging_dim`/`dragging_median` 列，`campaign_report.py:823-832` 还在正文点名最差格。
- **分数/app 层零命中**：`grep -rn "dragging|shortboard|weakest" app/probe/.../scoring/` = 0。

→ 决策②的真实形状**不是**"要不要造一个短板机制"，而是
**"要不要让短板影响总分本身"**（报告层已经能看见短板，只是总分不受它影响）。

### 2.2 四案与档位迁移矩阵

**主赛道**（基线 72E + 1G）：

| 案 | 公式 | 分数区间 | 中位 | 档位分布 | 迁移 |
|---|---|---|---|---|---|
| B0 基线 | 加权平均 | 84.824–91.683 | 89.068 | 72E + 1G | — |
| B1 min 拉动 λ=0.2 | 0.8·WA + 0.2·min(子分) | 80.303–87.910 | 84.691 | 27E + 46G | **excellent→good 45** |
| B2 阈值扣分 | 存在子分<70 则 −5 | 79.824–91.683 | 84.068 | 22E + 51G | **excellent→good 50** |
| B3 软封顶 | min(WA, min子分+20) | 76.489–91.683 | 86.958 | 57E + 16G | excellent→good 15 |

**Token 赛道**（基线 56E + 17G）：

| 案 | 分数区间 | 中位 | 档位分布 | 迁移 |
|---|---|---|---|---|
| B0 基线 | 82.312–91.100 | 86.662 | 56E + 17G | — |
| B1 min 拉动 | 78.293–87.374 | 82.393 | 18E + 55G | excellent→good 38 |
| B2 阈值扣分 | 77.312–91.100 | 81.662 | 16E + 57G | excellent→good 40 |
| B3 软封顶 | 76.489–91.100 | 86.115 | 49E + 24G | excellent→good 7 |

**决策②是三个决策里影响最大的**：B1/B2 让主赛道约**三分之二**的 run 掉出 excellent
（45/73、50/73），远超决策①的 9~17 条。

### 2.3 三案的性格差异（拍板时该看的不只是迁移条数）

- **B1（min 拉动）**：平滑、无断崖，每条 run 都被自己的最低子分按比例拖一点。
  但它**对所有 run 一视同仁地降分**（区间上下界同时下移），最高分也从 91.68 掉到 87.91
  ——它更像"给总分整体加了一个短板税"，而不是"把有短板的挑出来"。
- **B2（阈值扣分）**：断崖式，跨过 70 线才扣。**区间上界不变**（91.683 保持）
  ——没有短板的 run 完全不受影响，这是它比 B1 更"对症"的地方。
  代价是 70 这条线一旦定下就是新的常量（**需要出处**，不能拍脑袋——参照本项目
  D-264"常量单一来源"与 M7 预案 §4"不把拍出来的门槛包装成标定过的"）。
- **B3（软封顶）**：只在"总分与最低子分差距过大"时才生效，**最贴合"掩盖"这个词
  的字面含义**（掩盖 = 总分显著高于短板）。迁移最少（15 条），且上界不变。
  Δ=20 同样需要出处。

### 2.4 **一条代价低一个量级的替代路线**（本包认为最该先考虑的）

`spec/schemas/result-run.schema.json` 的 `run.aqs` 字段集 =
`[score, low_confidence, veto_applied, not_computable_reason, input_mapping, sub_scores]`
—— **`sub_scores` 已在契约里**，任何消费方**已经握有全部子分**，可自行 argmin 求出短板。

所以存在第四条路：**不改总分公式，只把"短板判词"标准化并下沉到契约/UI**
（把报告层已有的 `dragging_dim` 判据固化为跨端共享判据）。
- 好处：**不动评分语义 → 不触发版本号跳级**；历史分数全部保持可比；
  读者拿到 run.aqs 就能看见短板，而不是只有读战役报告的人能看见。
- 代价：Kotlin/Python 跨端无法共享实现，需靠对拍守卫钉住（已有
  `SpecScoringParityTest` 这类跨端对拍先例可循，不是新机制）。
- 风险：这解决的是"看不见短板"，**不解决"总分掩盖短板"**——若拍板的真实目标是
  "让总分自己反映短板"，这条路线不满足，仍需在 B1/B2/B3 里选。

### 2.5 我的推荐（建议，非决定）

**分两步**：
1. **先走 §2.4 的低代价路线**（短板判词下沉，不改总分）——它立刻消除"读者看不见
   短板"这个问题，且零版本代价、零历史不可比风险。
2. **总分公式改不改，建议等真实 LLM 服务端语料**再定。理由：当前 73 run 的最低子分
   **几乎恒为 N1**（网络 RTT，56.5–73.5 分，0/489 场景达 excellent，因 <30ms 门槛在
   移动网络下结构性不可达）。也就是说，现在加任何短板惩罚，**惩罚的都是同一个
   N1**，等于变相给 N1 加权——这与"识别真实短板"的意图不是一回事。
   若一定要现在选，**B3（软封顶）最贴合"掩盖"的字面含义、迁移最少、上界不变**，
   但 Δ=20 必须先找到出处。

## 3. 决策③：置信门槛

### 3.1 决定性发现：**门槛降到 2 是"看着解决了、实际没解决"**

生产判据是**两条析取**（`AqsScorer.kt:633-634`）：
```kotlin
val lowConf = kpi.validity == Validity.VALID_LOW_CONFIDENCE ||
    inputs.values.any { it.lowConfidence }
```
而第一条通路的 `composite.validity` 由 `AqsInputMapper.kt:76-77` 定：
```kotlin
val anyLowConf = listOf(s1, s2, s3).flatten().any { it.validity == VALID_LOW_CONFIDENCE }
```
—— **三个 profile 的任一场景低置信即低置信**，而场景级 validity 又由该场景内
**任一 KPI** 低置信驱动。

实测各 profile 的样本数（306 个带 `kpi_quality` 的场景）：

| profile | T1 sample_count | U1 sample_count |
|---|---|---|
| s1_chat | **恒 1** | **恒 1** |
| s2_coding_agent | 恒 2 | 恒 1 |
| s3_multimodal | 恒 2 | 恒 2 |

AQS 定向取值（`AqsInputMapper.kt:40-72`）：**T1←s2（=2）、U1←s3（=2）**。

**模拟结果**：

| 门槛 | 有场景低置信的 run | AQS 直接输入低置信的 run | **run 级 lowConf** |
|---|---|---|---|
| 3（现状） | 44/73 | 44/73 | 44/73 |
| **2** | 44/73 | **0/73** | **44/73 ← 纹丝不动** |
| 1 | 0/73 | 0/73 | 0/73 |

> **分母务必看清**：语料里 `run.aqs.low_confidence` 的**实测**值是 **73/73**；
> 上表只能覆盖带 `kpi_quality` 的 **44 个 run**（另 29 个该字段缺失，D-493 §4）。
> 表里的 44 不是"只有这些低置信"，是"这些是本表算得出来的"——缺字段的 29 个
> 按相位数规则同样会低置信（推断，非本表实测）。

**读法**：门槛从 3 降到 2，**AQS 的直接输入全部脱离低置信（44→0），但用户看到的
`low_confidence` 标记完全不变**——因为 s1_chat 的 T1/U1 恒为 1，仍 <2，
composite validity 那条通路依旧恒真。**这是一个会让人以为解决了、实则没解决的方案。**

### 3.2 三案

- **C0 维持门槛 3**：现状，73/73 低置信。诚实但"恒为真的旗标等于没有信息"
  （D-493 已指出这个形状）。
- **C1 门槛降到 2**：**无效**（见上表），不建议——它唯一的效果是让
  `kpi_quality` 里的数字变好看，而 run 级判词不动。
- **C2 门槛降到 1**：等于**取消门槛**（`sample_count>0` 即可）。run 级 lowConf 归零。
  但这不是"标准变合理了"，是"标准被取消了"——1 个样本的 TTFT 本来就不该被称作
  高置信。**不建议**。
- **C3 改 profile 相位数**（让 s1 的 `token_stream`/`upload_burst` 各达到 3 个）：
  **唯一真正对症的方案**。D-493 已实证 `sample_count` = 场景内相位出现次数，
  与时长/字节数无关（306/306 场景零不匹配），所以"测久一点"无效，**唯一杠杆是相位数**。
  代价：改 profile 结构 → 采集时长增加（D-493 估 s1 约 60s→90s）、
  **且既有 73 run 语料与新语料不再直接可比**（场景结构变了）。

### 3.3 我的推荐（建议，非决定）

**建议 C0 维持 + 把"为什么恒为真"写进报告口径**，理由：
1. C1 无效、C2 是取消标准而非修正标准——两者都不该选。
2. C3 虽对症，但它的代价是**打断语料连续性**（73 run 基线失去可比性），
   而当前正处在 48h 冲刺、M2 复跑与交付包定稿之前——**换 profile 结构的时机
   不该是现在**。
3. 更重要的是：`low_confidence` 恒为真**并不是错的**——T1 只测 1–2 次、
   U1 只测 1–2 次，本来就该标低置信。**问题不在旗标，在于"恒为真的旗标
   无法区分'这次特别差'和'一直如此'"**。低代价的缓解是：在报告/UI 上把
   "恒为真的结构性低置信"与"本次异常导致的低置信"分开表述，而不是动门槛。

## 4. 一句话总结（供拍板）

| 决策 | 我的建议 | 一句话理由 |
|---|---|---|
| ①T3 权重 | **维持 A0** | T3 不是坏指标，是当前被测对象触发不到它；降权重只让总分整体下移，不提升分辨力 |
| ②短板惩罚 | **先走 §2.4 低代价路线**（判词下沉不改总分）；总分公式等真实服务端语料 | 当前最低子分几乎恒为 N1，现在加惩罚等于变相给 N1 加权，不是"识别短板" |
| ③置信门槛 | **维持 C0** | 降到 2 无效、降到 1 是取消标准；C3 对症但会打断语料可比性，时机不对 |

**三条建议都是"维持或走低代价路线"**——这不是保守，是因为三个决策的共同前提
（被测对象是自建仿真服务端、最低子分恒为 N1、语料连续性正在冲刺期）都指向
"现在改评分体系，改的是对仿真环境的适配，而不是对真实体验的刻画"。
