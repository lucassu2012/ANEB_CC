## 3. ✅ FRLOSS 层混淆裁定（已裁 2026-08-02，**D-406**：层混淆，两处语义都对、只是措辞打架；已落两处消歧，FRLOSS 维持 `NOT_MEASURABLE` 待 E-06。**残留待裁**：生产端 FRLOSS 条目仍各取一半——`scored=false` 跟 §5 而 `target.good=0.01` 跟 §4.1）

**两段原文并列，未改一字**（`docs/PROFILE_FRAMEWORK.md`）：

| 出处 | 原文 |
|---|---|
| **§4.1**（L288，AI 实时交互 · Facet 2 全量指标） | 「……**质量目标**：口到耳 <150/300/400ms（对话自然度红线）；**音频丢帧 <1%**；抖动 <30ms 达 95%。可度量性：音频需**独立媒体端点**（非 token 流），**丢帧可直接测**（区别于 token 类丢包不可测）。」 |
| **§5**（L324，红线 · 测量口径绝不乱改） | 「……**丢包不设一等门限**（TCP+应用层不可直接测，用 retrans 共变量 + stall/ITL 间接反映）。」 |

**两段究竟在哪一点上打架**（只陈述，不选边）：

1. **可测性的直接对立**：§4.1 说丢帧「**可**直接测」，§5 说「**不可**直接测」。
2. **§5 的理由里点名了应用层**：括号里写的是「**TCP+应用层**不可直接测」——而 §4.1 讲的丢帧正是应用层的量。
   所以这不是「两句各说各的层」就能自动化解的：**是否属层混淆，恰恰取决于 §5 那半个括号算不算数**。
3. **要不要一等门限**：§4.1 给了具体门限（<1%）并列进「质量目标」；§5 的红线正是「不设一等门限」。
4. §4.1 自己**做了一次类别切分**（「区别于 token 类丢包不可测」），而 §5 的红线**未按类区分**。

**第三个事实：生产端今天已经各取了一半**（`spec/profiles/client/client_profiles.json:449-459`，`FRLOSS` 条目）——
`measurability = "NOT_MEASURABLE"`、`scored = false`、`anchorRef = null`（跟 §5），
**而 `target.good` 仍是 `0.01`**（跟 §4.1 的 <1%）。同一个条目里两边都在。其 `definition` 逐字：
「TCP 重传掩盖真实丢帧——代理=期望−实收帧数（通常 0）；真丢帧需 UDP 媒体通道」。

- **既有登记**：`PROFILE4_VOICE_LOOPBACK_SPEC.md` §5.7-e（L602）与 §7 待办 **2c**（L668，标「需裁决」）；
  `PLAN_ALIGNMENT_2026-07-17.md` §7(e)（L149，已记大脑的怀疑：应用层 seq 缺口 vs IP 层丢包，
  并写明「裁定前将读原文」——**本页即把原文摆上来供那一步**）；**D-390**（对抗复核挖出的两条 high 之一）。
- **不裁的后果**：FRLOSS 的 `NOT_MEASURABLE` 至今**没有框架依据**——它同时违反 §4.1、遵守 §5，
