## 0. 演练结论（先给证据，2026-08-29 实跑）

在本地建两个 worktree（`drill/wt-v2` / `drill/wt-v3`，各从同一 HEAD `72eb0bb` 分出，各 checkout 1434 文件），
模拟 v2/v3 **并行向同一演练文件的表尾追加一行**（正是本会话 T82 认领行撞过的 D-562/D-524「追加器吃表尾空行」场景）：

| 步骤 | 共享树（现状） | worktree 隔离（演练实测） |
|---|---|---|
| 两会话各改表尾 | 共享同一 index/工作树——第二个 add 可能**卷入**第一个的暂存（stage 卷入）；追加器基于对方未提交的中间态（游离空行/破表） | **各自独立 index**——wt-v3 完全看不到 wt-v2 的改动，物理上不可能 stage 卷入 |
| 各自提交 | 需 `git commit <pathspec>` + 逐行 `git diff --cached` 防搭车（O-5/O-7） | 各提交自己 worktree 的分支，**搭车物理上不可能**（只能提交本 worktree 的改） |
| 合并 | 撞车是**静默的**（游离空行/搭车提交，事后才发现，如 D-562） | **显式 CONFLICT**——git 报 `CONFLICT (content)`、`UU` 状态、`<<<<<<< / ======= / >>>>>>>` 标记，merge 拒绝完成直到解决 |
| 结果 | 静默污染需人工发现+板修（本会话 T82 认领行即 v2 代修 `f12cc04`） | 解决后合并干净（演练 `07aad2c`，表尾 DRILL-1/2/3 三行齐全、无游离空行） |

**核心结论**：worktree 隔离把「静默撞车」变成「**显式、可见、必须解决的 merge conflict**」——
后者不会污染主树、不需要事后板修、不依赖 O-5/O-7 的人工防撞纪律。演练已清理（`git worktree remove` + 分支删除，主树 list 干净）。

## 1. 方案：每执行会话独立 worktree + 独立分支 + 合并走 PR/大脑

- **结构**：每个执行会话（v2/v3/v4/…）在**独立 git worktree** 工作，各持**独立分支**（如 `sess/v2`/`sess/v3`/`sess/v4`）。
  共享同一个 `.git`（worktree 天然共享对象库），但**工作树与 index 完全隔离**。
- **合并**：各分支的成果统一走 **PR（或大脑合并）** 汇入集成分支（现 `feat/result-dev-v2` 或新建 `integration`）。
  合并时的冲突是显式的、按文件的——由合并者（大脑/PR reviewer）解决，不再有静默游离空行。
- **共享文件的特殊处理**：`DECISION_LOG.md`/`BRAIN_TASKBOARD.md`/`CLAUDE.md` 这类高频并行改的文件，
  隔离后每会话在自己分支改、合并时集中解决冲突——见 §2 的预留区段制把冲突降到最小。

## 2. D 号 / T 号防撞：区段制 vs 合并时单调赋号（推荐后者）

隔离后最容易冲突的是 `DECISION_LOG` 的 D 号追加（多会话都往表尾加）。**预留区段制**：

- 每会话分配一个 **D 号区段**（如按百位分段 v2=D-700..799 / v3=D-800..899 / v4=D-900..999）——
  各会话只在自己区段追加，**物理上不抢同一行**，合并时 D 号追加零冲突。
- **T 号同理**（任务板认领行）：按会话预留 T 号段。
- **⚠ 代价修正（v3 2026-08-29 关切，大脑背书）**：本条初稿写"连续性非必需"——**不准确**。台账用 **D 号相邻性表达因果链**（今夜 D-576→D-577 相邻即"承接同一事"）；预留区段后，跨会话的同一因果链会**跳段跳号**（v2 的 D-705 承 v3 的 D-803），**相邻性这个信号静默丢失**。故区段制**不能白拿**，需配下面二选一：
  - **方案 A（分段 + 强制指针）**：保留区段制，但**跨会话承接必须写显式「承 D-xxx」指针**——把相邻性从"隐式靠位置"改成"显式靠指针"。只解撞号，相邻性维护转成每次人工写指针（又一条靠纪律的事，与本提案"靠结构"主张相悖）。
  - **方案 B（合并时单调赋号，推荐）**：**不预分段**——各会话在自己 worktree 用**临时 D 号**追加，**合并时由合并者（大脑/PR）按合并顺序单调重赋正式号**。隔离下合并本就串行化（PR/大脑），赋号天然无撞、且**保持全局单调 ⇒ 相邻性不丢**。代价：分支内对临时号的引用在重赋后需一并更新（合并者的机械动作，可 `sed` 脚本化）。
  - **推荐 B**：同时解掉"撞号"与"相邻性丢失"；A 只解撞号。**换来的共同收益**＝零撞号（本会话 D-502 三重撞号、T70 撞号那类事故结构性消失）。**取舍归 PO/大脑。**

## 3. O-5 / O-7 共享索引纪律的退役条件

- **现行 O-5/O-7**（根 `CLAUDE.md` §「多会话协调」）：`git commit <pathspec>` 绕过共享 index、逐行 `git diff --cached`、
  未跟踪文件先 add、防搭车——**全部是为"共享同一 index/工作树"设计的防撞纪律**。
- **退役条件（明确写下）**：**当 worktree 隔离全面落地（所有执行会话都在独立 worktree + 独立分支）后，O-5/O-7 整节退役**——
  因为它防的撞车（stage 卷入、搭车、游离空行）在隔离下**物理上不可能发生**（演练 §0 已证）。
- **过渡期**：隔离迁移期间（部分会话已隔离、部分仍共享树），O-5/O-7 对**仍共享树的会话**继续有效；
  全部迁移完成才整节退役。**退役 = 从 CLAUDE.md 删除该节 + DECISION_LOG 记一条「O-5/O-7 随隔离落地退役」的 D 号**。

## 3.9 迁移步骤单（PO 2026-08-30 批 `D-587` 后产出；**先出单再动**）

> **执行前提**：本单**只描述步骤与验收**，不代任何会话执行——每个会话在自己的窗里跑属于自己的那步。
> **试点先行**（承 §4 建议）：**第 1 轮只做一个会话对**，验收通过再推广；任一步失败即按 §4 回滚，成本＝几个 worktree 的建删。
>
> **🚦 开工闸门（2026-08-30 补，`T87`）**：**设备窗期间一步都不许动**——豆包批设备窗（`DW-20260830-01`／`-02`）在跑时，
> **任何触及工作树结构的操作（建／删 worktree、切工作目录、改分支布局）一律不做**；本单的纸面打磨不受此限。
> **放行信号＝收窗 README 落库＋大脑点名**，两者缺一不开工。
> ⚠ **这条本来只写在板面 `T87` 行里，而操作者读的是本单**——「**摘要／板面写了 ≠ 被执行的那面写了**」（面册扫法③），故补在此处。

| 步 | 谁做 | 动作 | 验收（做完怎么知道成了） |
|---|---|---|---|
| **0** | 大脑 | 指定试点会话对与集成分支（现 `feat/result-dev-v2` 或新建 `integration`），并宣告试点窗起止 | 板面／消息里有一条写明「谁×谁、集成分支叫什么、窗多长」的记录 |
| **1** | 各试点会话 | 在自己窗里建 worktree＋分支：`git worktree add ../aneb-<id8> -b sess/<id8>`，**`<id8>`＝本会话 ccd session id 的前 8 位**（如 `61bd2401`／`b1769d1f`），**不得用 `v1`/`v2`/`v3`/`v4` 这类别名**——理由见下注意条**「分支名用 session id 前 8 位」**（按名指不按序号指——序号是位置的中间层，插一条就静默指错） | `git worktree list` 里出现自己那行；新目录里 `git rev-parse --abbrev-ref HEAD` 返回 `sess/<id8>`；**且该 `<id8>` 能在 `CLAUDE.md` 名册里查到对应会话** |
| **2** | 各试点会话 | **把工作目录切到 worktree**，此后所有编辑／提交只在其中发生 | worktree 内 `git status` 干净；主树 `git status` **不再因本会话而变脏** |
| **3** | 各试点会话 | 正常干活一个冲刺（**照旧跑门**：`verify_all` 与各自 lane 的守卫） | 门结果与共享树时期一致（**若门因路径假设而红，正是本步要暴露的问题**，记录后报大脑） |
| **4** | 各试点会话 | 收工把自己分支交给合并者：PR 或推分支＋消息点名 | 合并者手上有明确的分支名与变更范围 |
| **5** | 合并者（大脑／PR reviewer） | 合并进集成分支；**冲突在此显式解决**（正是 §0 演练证明的那个形状） | 合并后两方改动都在；冲突（若有）被显式解决而非静默丢失 |
| **6** | 大脑 | 试点复盘：磁盘开销／合并流程耗时／有无门因隔离而失效 | 三问各有一句结论；**任一不可接受即触发 §4 回滚** |
| **7** | 全体 | 试点通过后推广其余会话（重复步 1–5） | 各会话 `git worktree list` 有自己那行；主树只剩集成用途 |
| **8** | `CLAUDE.md` 属主 | **全面迁移完成后**按 §3 退役 O-5／O-7 整节 ＋ 记一条 D 号 | `CLAUDE.md` 无 O-5／O-7 节；`DECISION_LOG` 有退役记录 |

**⚠ 三条执行注意（都是本会话踩过的实况，不是设想）**：
1. **步 3 的「门照旧跑」是真风险点**——本会话实测过：跑全仓门时红在**他会话正在改、自己不拥有**的文件上。**隔离后这类假红应当消失**（各自跑在自己 worktree 的一致快照上）；**若仍出现，说明门读的是主树而非当前 worktree**——那是必须记录并上报的发现。
2. **D 号／T 号防撞**：§2 已给两方案（区段制 vs **合并时单调赋号，推荐后者**）。**试点期先沿用现行「写入前重取最大值」的老办法**——本会话实测有效：脚本重取时发现他会话已插 `D-588`，自动顺延到 589／590。**赋号方案随步 6 复盘一并定，别在试点期同时改两件事。**
3. **磁盘**：每个 worktree checkout 全部文件（§4 记 1434 份）。**步 6 要量的是真实占用，不是估计。**
4. **步 2 的「切工作目录」不照字面做（＝临时规矩 B，`D-606` ④ 批准，随步 6 回填）**——
   本 harness 的 shell **cwd 每次调用后重置**，`cd` 不持久；而**会话级**切目录属**会话配置变更**
   （移动项目设置／scratchpad／权限），**需用户批准，同侪与大脑都不能代批**。
   ⇒ **步 2 的实质判据是**：「此后所有编辑与提交**以 worktree 绝对路径 ＋ `git -C` 为准**」，
   验收仍取原两条（worktree 内 `git status` 干净 ∧ 主树不再因本会话变脏）。
   **照字面写会让下一个人要么卡住、要么越权**——这条补在这里就是为了不让他再撞一次。
5. **「无他会话未提交改动」怎么算（`D-605` ① 大脑释义，随步 6 回填）**——
   指的是**未归因的在飞编辑**；**已归因的持有物不算**（例如某会话明确认领、正在写的文件，
   或 `evidence/phase0` 这类由跑门再生、已知属主的产物）。
   ⇒ 开工前看 `git status` 时，判据不是「一行都没有」，而是**「每一行都能说出它是谁的」**——
   说不出属主的那行才是拦路的。
6. **分支名用 session id 前 8 位，不用 `vN` 别名（2026-08-30 补，执行前复核时发现）**——本树的 `vN` 别名**已经不唯一**：`CLAUDE.md` 名册（`D-591`）里，SPEC-1＋SPEC-2 的属主是**执行窗 `61bd2401`**、其窗口标题却是「20260711_ANEB测试方案_**v1**」而它**自报身份为 v2**；同时**编制外临时窗 `cd5239ba` 的标题正是「20260715_ANEB系统开发_v2」**。⇒ **`sess/v2` 会同时指向两个真实存在的会话**，这正是 `D-582` 误投事故的形状（标题≠身份），而**分支名比消息活得久、且出现在每一次合并里**。session id 是稳的：本轮实测**跨会话别名（`aneb-XX`）会轮换**——本册作者自己就从 `aneb-9e` 变成了 `aneb-9f`。**凡要长期存在的标识符，取稳定 id，不取会漂的别名或标题。**

**本单不含的（诚实边界）**：不含各会话的逐字命令脚本（各窗 shell 不同——本会话 Bash 即处于环境层故障、只能走 PowerShell）；不含 PR 模板；不含集成分支保护规则。**这些由步 0 指定人在试点窗内按实况补，补完回填本节。**

## 4. 回滚路径（worktree 不适应可退回共享树）

- **回滚触发**：若隔离带来新问题（如 worktree 磁盘开销过大——每个 worktree checkout 全部 1434 文件；
  或 PR 合并流程拖慢单人+AI 的高速节奏；或大脑合并成为瓶颈）。
- **回滚动作**：①停止新建 worktree，各会话 `git worktree remove` 回到主树；②恢复 CLAUDE.md 的 O-5/O-7 节
  （若已退役，从 git 历史恢复）；③D 号/T 号预留区段可保留（无害）或取消。
- **回滚成本低**：worktree 是**叠加**在现有共享树之上的（主树 `feat/result-dev-v2` 始终在），
  退回只是"不再用 worktree"，不需要迁移数据——这是本方案相对"改仓库结构"的最大优势。
- **建议**：**先试点一个会话对（v2+v3）用 worktree 跑一个冲刺**，验证磁盘/合并流程可接受后再全面推广；
  不可接受则回滚，成本仅为几个 worktree 的建删。

### 5.1 现场佐证（非演练 · 2026-08-29 真实发生，比演练更硬）

演练是构造的，这条是**本会话正常干活时自发撞上的**——同一危害的真实实例：

- **事件**：v4 提交自己的提案后跑**全仓渲染守卫**（`test_docs_commands.py`），红在 `TEST_MASTER_PLAN_v2.0.md`（**v1 的 SPEC-1 文件，v4 全程未碰**）。守卫报"line 183 五单元格 vs 表头四"。
- **追证（纯只读，实证不转述）**：`awk` 数**物理** 183 行是四单元格——与守卫报数**对不上**；`splitlines()=189` vs `split('\n')=190` 一度疑为异形断行符，核实是**末尾换行**的正常差、非异形符；`git log` 显示 v1 正连续提交该文件。**结论：v4 跑守卫的瞬间，撞上 v1 一张表的在飞中间态**。v1 随后提交 `2e7e602`（大脑裁 D-576）后守卫**自愈、PASS**。
- **这正是本方案要治的形状**：全仓门红在"**别的会话正在改、我不拥有**"的文件上——**隔离下 v4 会跑在自己 worktree 的一致快照上，不是被 v1 改着的移动靶，这个假红根本不会出现**。
- **附带立的一条运维规则（隔离落地前也适用，大脑已采纳用于其跑 `verify_all`）**：**全仓守卫红在他会话在飞的文件上时，先核是不是在飞中间态再定性**——判读信号=`awk` 物理行的单元格数与守卫报数对不上（说明守卫读到的与磁盘现态不是同一份）。
- **边界**：全程纯只读追证、未改 v1 文件；由 v1 自己的提交解决。共享树纪律的"只读边界"在此案例中守住。

### 5.2 被影响方（v3）一手数据（2026-08-29 · 诚实化收益 + 强佐证）

v3 作为共享树被影响方给的三条实测，**其一修正了本提案的收益口径、其二强化了佐证**（第三条见 §2）：

- **收益不是「不可能→可能」，是「需纪律+技巧→默认安全」**（诚实化）：v3 今夜用「从 HEAD 构造只含自己行的 index blob」**安全提交过共享文件 1 次，零污染零等待**——证明共享 index 下安全提交**做得到**。故本提案不应读作"不迁就没法干活"；隔离的真实价值是**把"每会话每次都得正确施加纪律+会那手技巧"变成"结构上默认安全"**（与 §5.1 立的"靠纪律不如靠结构"同一句）。
- **四撞车四处置 = 强佐证**：今夜四会话撞车，四种处置——`blob` 术 / 等 20 秒重试（D-575）/ 点名搭车 / 差点删锁——**其中三种靠人当场判断**。这正是"靠纪律不如靠结构"的实证：能安全全靠"恰好这个会话会这手"，换个不会的就退回污染。**结构（隔离）不依赖谁会什么。**

### 7.2 门失效的两类（**分开是本节最要紧的一句**）

1. **纯滞后型**：分支落后主树导致的时序红。**跟进主树即自愈，不需要任何豁免。**
   ⚠ 反面教训同批已记：**拿一条永久削弱守卫的豁免去掩盖一次时序差，是把一次性问题做成永久性问题**。
2. **结构性**：`server/data/` 被 `.gitignore` 挡、**0 受跟踪文件** ⇒ **全新 worktree 里根本不存在**
   （主树靠长期积累才有）。**两阶危害，第二阶才是真危险**（`D-606` ②）：
   - 一阶：门 `test_every_path_literal_in_verify_all_resolves` worktree 红／主树绿——**看得见**；
   - 二阶：`corpus_ledger.py` 的 `DEFAULT_ROOTS` 含该路径 ⇒ **同一份代码在 worktree 里算出不同的语料范围，
     不报错、只给一个不同的数**——**看不见**。

**现行临时规矩（试点期，`D-606` ②④）**：
- **规矩 A**：台账重算、`-Scope all` 及一切依赖 `server/data` 的动作**只在主树跑**，worktree 只用于编辑与提交。
- **规矩 B**：步 2 的「切工作目录」**不照字面做**（详见 §3.9 注意 5）。

**`D-609` ③ 的定位要写准**：`missing_roots()` 从**生产者侧**把二阶危害
**从「静默错数」降级为「响亮拒算」**——判据落在**根存不存在**、不落在「扫出几条」
（空目录与不存在目录都扫出 0 条，**只有后者是环境问题**）。
**这是降级不是消除**，故规矩 A 不因它解除；但它同时是下面 (a) 支**已经跑起来的实现证据**。

### 7.3 长期方案三选一（**提案，非裁定**）

| 支 | 做法 | 代价 | 现状 |
|---|---|---|---|
| **(a) fail-closed** | 凡依赖「不在版本库内」的数据根，**缺根即拒算**（记 `NOT_EXECUTED`，既不冒充 PASS 也不冒充 FAIL） | worktree 里这些门**永远不可用** ⇒ 每会话仍须回主树跑，隔离收益被削掉一角 | **已有实现证据**：`D-609` ③ 的 `missing_roots()` ＋ ② 的退出码三分（0/1/2，门对 2 记 `NOT_EXECUTED`）——**这一支不是设想，是已经在跑的半成品** |
| **(b) 共享数据目录** | 把 `server/data` 这类运行期数据挪到 worktree **共享的固定位置**（环境变量或链接），各 worktree 都解析得到 | **把共享可变状态请了回来**——而隔离的全部意义正是消除它；且要改 `verify_all.ps1` 与 `corpus_ledger.py` 的根解析 | 未实现 |
| **(c) 豁免清单** | 明文登记「这些门不在 worktree 跑」 | **零代码，但清单会过期**，且「不在这里跑」是**静默的**——正是本仓反复咬到的形状（漏登的门**从汇总里彻底消失**） | 未实现；**不推荐** |

**v4 建议（非裁定，前提写明）**：**(a) 为主 ＋ (b) 为选配**。理由三条：
1. **(a) 已有一半在跑**，且它把判据放在「根存不存在」这个**二元、不可静默**的事实上；
2. **(c) 的失败模式与本仓最贵的那类缺陷同形**——清单过期不报错，而**读者会把「没红」读成「查过了」**；
3. **(b) 单独用会退回共享可变状态**，但作为 (a) 之上的**可选加速**（想在 worktree 里跑全量的人自行挂载）是安全的——
   **因为此时 (a) 仍在兜底：挂载失败就拒算，而不是算出一个不同的数**。

**本节不主张的**：不主张现在解除规矩 A（解除条件应是「(a) 或 (b) 落地并验过」，**不是「试点结束」**）；
不主张把 (a) 的 `NOT_EXECUTED` 计入通过——**「没比成」永远不许冒充「比过了」**（同本仓四态纪律）。
