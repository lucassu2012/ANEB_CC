## 0. 演练结论（先给证据，2026-08-29 实跑）

在本地建两个 worktree（`drill/wt-v2` / `drill/wt-v3`，各从同一 HEAD `72eb0bb` 分出，各 checkout 1434 文件），
模拟 v2/v3 **并行向同一演练文件的表尾追加一行**（正是本会话 T82 认领行撞过的 D-562/D-524「追加器吃表尾空行」场景）：

| 步骤 | 共享树（现状） | worktree 隔离（演练实测） |
|---|---|---|
| 两会话各改表尾 | 共享同一 index/工作树——第二个 add 可能**卷入**第一个的暂存（stage 卷入）；追加器基于对方未提交的中间态（游离空行/破表） | **各自独立 index**——wt-v3 完全看不到 wt-v2 的改动，物理上不可能 stage 卷入 |
| 各自提交 | 需 `git commit <pathspec>` + 逐行 `git diff --cached` 防搭车（O-5/O-7） | 各提交自己 worktree 的分支，**搭车物理上不可能**（只能提交本 worktree 的改） |
| 合并 | 撞车是**静默的**（游离空行/搭车提交，事后才发现，如 D-562） | **显式 CONFLICT**——git 报 `CONFLICT (content)`、`UU` 状态、`<<<<<<< / ======= / >>>>>>>` 标记，merge 拒绝完成直到解决 |
| 结果 | 静默污染需人工发现+板修（本会话 T82 认领行即 v2 代修 `f12cc04`） | 解决后合并干净（演练 `07aad2c`，表尾 DRILL-1/2/3 三行齐全、无游离空行） |

**核心结论**：worktree 隔离把「静默撞车」变成「**显式、可见、必须解决的 merge conflict**」——
后者不会污染主树、不需要事后板修、不依赖 O-5/O-7 的人工防撞纪律。演练已清理（`git worktree remove` + 分支删除，主树 list 干净）。

---

## 1. 方案：每执行会话独立 worktree + 独立分支 + 合并走 PR/大脑

- **结构**：每个执行会话（v2/v3/v4/…）在**独立 git worktree** 工作，各持**独立分支**（如 `sess/v2`/`sess/v3`/`sess/v4`）。
  共享同一个 `.git`（worktree 天然共享对象库），但**工作树与 index 完全隔离**。
- **合并**：各分支的成果统一走 **PR（或大脑合并）** 汇入集成分支（现 `feat/result-dev-v2` 或新建 `integration`）。
  合并时的冲突是显式的、按文件的——由合并者（大脑/PR reviewer）解决，不再有静默游离空行。
- **共享文件的特殊处理**：`DECISION_LOG.md`/`BRAIN_TASKBOARD.md`/`CLAUDE.md` 这类高频并行改的文件，
  隔离后每会话在自己分支改、合并时集中解决冲突——见 §2 的预留区段制把冲突降到最小。

---

## 2. D 号 / T 号预留区段制（把合并冲突降到最小）

隔离后最容易冲突的是 `DECISION_LOG` 的 D 号追加（多会话都往表尾加）。**预留区段制**：

- 每会话分配一个 **D 号区段**（如按百位分段 v2=D-700..799 / v3=D-800..899 / v4=D-900..999）——
  各会话只在自己区段追加，**物理上不抢同一行**，合并时 D 号追加零冲突。
- **T 号同理**（任务板认领行）：按会话预留 T 号段。
- **代价**：D 号不再全局连续（v2 的 D-700 和 v3 的 D-800 可能同时刻产生）——但台账本就是「追加不覆盖」，
  连续性非必需；换来的是零撞号（本会话 D-502 三重撞号、T70 撞号那类事故结构性消失）。

## 3. O-5 / O-7 共享索引纪律的退役条件

- **现行 O-5/O-7**（根 `CLAUDE.md` §「多会话协调」）：`git commit <pathspec>` 绕过共享 index、逐行 `git diff --cached`、
  未跟踪文件先 add、防搭车——**全部是为"共享同一 index/工作树"设计的防撞纪律**。
- **退役条件（明确写下）**：**当 worktree 隔离全面落地（所有执行会话都在独立 worktree + 独立分支）后，O-5/O-7 整节退役**——
  因为它防的撞车（stage 卷入、搭车、游离空行）在隔离下**物理上不可能发生**（演练 §0 已证）。
- **过渡期**：隔离迁移期间（部分会话已隔离、部分仍共享树），O-5/O-7 对**仍共享树的会话**继续有效；
  全部迁移完成才整节退役。**退役 = 从 CLAUDE.md 删除该节 + DECISION_LOG 记一条「O-5/O-7 随隔离落地退役」的 D 号**。

## 4. 回滚路径（worktree 不适应可退回共享树）

- **回滚触发**：若隔离带来新问题（如 worktree 磁盘开销过大——每个 worktree checkout 全部 1434 文件；
  或 PR 合并流程拖慢单人+AI 的高速节奏；或大脑合并成为瓶颈）。
- **回滚动作**：①停止新建 worktree，各会话 `git worktree remove` 回到主树；②恢复 CLAUDE.md 的 O-5/O-7 节
  （若已退役，从 git 历史恢复）；③D 号/T 号预留区段可保留（无害）或取消。
- **回滚成本低**：worktree 是**叠加**在现有共享树之上的（主树 `feat/result-dev-v2` 始终在），
  退回只是"不再用 worktree"，不需要迁移数据——这是本方案相对"改仓库结构"的最大优势。
- **建议**：**先试点一个会话对（v2+v3）用 worktree 跑一个冲刺**，验证磁盘/合并流程可接受后再全面推广；
  不可接受则回滚，成本仅为几个 worktree 的建删。

### 5.1 现场佐证（非演练 · 2026-08-29 真实发生，比演练更硬）

演练是构造的，这条是**本会话正常干活时自发撞上的**——同一危害的真实实例：

- **事件**：v4 提交自己的提案后跑**全仓渲染守卫**（`test_docs_commands.py`），红在 `TEST_MASTER_PLAN_v2.0.md`（**v1 的 SPEC-1 文件，v4 全程未碰**）。守卫报"line 183 五单元格 vs 表头四"。
- **追证（纯只读，实证不转述）**：`awk` 数**物理** 183 行是四单元格——与守卫报数**对不上**；`splitlines()=189` vs `split('\n')=190` 一度疑为异形断行符，核实是**末尾换行**的正常差、非异形符；`git log` 显示 v1 正连续提交该文件。**结论：v4 跑守卫的瞬间，撞上 v1 一张表的在飞中间态**。v1 随后提交 `2e7e602`（大脑裁 D-576）后守卫**自愈、PASS**。
- **这正是本方案要治的形状**：全仓门红在"**别的会话正在改、我不拥有**"的文件上——**隔离下 v4 会跑在自己 worktree 的一致快照上，不是被 v1 改着的移动靶，这个假红根本不会出现**。
- **附带立的一条运维规则（隔离落地前也适用，大脑已采纳用于其跑 `verify_all`）**：**全仓守卫红在他会话在飞的文件上时，先核是不是在飞中间态再定性**——判读信号=`awk` 物理行的单元格数与守卫报数对不上（说明守卫读到的与磁盘现态不是同一份）。
- **边界**：全程纯只读追证、未改 v1 文件；由 v1 自己的提交解决。共享树纪律的"只读边界"在此案例中守住。
