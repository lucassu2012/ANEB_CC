## 0. 一页结论

**项目不是停滞，是"仪器造好了、数据没采够、关键路径全悬在人身上"的错位。**

- **仪器侧完成度约八九成**：app 端 Kotlin/Compose 主代码 ~2.9 万行 + 899 个单测；server Go 5,978 行 + 97 个测试函数；scripts 分析链 13,103 行 + 16,920 行测试；verify_all 19 门全绿；交付包 08-22 起处"终稿候选，待 PO 验收"。TODO/FIXME 密度近零——代码不是占位货。
- **成果侧完成度不足一成**：真实测量语料只有 **73 run**（单点位 SZ-PILOT-01、单运营商 ctcc、4 天窗口、73/73 low_confidence），对照分析链自设目标"1000+ 样本综合报告"约 7%。v1.0 计划里唯一对外强感知交付物《城市热力卡与归因报告》至今不存在。
- **执行吞吐已被实证不是瓶颈**：08-19 与 08-21/22 两次 48h 自主授权窗，"原 7 天计划主体 ~24h 完成"、单日 48 提交收口。
- **解法**：PO 半天清欠会 → 需求基线 v2.0 锁定 → 四份 SPEC 分发四个会话 → **PO 侧配合到位后约 2 周（10–12 个工作日）可交付**"豆包首批数据 + wave-1 外场热力卡 + s4 闭环 + 交付包 v2 验收"。

## 1. 为什么"一个多月没有明显进展"——五个真因

### 1.1 "进展"被记成了流程产物，而不是数据与交付

- 43 个档案日入册 **561 条决策**（编号至 D-564，日均 13+ 条），对应的真实测量只有百余 run；决策抽样中"守卫/纪律/订正/表格式"类占 55–60%，07 月底高峰段抽样高达 ~87%。
- 08-22 冲刺日 48 个提交、8,509 行改动中：证据归档 44%、自动生成 schema 24%、测试与守卫 23%、**产品主线代码仅 412 行（4.8%）**；记账类提交占 75%（36/48）。
- 整天规模的交叉对抗审计（T13/T14/T16）全天产出"确认 1 条缺陷 + 诚实的否定 17 条"；对一份 101 行的交付包文档动用 6 agent / 105 万 token / 353 次工具调用做审计，随后又做"审计的审计"。

### 1.3 流程体系自我增殖，元层复利增长

- 一个普通功能从动手到入册约 9 道手续（认领→守卫→突变审计→19 门全链→证据归档→D 号入册→回执→简报→抽查）；THERMAL 一个小接线产生 7 个提交、2 次全链归档、3 条决策 + 1 条补注。
- verify_all 19 门峰值一天全链跑 51 次，274 份日志全部入库；scripts 测试代码（16,920 行）已超过被测代码（13,103 行）。
- 多会话共享同一工作树是大量纪律的根源：pathspec 提交、逐行 diff 复核、撞号让号、stage 事故（723 行他人文件被卷入、派单行被吞掉改号 T15→T16）、"他会话游离空行"守卫、五层督导栈 + 40 分钟死人开关。**这套体系抓过真问题**（D-532 幽灵门从未执行却每次报 PASS、G-1 假绿、H-1 交付包踩红自己的守卫），但它管的全是"内部诚实"，而项目的硬阻塞全在外部——内部越转越快，外部原地踏步。

### 1.4 需求顶层从未重新锁定，PO 转向周期短于战役闭环周期

- SYSTEM_DEV_PLAN v1.0（07-17）发布当日核心假设"三级部署"即被 D-48 推翻，此后靠 PLAN_ALIGNMENT §7.5"失效字样台账"打补丁，从未重立基线 v2——每个新会话开工前都要先做一轮"计划 vs 现实"考古（PROFILE2/PROFILE4 两份规格的 §0 都在干这个）。
- 三次转向有案可查：07-31 M2 由 6–8 点位缩为 1 点位 → 08-04（档案）外场整体暂停 + 转吞吐探针 → 08-24 豆包战役直派（当日撞三条环境阻塞转 BLOCKED）。**扩展轮经提案→彩排→守卫修复→生成器四轮准备全备，外场一轮未跑**——每次转向都把上一条线的收口成本沉没。
- M3 核心需求"业务画像网络层参数"与自家红线（D-24/D-61 不解密不 MITM）不可同真，portraits 七字段×四 App 全 null 挂 PENDING-BY-CALIBER 六周，没人回头请 PO 重裁需求口径。

### 1.5 两处纯感知扭曲，放大了"没进展"的观感

- **时钟事故（D-494）**：08-19 前全部档案日期慢 10 天，档案 08-06..08-14 九天空白是结构性不存在，不是九天停摆。真实停摆 ≈ 8 天（宿主停机 ~4 天 + 尾部等待），占真实总历 39 天的约 1/5。真实有效工期约 4.5–5 周；按计划应处 M2 收尾段（不是想象中的"第 6 周末应到 M3"）——滑点存在，但被夸大约一个里程碑。
- **诚实性纪律持续下修既有结论**：AQS 89 标注"不能读作定论"、n≥15 判据自我推翻重推（D-473/474）、RAT/忙闲效应被 D-471 归零为未定——科学上是收紧，观感上是原地踏步。

## 2. 优化方案

### 2.0 第一步（一切的前提）：PO 半天"清欠会"

把 §1.2 的 8 项一次清完，每项都要有显式结果——**"不给"也必须入册**（例如"第二张 SIM 不办→双运营商目标正式降级"），杜绝任务半悬。这半天是全部 ETA 的起点 D0。

### 2.1 需求基线 v2.0（锁定需求）

由 PO 在清欠会上裁掉三个顶层悬空问题，随后落成一份**可改写、带版本号**的《需求基线 v2.0》，取代"v1.0 不可改写 + 失效字样台账"补丁制：

1. **主交付物排序**：交付包收尾 / 豆包战役 / 外场热力卡三者定序（三者的环境阻塞高度重叠，同一批到场动作可同时解锁，但 spec 拆分与会话分派完全不同）。**同时定义验收方**——当前"读者视角终验 = PO 验收本身"，全仓无外部客户/验收标准定义；若最终读者是运营商局点（"带数据进局点的弹药"），验收标准要从那里倒推。
2. **M3 画像口径三选一**：PENDING-BY-CALIBER 字段正式放弃 / 改 UI-proxy 口径纳入 / 解禁受控采集。
3. **外场线复活与否**：扩展轮设计全备只差执行令；不复活也要显式作废入册，释放沉没成本。
4. 新规则：**转向只在战役边界生效**——in-flight 战役要么跑完、要么显式作废入册，不许无限挂 DOING。

### 2.3 流程减负（六砍四保）

**砍**：①认领/回执/登记类 1–2 行提交并入 feat 提交或每日一次批量记账（可砍当日约一半提交事务）；②决策入册门槛提为"改变行为/口径/边界"，摘要 ≤200 字，"自查无问题/补注"并入原条目；③verify_all 分层触发（见 SPEC-3）；④文档禁止写死门数/测试数字面量，由脚本生成徽章行（H-2/H-3 一族订正循环整体消失）；⑤多 agent 审计只保留"方向性错误"镜头，降频为按周抽样；⑥worktree/分支隔离 + 合并走 PR，整节共享索引纪律退役。

**保**：①四态证据核心语义（NOT_EXECUTED/BLOCKED_EXTERNAL 永不折算 PASS，建议 -Strict 设为默认）；②发布门 + gate-integrity 本身（减频不减门）；③突变测试对守卫类代码的强制（范围不扩展到业务代码）；④树边界与设备实况检查。

**节奏**：周度 /goal 48h 授权窗固化为常态（两次实证吞吐极高）；每周一页《业务进展视图》只写"新增了什么数据/回答了什么业务问题/离热力卡还差几步"，与决策台账分离；决策请求一律一页清、PO 承诺 48h 内批复或显式挂起。
