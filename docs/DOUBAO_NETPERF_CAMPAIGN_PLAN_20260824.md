## 0. 一句话结论（先给 PO）

**原文那套方法（破解 POW + 免 root MITM 重打包注 CA + mitmproxy L7 整形 + 纯 API 精确回放）
在本树对真实 App 是红线禁止的**（D-24/D-49/D-61：不解密、不注入证书、不 MITM、观察模式 only），
**不能照搬**。但原文要问的那个问题——「豆包各项功能到底向网络要什么」——**可以在本树红线内、
用一套不同的装置回答**：**设备外 L3 透明整形（PC 热点侧，不碰 App、不解密）＋ 观察模式采集
（无障碍事件／帧差／免解密抓包）**。代价是三条硬约束（§6）：**无服务端精确 token 计数**（σ=0
那条铁律不可测）、**只能 UI 呈现口径**（绝对值不可与原文 API 口径互比）、**样本必须人工驱动
故规模远小于原文 2005 条**。本文给出可落地的**缩小版战役**，并列出解阻它所需的三件事（§7）：
一次设备窗授权、一套 L3 整形器（需新建＋验证可行性）、以及若干 PO/大脑裁定。

## 1. 与原文的分工：什么能迁移，什么不能（诚实的差异表）

原文十条结果单元（A–J，见 `ds_paper.md` 第五节）逐条对账。**「口径」列是全文最要紧的一栏**：
凡标「UI 呈现口径」者，其绝对值**不可与原文 API 口径互比**（原文 §3.5、§八第 2 条已自证 API
基线 TTFT≈2s 含多跳代理，设备 UI≈0.6s）；凡标「不可测」者，本战役**不宣称**该结论。

| 原文单元 | 原文结论 | 本战役能否迁移 | 迁移口径与手段 / 不能的理由 |
|---|---|---|---|
| **A** 时延→TTFT ~1:1 | 斜率 0.84–1.06 ms/ms | **✔（UI 呈现口径）** | 通道 A 无障碍事件取 UI-TTFT（A0′→A2，豆包基线实测 1984ms，D-52/D-54）；L3 加时延档扫斜率。**斜率可测，绝对值不可比原文** |
| **B** 丢包→卡顿 2–5% 膝点 | loss5→67%、loss10→100% 卡顿 | **✔（口径三重代理声明）** | L3 丢包；卡顿＝cadence 间隔 ≥阈（通道 A）／帧差（通道 B 粗）。**膝点形状可测**。⚠ 口径：本战役的 L3 丢包，既非原文 L7 逐块停顿、更非 RF 物理丢包——**是第三种代理**，须显式声明 |
| **C** 下行→吞吐 16kbps 地板 | 133–139 tok/s 封顶、8k 悬崖 | **⚠ 部分（弱化）** | **无服务端 token 计数 ⇒「tok/s 吞吐」不可测**。替代＝RCT（回答完成时长，但 A4 判据未落地，§3）对下行帽的曲线＋cadence。**能看地板/悬崖形状，不能给 tok/s 锚点** |
| **D** 上行→多模态 3.15s 协议地板 | 1.44MB<6s 需≥4.3Mbps 上行 | **✔（本战役最强迁移点）** | 豆包识图/文件上传：通道 D（PCAPdroid 免解密，只读方向字节与时戳，D-57）测 upload_ms＋上行字节；L3 上行帽扫。**这正是「功能对网络的诉求」最锐利的一问**，且证据链不依赖 MITM |
| **E** 抖动→TTFT 尾部纯均值平移 | ΔP95−ΔMean≈0 | **✔** | L3 抖动档；测 UI-TTFT 分布是否只平移不加尾。样本量要求较高 |
| **F** 输入体积→TTFT 6.4ms/KB | prefill 斜率 | **✘ 大部** | prefill 斜率分解需服务端时序＝API 口径。设备侧只能测「长 prompt vs 短 prompt 的 UI-TTFT 差」，**不能给 ms/KB 分解** |
| **G** 思考模式弱网墙钟 ×1.6 | loss10 下 19.3s vs 15.4s | **✔（有价值）** | 豆包**深度思考**模式 vs 普通模式，在 loss 档下测 RCT。**功能级迁移，直接答 PO 的「各项功能」** |
| **H** token 网络零弹性 σ=0 | long 恒 1246 tokens | **✘ 不可测** | **需服务端精确 token 计数＝MITM**。本树红线外。**本战役放弃该条**，至多定性说「答案内容不随弱网改变」，不给 σ=0 证据 |
| **I** 三维正交 | TTFT↔时延、卡顿↔丢包 | **✔ 部分** | loss×lat 网格在 UI 指标上建；正交主效应可观察。样本量是瓶颈 |
| **J** loss×lat 尾部超可加 | +680ms@p95 | **⚠** | 需网格＋p95 尾部＋足够样本；UI 口径噪声更大，缩小版战役下**列为拉伸目标**，样本不足即诚实报 `NOT_EXECUTED` |

**三条彻底出局（红线／口径所致，本战役不宣称）**：H（σ=0 token 铁律）、F 的 ms/KB 分解、
C 的 tok/s 吞吐锚点。**三条最值得做（红线内且直接答 PO）**：**D 多模态上行诉求**、
**G 深度思考弱网代价**、**A 时延→TTFT**。

## 4. 网络整形机制：设备外 L3（红线内的唯一可行路径）＋ 可行性

**为什么必须设备外**：本树对真实 App 红线＝不 MITM、不注 CA、不解密、不 `performAction`
（D-24/D-49/D-61）。因此**整形不能落在 App 里、也不能落在需要解密的代理里**。唯一干净路径＝
**在设备之外的链路上做 L3 透明整形**：P40 连一个 **PC 侧 WiFi 热点**，PC 用 L3 工具对转发流量
注入时延/丢包/限速。App 全程无感、流量不解密、tier 标签由整形器自报（可信）。

**候选工具**（按可行性排序，**均需实测确认，当前 PC 上都未装**）：

| 方案 | 机制 | 可行性风险 | 状态 |
|---|---|---|---|
| **A. PC 移动热点 + clumsy/WinDivert** | Win 移动热点(ICS) 转发 P40 流量，WinDivert 在 L3 抓转发包注延迟/丢包 | 需管理员；ICS 转发路径能否被 WinDivert filter 命中待验；限速（带宽帽）WinDivert 需自实现令牌桶 | **待建＋待验**（PC 无 clumsy/WinDivert） |
| **B. PC 热点 + 第三方 L3 整形（如 netem via WSL2 bridge）** | WSL2/Linux 侧 tc netem | WSL2 桥接热点转发路径复杂，Win↔WSL 网络命名空间隔离 | 备选 |
| **C. 独立 Linux 路由盒（树莓派等）做热点+tc** | 最干净、与原文 netem 同族 | 需额外硬件 | 若 PO 有硬件则最优 |

**本文推荐 A（clumsy 优先，它就是 WinDivert 的 GUI 封装）**，并把「热点转发可整形性」列为
**执行前必须先验证的第一件事**（一个 0 成本干跑：起热点→P40 连→`ping`／限速看 clumsy 是否命中）。
**这条与记忆里「抖音 QoE 用 WinDivert 热点 L3 整形」同源**，但那套 harness **未在本树/本机留存**
（只 `ds_netperf` 一个兄弟目录在），故本战役需**新建整形器**，不是复用。

**整形档定义可直接移植** `ds_netperf/profiles_def.py` 的档结构（lat/loss/dn/up/jit 语义），
分析侧可复用 `ds_netperf/analyze_dn_knee.py` 的膝点/线性拟合逻辑——**但整形执行层是全新的**
（原文是 mitmproxy L7，本战役是 L3）。

## 6. 规模现实：为什么必须缩小，缩到多小

### 6.1 原文的规模来自 API 自动化，本战役没有

原文 ~2005 条干净样本＝**API 精确回放自动跑**（可独占、可慢速、可跑满 35 档矩阵）。
本树对豆包**红线禁止任何注入/自动化**（D-49 观察 only；且 EMUI 在 a11y 服务开启时**拦截
`adb input` 注入**，§5.3）——**每一轮对话都得人工手敲手点**，探针只在旁观察。
**结论**：全矩阵（35 档 × 6 功能 × N≥20 ≈ 4200 轮人工对话）**不可行**，且每轮消耗真实账号额度
（豆包免费额度有限，D-50 逐字「最小化」）。

### 6.2 缩小版战役（可落地提案）

**只测「红线内 × 直接答 PO × 每单元最省样本」的三块**，每块选**功能差异/网络诉求最锐**的档：

| 批 | 功能 | 网络档（裁剪） | 指标 | 样本 | 答什么 |
|---|---|---|---|---|---|
| **批 D**（首选） | F3 识图上传、F4 文件上传 | `good`＋`up2m/512k/128k` | upload_ms＋上行字节（通道 D） | 每格 N≥5 | 「豆包多模态上传向上行要多少」——**最强、最不依赖 UI 口径** |
| **批 G** | F2 深度思考 vs F1 普通 | `good`＋`loss5/loss10` | RCT（若 A4 解阻）＋cadence | 每格 N≥5 | 「深度思考弱网代价几何」 |
| **批 A** | F1 文本对话 | `good`＋`lat200/lat800`＋`loss5` | TTFT_ui＋stall 代理 | 每格 N≥5 | 「首字时延吃时延不吃丢包」验证 |

**N≥5 是登记级下限**（不是回核级；对齐本树 D-474/D-50 的最小化实践），**样本量不足以给
置信区间，产出恒标 LOW/登记级**（`INSTRUMENTATION_SPEC` §4.4：G-5 未 PASS 前 confidence≤LOW）。
若 PO 要回核级（N≥20、多网络条件），需多个设备窗，工时按窗排。

### 6.3 F7 实时语音：单独说明

豆包实时语音的外部观测缺可行通道（无 `screenrecord`、不侵入麦克风、a11y 对语音 UI 事件稀疏），
**列为拉伸项**，不进缩小版首批。原文自己也把语音列为「未来工作」。
