> **⚠ 能力缺口（本单最要紧的一条，请大脑先裁再动工）**
> **clumsy/WinDivert 没有带宽帽（令牌桶）**——方案 §4 自己写着「**限速（带宽帽）WinDivert 需自实现令牌桶**」。
> **本单未独立验证该断言**（无法安装，见 §7），**按方案原文采信并标明出处**。
>
> **🔴 已独立验证，并订正其边界（2026-09-04，D-696；上文照留不改，它如实记录了当时的认知状态）**：
> 直接读 clumsy 上游源码 `github.com/jagt/clumsy` `src/bandwidth.c`（该文件首行注释即 `// bandwidth cap module`）：
> **clumsy 0.3 有独立的带宽限速模块**，UI 为 `Inbound`／`Outbound` 复选框 ＋ `Limit(KB/s)`，取值 `0`–`99999` KB/s
> （0.3 release body 列有 `bandwidth module by @skywind3000` PR#70；**该模块是 0.3 才有的，方案原文可能成文于更早版本**）。
> ⇒ **原断言分两半，一半对一半错**：
> **对的那半**——「没有**令牌桶**」属实，`bandwidthProcess()` 的核心是
> `if (rate + size > limit) { discard = 1; }` 随后 `freeNode(popNode(pac))`：**超限直接丢包，不排队、不缓冲**；
> **错的那半**——「带宽限速能力不存在」不成立，**它存在，只是实现语义是丢包式**。
> **🔴 这个差别是承重的，不是措辞**：令牌桶（`tc tbf`）超限**排队延迟** ⇒ RTT 上升、TCP 拥塞窗口平滑收敛，模拟真实窄带链路；
> 丢包式超限**丢弃** ⇒ TCP 触发重传/超时，实际达成速率远低于设定值且剧烈震荡。
> **后果落在归因上**：用它跑 `dn*` 下探所看到的性能崩塌，**分不清是「带宽不足」还是「丢包」**——
> 而 `loss1/2/5/10` 本就是另一个独立档族 ⇒ **两个档族会混淆，且混淆发生在本战役的主证据（膝点/悬崖）上**。
> ⇒ **`D-656` ① 的裁定结论（限速档本批不覆盖）维持不变，但其理由必须订正**：
> 不是「做不到」，是「**做得到但语义不干净，会污染主证据的归因**」——
> 这与本册「把模糊判据硬编成假精确比不编码更坏」同族。
> ⇒ **新增一个保底选项 (d)**：若 Linux 盒长期没有，可用 clumsy bandwidth 跑一批**探索性**限速数据，
> 但必须在格 README 与 `RUN_KIND.json` 里**显名标注「丢包式限速，非令牌桶」**，且**不得与 `loss*` 档结论合池**。
> ⚠ **(d) 尚未验的两件**：①该模块的实际限速精度（限速器自身误差直接算进档语义）；
> ②`crate_stats` 的滑动窗口尺度与我们的测量窗口是否同量级。**未验完不得启用 (d)。**
> 后果不是「少几个档」：**下行限速档正是本战役的核心结论来源**——膝点／悬崖（`dn` 下探到 64k/32k/16k/8k）
> 是「网络诉求」这个命题的**主证据**，而 §2.2 把 `up*` 档专留给 F3/F4 多模态上行诉求。
> ⇒ **三条路，取舍归大脑**：
> **(a) 自建令牌桶**（在 WinDivert 之上写限速层）——可行，但那是**工程件**，须排期、须测准（**限速器自身的误差会直接算进档语义**）；
> **(b) 改走备选 C**（独立 Linux／树莓派 `tc netem` ＋ `tbf`）——**带宽帽是 tc 原生能力**，与原文 netem 同族、最干净，代价是**需要硬件**；
> **(c) 本批只跑「能直接出」的档**（lat/loss/jit/复合），**下行/上行限速档明确标为「本批不覆盖」**——
> 不是删掉，是**如实登记为未覆盖**，避免下游把「没有膝点数据」读成「没有膝点」。
> **v4 倾向 (b) ＞ (a) ＞ (c)**：(b) 一次性解决且不引入自制测量器的误差；(a) 会让**整形器本身变成一件待标定仪器**
> （本仓吃过「被造物不可能比造它的模具更精确」的亏）；(c) 保底，但会让本批答不了核心命题。
>
