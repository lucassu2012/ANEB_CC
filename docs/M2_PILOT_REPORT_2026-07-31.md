### 2.2 关键 KPI（忙时格中位）

| KPI | 中位 | 分级 | 三个 profile 各自的中位 |
|---|---|---|---|
| 首字时延 T1 `t1_ttft_ms` | 53.26 ms | excellent | 53.01 / 53.26 / 54.07 —— 一致 |
| 字间时延 T2 `t2_itl_p95_ms` | 29.50 ms | excellent | 15.02 / 30.16 / 30.31 —— 2 倍 |
| 上行吞吐 U1 `u1_goodput_mbps` | 10.05 Mbps | good ⚠ | **0.14 / 10.05 / 16.43 —— 117 倍** |
| **往返时延 N1 `n1_rtt_p50_ms`** | **64.13 ms** | **fair** | 62.55 / 65.03 / 65.07 —— 一致 |

**⚠ U1 那一行不要按字面读**，它是本轮第二个「数字本身没错、读法会错」的地方：
中位 10.05 恰好等于 `s2_coding_agent` 一家的值，而三个 profile 的取值区间**完全不重叠**
（0.125–0.153 / 8.68–11.52 / 14.95–17.98），**中位谁都不代表**。

成因**不是网络，是负载大小**：三者的 `upload_burst` 单次分别是 **2 KB / 512 KB / 1 MB**
（`s3` 跑两次 1 MB；它配置里那两条 12 MB 是 `download_burst`，走 D1 不进 U1）。
已实测证实——把每次上传的耗时换算成该次自己的 RTT 的倍数：

| profile | 上传量 | 耗时 ÷ 该次 RTT | 读法 |
|---|---|---|---|
| `s1_chat` | 2 KB | **1.60–1.99（中位 1.77）** | 不到两个往返就传完，拥塞窗口从未打开 |
| `s2_coding_agent` | 512 KB | 5.69–7.69 | 已离开纯时延区间 |
| `s3_multimodal` | 1 MB | 6.83–9.75 | 同上 |

即 `s1_chat` 的「0.14 Mbps」= `2KB ÷ 1.8 个往返`，是**一个披着 Mbps 单位的往返次数，
不含任何带宽信息**——12 次测下来这个倍数几乎不动，正说明它跟着 RTT 走、不跟着带宽走。

**由此带出一个必须上报的问题（不在分析层，在评分/画像侧）**：设备给 `s1_chat` 的
11 个场景**全部判 `u1_grade=poor`**（11/11），而该格印出的一个词是 `good`——
那是 33 个场景里 22 个的众数，**被盖住的 11 个不是「稍差」，是最差档**。
这不是本点位的问题：**只要 `s1_chat` 的上传量仍是 2 KB，任何点位、任何一轮都会得到
一个恒定的 `poor`**。两个可选处置，请 PO 与画像/评分属主定：
①把 `s1_chat` 的 U1 排除在评分之外（承认 2 KB 测不出吞吐）；
②把它的上传量提高到能离开时延区间的量级（≥256 KB）。

> **已批**：PO 2026-08-01 拍板**选项①**（D-366）。落地时发现**评分侧本来就没算过它**
> （`AqsInputMapper` 合同：U1 ← S3 的 1MB 上传，S1/S2 的上传都不进 AQS——诚实的否定），
> 需要改的是**分析层的跨 profile 汇池**：分 KPI 热力卡与预热效应段现已按裁决排除
> `s1_chat` 的 U1 读数，**逐格计数交代**（`RULED_OUT:s1_chat×N`，三个输出面同到），
> 判据常量已入溯源清单。逐 profile 表（复测稳定性等）保留原值——它作为时延代理是诚实的。
> 排除后该格实测中位 = **13.24 Mbps（n=22，`RULED_OUT:s1_chat×11`）**，证据包 CSV/热力卡
> 已按新口径重生成；上表的 10.05 是**裁决前**的汇池历史值，保留供对照、不再是现行口径。

**总分 excellent，而 N1 只有 fair** —— 这不是矛盾，是**总分掩盖了短板**：
分数侧归因把 **N1 点名为拖累维度**（该格 N1 子分 68.1，是七个子分里最低的）。
读法：**AI 交互体验好，是因为首字与吐字都快；真正拉后腿的是基础往返时延**。
64ms 的 RTT 与 §1 记的「到 E-01 ping ≈44ms」同量级，差额是应用层往返与服务端处理，
**不宜进一步归因**——单层级下没有分段证据，且本轮没有无线上下文。

分段归因在**单层级**下只有**接入段绝对值**：最大单项 `s2_coding_agent·接入=65.1ms`，
且**未见单点异常**（MAD 稳健筛查未越阈）——即它落在该段分布内，**不构成「这个点位这一段有问题」**。

### 2.3 复测稳定性（本轮最有决策价值的一段）

| profile | n | 中位 | CV% | CV 门(≤10%) | 需 n≥（80% 把握看见 5% 差异） |
|---|---|---|---|---|---|
| s1_chat | 11 | 53.26 | 5.5 | 达门 | 13 |
| **s2_coding_agent** | 11 | 54.07 | **10.3** | **✗ 超门** | 47 |
| s3_multimodal | 11 | 53.01 | 5.9 | 达门 | 15 |

**前提已核对（诚实的否定，但判据留下）**：上面这套「需 n≥…」的算术，前提是**同一格的重复可交换**
（同分布抽样）。若 11 次读数随时间漂移（发热、服务端预热、网络负载），CV 会低估单次读数的散布，
加大 n 也买不到它承诺的把握。**实测 24 分钟窗内未见漂移**：与时间的秩相关
rho = **+0.49 / +0.27 / −0.15**（TTFT / RTT / 吞吐；n=11 的 5% 显著阈约 0.62），
前半段与后半段中位仅差 **2.0% / 1.8% / 2.9%**，远小于实测 CV 5.5–10.3%。
→ **可交换性成立，采样量结论可用**。（判据与序列见 `evidence/m2_pilot_20260731/drift_check.py`。）

**这直接检验了 D3 的 n=11**：n=11 是按 **CV≈5%** 推出来的「八成把握」拐点，
而实测 CV 为 **5.5 / 10.3 / 5.9%**——**都不小于 5%，编码 Agent 场景是它的两倍**。
按实测重算，**80% 把握需要 n≥13–47（中位 15）**，所以：

- **本轮 n=11 不足以支撑「5% 的差异看得见」**，只能给量级指示；
- `s2_coding_agent` **CV 已超门**，`需 n≥47` 只是把噪声摊薄的算术，**不解决它本身不可重复**——
  **先查原因**（该场景的工具循环阶段本身抖，还是设备/环境），别照着 47 硬加复测。

### 2.4 追加实测：**快测测的永远是「冷」的那一轮**（4 轮取证语料，D-355）

试点报告原本只能说「拉丁方未轮转、序位效应无法校验」。补跑 **3 轮取证**、连同首轮探针
（D-354，已并入 `forensic_raw.jsonl`）共 **4 轮**（每位次 n=4）后
该问题**已可判定**：9 处全部可判，**6 处判为疑似位次相关**。但把同一份语料**换一种切法**
就看清了真正的成因——

| 切法 | t1_ttft_ms | n1_rtt_p50_ms | u1_goodput_mbps |
|---|---|---|---|
| **按轮次**（第 1 轮 → 第 2/3 轮） | 51.75 → 47.35 / 47.13（**−8.5% / −8.9%**） | 60.20 → 53.01 / 53.62（**−12.0% / −10.9%**） | 10.26 → 11.96 / 11.26（**+16.5% / +9.7%**） |
| **按轮内位次**（第 1/2/3 个场景） | 48.64 / 47.71 / 49.82（−1.9% ~ +2.4%） | 56.76 / 56.88 / 59.01（+0.2% ~ +3.9%） | （仅 S3 贡献 U1，与按轮次同一分组） |

**结论**：差异**几乎全部来自轮次**，而非场景在轮内的先后——这是**预热/冷启动效应**
（首轮付掉 App 冷启、TLS 握手、无线唤醒的代价），不是拉丁方失效（反平衡实测成立，9/9 位次由同一组单元供样）。

**这直接改变前面每个绝对值的读法**：**快测模式只有一轮**，所以 §2.2 的
TTFT 53.26ms、RTT 64.13ms 都是**冷启动读数**；同一台设备同一位置，第 2/3 轮是 **TTFT ≈47ms、RTT ≈53ms**。
**冷热差（约 9~12%）比本轮采样量计划想分辨的 5% 还大**——横向比格子仍然公平（每格都一样冷），
但**任何绝对数字都必须标明它是冷启动口径**。

**追问：预热到底是「无线唤醒」还是「App/TLS 冷启动」？——已用对照实验答出（D-358）**

同点位、同时段又跑了 **4 轮 WiFi 取证**做对照。比较的量是**同一 run 内**「首轮 vs 后续轮」的差值
（**配对量**），所以两个采集窗之间的慢漂移**造不出也掩不掉**这个效应：

| KPI | 蜂窝（4 轮） | WiFi（4 轮） | 倍数 |
|---|---|---|---|
| t1_ttft_ms | **+9.5%** | +3.9% | 2.4× |
| n1_rtt_p50_ms | **+14.6%** | +4.1% | 3.6× |
| u1_goodput_mbps | **+8.9%** | +3.9% | 2.3× |

**已排除「基线不同造成的百分比假象」**：按**绝对毫秒**同样是 2 倍量级
（TTFT +4.71ms vs +2.05ms = 2.3×；RTT +7.83ms vs +4.02ms = 1.9×）。

**结论**：预热的**主要成分是无线唤醒**（RRC idle→connected / C-DRX），
**但没有完全消失**——WiFi 上仍有约 **4%** 的残余，那部分是 **App/TLS 冷启动**。
**对本项目的直接含义**：战役口径是**蜂窝**，正是预热代价最大的那一侧；
「丢弃一轮预热」在蜂窝上值 **RTT 约 15%**，在 WiFi 上只值约 4%。

**建议**：正式轮要么①在每次测量前跑一次**丢弃的预热轮**（**推荐**：代价一轮、收益是把
最大的一项系统性偏差移出结论），要么②改用取证模式并**明示丢弃第 1 轮**，
要么③保持现状但在报告里**把「冷启动口径」写进结论句**。三选一是 PO 的口径决策，不是工具能替的。

> **已批**：PO 2026-08-01 拍板**选项①**（D-366）。操作步骤与台账要求已写进
> runbook §0.6.1 ③；此后计入 run 的绝对值口径 = 「射频已热、App 冷」。

**顺带一个可能有价值的观察（但只是一次、一地、n=4）**：本地点 **访客 WiFi 明显劣于 5G SA**
——分析层的介质对比段给出 Δ(蜂窝−WiFi)=**+3.3 AQS**、噪声尺度 ±0.7（超噪声）；
原始 KPI 差距更大（RTT 中位 90ms vs 53ms、上行 7.5 vs 11.5 Mbps）。
**注意**：绝对水平的比较**没有**配对保护，两臂采集窗相差约半小时，
且这是一个访客 AP——**不得**据此对「WiFi vs 5G」作一般性结论。

（证据：`evidence/m2_pilot_20260731/forensic_raw.jsonl` 与 `forensic_labelled.jsonl`，4 轮 × 9 场景。
限制：单点位、单时段、n=4 轮——效应在三个 KPI、三个 profile 上方向一致，但仍是一次会话的观测。）

## 4. 建议（供 PO 决策）

1. **扩展轮的 n 按实测重算**：若目标仍是「看得见 5%」，`s1/s3` 取 **n≥15**，
   `s2_coding_agent` **先定位它为何抖**再决定 n——这是本轮最值钱的产出。

   > **已定位（D-372，2026-08-01，`s2_jitter_probe.py` 三假设裁定）**：逐一剔除后 CV 仍
   > 8.6–10.9%（**非单点异常**）、与时序秩相关 −0.03（**非时间趋势**）、同批 RTT CV 仅
   > 3.6% 且 TTFT~RTT 相关 0.00（**抖动不在网络路径**）——s2 的 TTFT 噪声是**场景/服务端
   > 内生**的（TTFT 排在 512KB 上传 + tool_loop 之后）。**推论**：拿 s2 的 CV 去推「网络
   > 采样量」会高估 n；扩展轮 n 按 s1/s3 的网络侧 CV 定（**n≥15**），s2 的门按其内生
   > 噪声**单列口径**（或对 s2 放宽 MDE 目标），不再作为「加测网络样本」的理由。
2. **无线上下文接线**（`RADIO_CONTEXT_WIRING_SPEC.md`）优先级应提前：
   没有它，任何跨点位/跨时段的差异都无法排除「信号差」这个解释。
3. **取证模式（forensic）已实跑验证**（单轮 6.5 分钟，9 场景、三种轮次、`repeat_index` 0/1/2）：
   拉丁方**确实轮转**，但**一轮不够**——每个位次只有 1 个样本时位次差与噪声不可分离（D-354）。
   要得到序位效应的真结论，**至少跑 2 轮、建议 4 轮**（每位次 n≥4）。
   注意它**不能**解决自评低置信：取证轮同样 9/9 场景 `valid_low_confidence`（见下附）。
4. 点位真名补进 `campaign_grid_shenzhen.json` 后即可复跑，其余参数不动。
5. **（当晚补充，D-365）闲时对照探针实测：同点位 23 点反而全面更差**——暖轮 RTT/TTFT
   +26~34%，且 CGNAT 出口 IP 变了（路径不同）；候选解释三个（路由/夜间节能/小区变化）
   今晚分不开。**这不改本报告任何数字**（探针独立 campaign_id），但说明 D4「只测忙时」
   躲开的是一个真变量——**跨时段扩点前，无线上下文（建议 2）与出口 IP 必须随采**。
   证据见 `evidence/m2_idleprobe_20260731/`。

## 5. 本轮暴露并已修复的分析层缺陷（真实数据的第一份回报）

| # | 缺陷 | 影响 |
|---|---|---|
| D-350 | 发布门在**单层级**语料上印「N 个格**三层级**接入介质一致」 | 发布前必读的表上的**假陈述** |
| D-351 | 一条 run 被标 `MIXED_PROFILE_VERSION`（其实是三个不同 profile 各自的版本） | 该标记会在**每份真实语料**上永久误报 |
| D-352 | 打分器自评低置信只到表格、**没到摘要** | 决策者只读摘要，会把 89 当定论 |
| D-354 | 单条取证轮里每个位次只有 1 个样本，却判「**疑似序位偏倚**、本报告 KPI 中位存疑」 | 位次差**就是**运行间噪声，该比较什么都判不了，却把整份报告打成存疑 |
| D-360 | 分 KPI 热力卡把一格里三个 profile 汇成一个中位，**不说汇了谁** | 就是上面 §2.2 那一行：U1 中位 10.05 谁都不代表 |
| D-361 | 跨单元异常筛查里，**测过一次的单元与测过十一次的等权** | 既能拉动阈值、也可能自己被点名，把人派去追一个单次噪声读数 |

六条都是**跑真数据跑出来的**，合成语料一条都没暴露——这本身是本次试点最重要的结论之一。
原因是结构性的：彩排语料**每格样本数整齐、维度齐全**，而外场第一天就是单层级、单格 `n=1`、
每条 run 都自评低置信。这六条已合并成分析层的一条新红线（交接文档 §2.15：
**一个汇池出来的数，必须交代它汇了谁、每份多大**），并已用突变审计验过守卫确实存在。

**附:低置信为何恒为真(实测溯源)**。契约只导出「低置信」这个**判词**,不导出**理由**——
per-KPI 的 sampleCount/lowConfidence 只活在设备上。按 `KpiCalculator` 的口径,
任一 KPI 样本数低于其下限(U2<8、echo<10、U1<3、D1<3、TTFT<3、ITL 配对<100)即低置信,
而**实测 36/36 场景全为 `valid_low_confidence`**,快测与取证**都一样**。
所以这个标记当前**恒为真**、无从定位是哪一项不足——
**建议把 per-KPI 的 sampleCount 与 lowConfidence 纳入结果契约**(下一轮契约演进),
否则「分数自己声明了不确定」这句话读者只能看见、无法据以行动。

`VALID_LOW_CONFIDENCE`,而生产端写的是小写 `valid_low_confidence`;契约门把它记为
**advisory(非致命)**而非违规,分析层也已统一小写归一化,故**今天没有下游受影响**。
但**两个事实源对同一枚举各说各话**是个潜伏陷阱:任何新消费方若照 schema 字面比较,
