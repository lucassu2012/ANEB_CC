## 1. 采样量论证：扩展轮取 **n ≥ 15**（点 ①）

### 1.1 结论先行

扩展轮每格网络侧 KPI（首字时延 T1 / 往返时延 N1 等）复测数取 **n ≥ 15**，
判据来自 **s1 / s3 的网络侧 CV**（5.5% / 5.9%），**不用 s2 的 CV 定 n**（理由见 §1.4）。
此结论与试点报告建议 1、决策 D-372 逐字一致
（报告 §4：「若目标仍是『看得见 5%』，s1/s3 取 n≥15」；D-372：「扩展轮 n 按 s1/s3 的
网络侧 CV 定（n≥15）」）。

### 1.2 采样量模型（把算术摊开）

网络侧 KPI 复测数与「变异系数 CV」「目标最小可辨相对差异 MDE」的关系，正态近似下为：

```
n_required  ∝  ( CV / MDE_rel )²          （固定置信与把握时）
```

即 **n 随 CV² 增长**（固定 MDE 与把握）。这正是 `stability.py --plan` 的
`需 n≥(80%)` 列背后的模型（两列语义见 runbook §3 与 D-201/D-240：
`需 n≥(80%)` 是让目标差异有 **80% 把握**被判为「超噪声」所需的 n；
`需 n≥(平)` 是让差异恰等于噪声尺度、检出率仅约五成的 n，**不可拿来规划**）。

- 设计目标（沿用试点口径，均有据）：**MDE_rel = 5%（相对）**、**把握 = 80%**
  [runbook §3 / 试点报告 §2.3]。
- 说明：`需 n≥(80%)` 列内置的显著性水平 α 未在源文档显式印出，故本文不臆断其精确值
  （不写「95%」）；把握 80% 与 MDE 5% 是文档明载的，n 的具体值直接取工具已发布的输出，
  **不由本文重新推导**（见 §1.3）。

### 1.3 代入实测 CV（数字取自试点已发布的 `需 n≥(80%)` 列，不臆造）

| profile | 网络侧 CV%（实测） | `需 n≥(80%)`（工具输出） | 来源 |
|---|---|---|---|
| s1_chat | **5.5** | **13** | 试点报告 §2.3 / D-353 |
| s3_multimodal | **5.9** | **15** | 试点报告 §2.3 / D-353 |
| （取上界，即扩展轮 n） | — | **15** | 报告 §4 建议 1 / D-372 |

**取 max(s1, s3) = 15 → n ≥ 15。**

**自洽交叉核验（只用已引用数字，不引入新常量）**：由 n ∝ CV² ，
以 s1 的 `n≥13`（CV 5.5%）为锚推 s3（CV 5.9%）：

```
n_s3 = 13 × (5.9 / 5.5)²  =  13 × 1.151  =  14.96  ≈  15   ✓
```

与工具发布的 15 一致——说明「s3 因 CV 更高而需要更多复测」这一步是 CV² 标度的直接后果，
并非另设参数。

**同时印证「n=11 已不足」**：n=11 是按 **CV≈5%** 推的 80% 把握拐点
（n=5 只有 63%、n=11 到 80%）[grid-design §3.1 / D-353]；而实测 CV 均 **不小于 5%**
（5.5 / 10.3 / 5.9%），故 80% 把握需 **n≥13–47（中位 15）**[试点报告 §2.3 / D-353]。
本轮 n=11 只能给量级指示，扩展轮据实测上调到 n≥15。

### 1.4 为什么**不**用 s2 的 CV 定 n（关键约束，D-372）

s2_coding_agent 实测 CV **10.3%**（超 10% 门），照它推需 **n≥47**[试点报告 §2.3]。
**但 s2 的抖动是场景/服务端内生，不在网络路径**——D-372 用探针一次裁定三假设：

- **H1 单点异常 → 否**：逐一剔除后 CV 仍 8.6–10.9%（没有哪次 run 在背锅）；
- **H2 时间趋势 → 否**：与时序秩相关 −0.03；
- **H3 内生噪声 → 是**：**同批 RTT CV 仅 3.6%**、**TTFT~RTT 皮尔逊 0.00**——
  网络路径平稳而 TTFT 独抖，抖动源在「512KB 上传 + tool_loop」之后的场景/服务端侧。

**推论**：拿 s2 的 CV 去推「网络采样量」会**高估 n**（那不是网络方差）；
`需 n≥47` 只是把内生噪声摊薄的算术，**不解决它本身不可重复**。故网络侧采样量只用
s1/s3 → **n≥15**；s2 另行处置（§2）。

## 2. s2 门处置：采 **单列口径（单独门）**（点 ②）

**二选一取「单列口径」，不选「放宽 MDE」。**

- **做法**：s2_coding_agent 的复测稳定性按其**内生噪声尺度**单列一套门与结论
  （其 CV 门、`需 n≥` 均以场景内生方差计），与 s1/s3 的网络侧 n≥15 **分栏并列**，
  不并入网络侧采样量核算。
- **理由**：
  1. s2 的方差**不是网络方差**（D-372：同批 RTT CV 仅 3.6%、TTFT~RTT 相关 0.00）。
     把它并进网络侧会**污染网络采样量结论**（高估 n），也会让「s2 场景本身抖」这个
     真问题**被稀释隐藏**。单列口径把噪声来源**点名**在场景/服务端侧，读者据以行动的
     对象是对的。
  2. D-372 已回答「先查为何抖再决定 n」——答案是内生，故**加 n 不解决**其不可重复；
     单列口径承认这一点，比「用更大 n 追 5%」更诚实。
  3. 「放宽 MDE」会把 s2 的可辨差异门全局抬高、且模糊「这是另一种噪声源」这一事实；
     单列口径保留 s2 自身噪声尺度的可见性，是更小、更如实的改动。
- **落地形态（建议，具体渲染 待与分析层属主定）**：复测稳定性段对 s2 标
  `SCENARIO_INTRINSIC_JITTER`（承 D-372），其 `需 n≥` 与 CV 门单列，
  并在结论句写明「s2 的采样量不作为加测**网络**样本的理由」。
  注：CV>10% 的格「无论 n 多大都应先查测量装置」本就是既有口径 [grid-design §2 / D-170]，
  单列口径与之相容。

## 4. 轮次协议（点 ④）

### 4.1 丢弃的预热轮如何计入总工时（承 D-366）

PO 已拍板**冷启动协议 = 选项①「每格丢弃一轮预热」**（D-366）。计入工时的方式：

- **每格：正式计入 n 轮之前，先跑 1 轮丢弃的预热（quick）run**（D-366 / runbook §0.6.1③）。
- 预热轮**会正常上报进服务端**，但**拉取时按台账排除**，绝不进语料
  （台账是唯一能认出它的地方，D-366）。
- 预热轮之后**紧接着**跑计入轮，间隔别超过 ~1 分钟（射频回落预热就白跑，runbook §0.6.1③）。
- 此后计入 run 的绝对值**口径 = 「射频已热、App 冷」**（~4% App/TLS 残余仍在，D-358/D-366）。
- **工时记账**：每格采集工作量 = **n_计入 + 1 预热丢弃**。取 n≥15 则每格 **16 run** 的采集
  动作、**15 run 计入**。这与「丢弃一轮预热在蜂窝上值 RTT 约 15%」的收益对应（D-358）——
  用一轮的代价把最大的一项系统性偏差移出结论。

### 4.2 拉丁方轮转设计（承 D-353 缺陷、D-354 已验轮转正确）

**试点缺陷（D-353）**：quick 模式**只有一种场景顺序**，故三个 profile 之间的差异
**无法与位次差分离**（拉丁方未轮转）。

**修法：扩展轮采用取证（forensic）模式作为标准采集模式**——它**已被实测证明轮转正确**
（D-354：`order_index` 0..8、`scenario_order` 带三种轮次、9/9 位次由同一组单元供样），
直接把「单一顺序」缺陷从**全部**数据上移除，而非只在子集补测。

**拉丁方设计（3 个场景位次的循环 3×3 方）**：

| 轮次 | 位次 1 | 位次 2 | 位次 3 |
|---|---|---|---|
| A | s1_chat | s2_coding_agent | s3_multimodal |
| B | s2_coding_agent | s3_multimodal | s1_chat |
| C | s3_multimodal | s1_chat | s2_coding_agent |

每个 profile 在每个位次各出现一次（反平衡）。取证模式经 `scenario_order` / `order_index`
编码此结构（D-354）。

> ⚠ **本段的「建议 4 轮」已被 2026-08-01 的裁定取代为 **5 轮**（D-379）**。理由不在此复述，
> 见增补草案 [`M3_EXPANSION_ROUND_RUNBOOK_ADDENDUM.md`](M3_EXPANSION_ROUND_RUNBOOK_ADDENDUM.md)
> §8「#3 落定」段（一句话版：4 轮低于 `DEFAULT_MIN_SAMPLES=5`，取证格因此恒标 `low_conf`；
> 5 轮同时满足序位与样本充分性两条判据，零代码改动）。**「≥2 轮为最低」仍成立**——
> 那说的是能不能算，不是算得准不准。下面这段的论证过程保留原样，只有那个建议值失效
> （D-301：判据换了，转述它的每一处都要跟着换；这里改的是**指针**，不是重写历史）。

**每格轮数**：**≥2 轮为最低、~~建议 4 轮（每位次 n≥4）~~ → 建议 5 轮（每位次 n≥5，D-379）**——一轮取证每位次只有 n=1，
位次间极差**就是**运行间噪声、判不了（D-354）；要得到序位效应的真结论至少 2 轮、
建议 4 轮（试点报告 §4 建议 3）。多轮同时让**预热/冷启动效应**（按轮次切）与
**序位效应**（按轮内位次切）可分离（D-355/D-356：同一份语料两种切法才分得清预热与位次偏倚）。

**预热与轮转的关系**：按 D-366 既定口径，预热用**单独一轮丢弃的 run**（选项①），
**不是**「丢弃取证第 1 轮」（那是 D-358 未被选中的选项②）。若 PO 希望在取证模式下改用
「丢第 1 轮」口径，需另立决策——本提案照 D-366 现行口径写。

### 4.3 工时总量（结构给出，最终值 待重算）

- **参考基线（grid-design §2，已被 D-345 降格为「扩展轮预算」）**：
  单层级 `8×2×2 = 32 格 × n=11 quick = 352 run ≈ 7.1h 纯测 / 9.9h 含开销 / 1.65 外场日`
  [grid-design §2；单 quick run = 72.4s]。**该表按 n=11、单顺序 quick 计**，需为扩展轮重算。
- **重算的三个增量来源**：
  1. n：11 → 15（网络侧，+36%/格）；
  2. 每格 +1 预热丢弃轮（D-366）；
  3. 采集模式若改取证（6.5 min/run，D-354）而非 quick（72.4s/run），单轮时长量级不同。
- **一个明确的下界（仅供 PO 看量级，非最终值）**：若仍用 quick 模式承载 n≥15 主体，
  每格 = 15 计入 + 1 预热 = 16 run，参考 32 格 → `32×16 = 512 run`；
  `512 × 72.4s ≈ 10.3h 纯测`，按 grid-design 含开销系数（9.9/7.1 ≈ 1.40）≈ **14.4h 含开销
  ≈ 2.4 外场日**（按其 6h/外场日口径）。**此下界不含取证序位块的额外时长。**
- **最终总工时 = 待重算**：取决于 (a) PO 定的点位数/运营商/时段（§3，D1/D2/D4 待 PO），
  (b) 采集模式（取证全量 vs quick 主体+取证子集校验序位），
  (c) 联合满足「n≥15 网络样本」与「每位次 n≥4 序位」所需的每格取证 run 数——
  后者应在**首点位测完当天用 `stability.py --plan` 现场核算**（runbook §3），**不预写**。

> **采集模式选择（留给 PO / 大脑，本文不擅定）**：
> (A) **取证全量**——所有数据都轮转，最干净地消除 D-353 缺陷，代价是每 run 6.5 分钟；
> (B) **quick 主体 + 取证子集**——quick 快速堆够 n≥15 的跨格 MDE 样本，另在代表性子集
> 跑 ≥2（建议 4）轮取证校验序位（序位/预热是协议+设备属性、非强点位属性，可子集校验后
> 全网格套用轮转）。两者的工时与严谨度权衡不同，**建议 PO 拍口径后再由现场核算落定 run 数**。
