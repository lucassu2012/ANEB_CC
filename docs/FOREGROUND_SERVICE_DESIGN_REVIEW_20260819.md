# 前台 Service 迁移 · 设计评审（v2，2026-08-19）

## 0. 一句话结论

**这不是"要不要加个新功能"，而是一处已存在一年的设计-实现分叉**：设计文档 §6 与 §7.2 白纸黑字写着"前台 Service（`dataSync` 类型）承载测试执行"，而代码里**从未有过该 Service**——测量期实际靠 `FLAG_KEEP_SCREEN_ON` 窗口 flag 顶着。**建议：不照文档原样实现，而是修正文档、维持现状 + 补一处窄口子**（理由见 §4）。

## 1. 现状（实测）

| 项 | 实况 |
|---|---|
| 前台 Service | **不存在**。`AndroidManifest.xml` 里唯一 `<service>` 是 `AnebAccessibilityService`（无障碍观察，`BIND_ACCESSIBILITY_SERVICE`），与测量执行无关 |
| 权限 | `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` **已声明**（为文档承诺预留，实际无 Service 使用） |
| 测量期存活机制 | `KeepScreenOnPolicy` → `FLAG_KEEP_SCREEN_ON` **窗口 flag**（T25/D-427）。**仅 autorun 路径持有**；手动路径 `onCreate(false)` 恒不持有 |
| 该机制的实测背书 | **T30/D-437**：15/15 清洁 NR_SA run、135 场景，radio 覆盖率 **135/135**、零 stale，2.6h 连续窗零复现息屏归零（对照 D-424 缺口 2/9） |
| 文档承诺 | 设计文档 §6「测前检查（**前台 Service**、屏幕常亮…）」、§7.2「**前台 Service（`dataSync` 类型）承载测试执行**，防止息屏/切后台被杀」、§风险表「厂商 ROM 省电策略杀测试进程 → 前台 Service + 屏幕常亮」 |

**分叉定性**：文档承诺的是**进程级存活保障**（前台 Service），实现给的是**窗口级屏幕保持**（`FLAG_KEEP_SCREEN_ON`）。两者防的不是同一件事——前者防"进程被杀/切后台"，后者防"息屏导致采集节流"。**现有实测只证明了后者有效，前者的必要性从未被实测检验过。**

## 2. 四问（大脑派单指定必答）

### ① 前台 Service 生命周期与 run 生命周期的绑定点

建议：**`startForeground` 于 run 开始、`stopSelf` 于 run 终态（完成/失败/取消）之后**，绑定点放在 `TestEngine.run` 的 channelFlow 边界，而非 Activity 生命周期——因为 run 可以比 Activity 活得久（这正是迁移的动机）。
**但这引出一个必须先答的问题**：目前 `MainActivity` 用 `lifecycleScope.launch` 驱动 run，Activity 销毁即取消。迁移后 run 归 Service 协程作用域，**"用户离开 App，测量继续"** 成为新行为——**这是测量语义变更**：既有全部语料都是"操作者在场、屏幕常亮"下采集的（D-427 论证的核心前提），新语义会产生**与历史语料不同态的样本**。若实施，必须：跨批次可比性由**新增元数据字段**（如 `foreground_visible`）承载，而非默认合并。

### ② 通知渠道与用户可见文案

- 渠道：`IMPORTANCE_LOW`（无声无震），类型 `dataSync`（与已声明权限一致）。
- 文案红线（承 claim scope 纪律）：**只描述"正在测量到指定节点的应用层体验"，禁止**出现"网络评级/运营商/5G 质量/信号强度评分"等暗示——通知是最容易被截图外传的面，措辞等同对外表述。
- 建议文案：`ANEB 测量进行中 · 场景 2/3`（+ 停止动作）。

### ③ 对既有"测中持续监控"有效性守卫的影响 ★ **最关键**

**实测链条**：`EnvMonitors` 监听 `ACTION_POWER_SAVE_MODE_CHANGED` / `ACTION_DEVICE_IDLE_MODE_CHANGED` → `TestEngine` 收到 `POWER_SAVE`/`DOZE` 事件即 `invalidate("power_state_changed:…")` → **场景判 invalid**（R-12 fail-closed）。

**前台 Service 会改变这条链的触发面**：前台 Service 使进程**豁免部分 Doze 限制**（App Standby / 后台执行限制），于是——
- **好的一面**：真的能防"厂商 ROM 杀进程"（文档 §风险表的原始动机）。
- **危险的一面**：**它可能让原本会触发 invalid 的场景变得"看起来正常"**。Doze 生效时的测量本就该判 invalid（那不是用户正常体验的网络路径）；若前台 Service 让进程绕过部分限制，**系统仍报 `device_idle=true`，而实际调度已被豁免** → 我们会把一个"被豁免的、非典型"的样本判成 invalid（过严），或反之在部分 ROM 上**根本收不到 idle 广播**（过松，静默）。
- **结论**：迁移**必须**同批做一次 `POWER_SAVE`/`DOZE` 事件在前台 Service 下的**真机对照实测**（前台 Service on/off × Doze 触发），确认 invalid 判据仍与用户真实体验对齐。**不做这个对照就迁移＝拿有效性判据换存活率，方向危险。**

### ④ 失败路径：用户划掉通知 / 系统杀

- **`dataSync` 前台 Service 在 Android 14+ 有 6 小时上限**，超时系统 `ANR`/杀。本项目 run ≤ ~12 分钟，**不触顶**，但取证模式若将来延长需重估。
- **用户划掉通知**：`dataSync` 通知**不可被用户直接划除**（前台 Service 通知常驻），但用户可从设置强停。
- **系统杀 / 强停**：进程死 → **既有落库口径是"run 未收尾即无 `RUN_END`"**，分析层据此识别不完整 run。迁移后须保证：**Service `onDestroy`（非正常终态）必须落一条 `invalid` 结果 + 原因码，而不是静默消失**——否则会出现"用户以为测过了、库里查无此 run"的静默截断（违 R-10 精神：缺失要显式，不能沉默）。
- **建议**：`onDestroy` 里 `if (runInFlight) persist(status="killed_foreground_service")`，并让发布门/报告层认这个状态码。

## 3. 与「屏幕常亮」的关系（不可混为一谈）

| 机制 | 防什么 | 现状 | 实测背书 |
|---|---|---|---|
| `FLAG_KEEP_SCREEN_ON`（现有） | 息屏 → EMUI 对 cell info 节流 → radio 样本 stale | ✅ 已实现（autorun 路径） | **T30/D-437：135/135 零 stale** |
| 前台 Service（拟迁移） | 进程被厂商 ROM 杀 / 切后台被冻结 | ❌ 未实现 | **无——该失败模式在本项目从未被实测观察到** |

**关键提问**：**我们观察到过"测量期进程被杀"吗？** 全仓 grep 未见此类事故记录（D-424 的缺口经 T23/T24 三候选根因排查，**结论是息屏节流，不是进程被杀**）。**前台 Service 要解决的问题，在本项目缺少实测证据表明它存在。**

## 4. 建议（供裁）

**主张：不照文档原样实施「前台 Service 承载测试执行」，改为三步走。**

1. **【立即·文档侧】修正设计-实现分叉**：把设计文档 §6/§7.2/§风险表里"前台 Service 承载测试执行"改为**如实描述现状**（`FLAG_KEEP_SCREEN_ON` + autorun 常亮策略，T25/D-427/D-437），并把前台 Service 移入"**备选加固手段（未实施，触发条件见下**）"。**理由：文档承诺一个不存在的机制，比没写更危险——它会让读者（含未来的我们）以为进程存活已有保障。**
2. **【触发条件·而非现在做】** 前台 Service 在**观测到真实失败模式**时才实施，触发条件写死：**任一真机批次出现"run 中途进程死亡（无 `RUN_END` 且非用户取消）≥1 次"**。在此之前实施＝为一个未观测到的问题引入一处**会动摇有效性判据**的改动（§2③）。
3. **【若大脑仍决定实施】** 必须同批交付四件：(a) §2③ 的 Doze × 前台 Service 真机对照实测；(b) §2④ 的 `killed_foreground_service` 状态码 + 发布门认账；(c) §2① 的 `foreground_visible` 元数据字段（保跨批次可比）；(d) 通知文案过 claim scope 审。**缺任一件不上线。**

## 5. 风险登记

- 若**不实施且不修文档** → 分叉继续存在，交付包里"能力边界报告"会引用一个不存在的机制（T61 正在起草，**此项须同步**）。
- 若**照文档实施但不做 §2③ 对照** → 有效性判据可能被静默改变，且**改变方向是"更容易判 valid"**（危险方向：把非典型样本当正常）。
- `dataSync` 6 小时上限对当前 run 时长（≤12min）无影响，但**取证模式若延长需重估**。
