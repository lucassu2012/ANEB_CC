## 1. 背景与目标

项目至今没有一份**现行有效**的需求基线：SYSTEM_DEV_PLAN v1.0 自我声明"不随决策改写"，发布当日即被 D-48 推翻一条，此后靠 PLAN_ALIGNMENT §7.5"失效字样台账"打补丁，每个新会话开工都要先做"计划 vs 现实"考古（PROFILE2/PROFILE4 两份规格的 §0 都在干这个）。本单产出三件套：**需求基线 v2.0 + 决策请求一页清 + 测试执行总计划 v2.0**，让"需求锁定"从口号变成一份可指认、可改写、带版本号的文件。

## 2. 范围与文件边界

- **可写**：`docs/` 下新增文件；`README.md` 加一行指针（指向基线 v2.0）。
- **只读**：`spec/`、`app/`、`scripts/`、`server/`、既有 runbook 正文（M2_CAMPAIGN_RUNBOOK、M3_EXPANSION_ROUND_RUNBOOK_ADDENDUM——整合时只引用不改写）。
- **非目标**：不改代码；不做新审计轮；不替 PO 预写裁定结论（裁项一律留【PO-裁定占位】）。

## 3. 任务分解

### 1.1 需求基线 v2.0（`docs/REQUIREMENTS_BASELINE_v2.0.md`）
内容骨架：
1. 一句话产品定义 + 验收方定义（当前事实：「读者视角终验 = PO 验收本身」，外部读者唯一线索是 v1.0 §6 M2 的「带数据进局点的弹药」——把"最终读者是谁"列为裁项 A）。
2. Profile 1–4 + s4 现状总表，每行五列：规格状态 / 实现状态 / 数据状态 / 已知偏差 / 裁定归宿。数据来源：PLAN_ALIGNMENT、PROFILE2/3/4 三份 spec 的 §0、DELIVERY_PACKAGE_v1_DRAFT。
3. 三大裁项占位：**A** 主交付物排序与验收方（交付包收尾 / 豆包战役 / 外场热力卡三选一排序）；**B** M3 画像口径三选一（放弃 PENDING-BY-CALIBER 字段 / 改 UI-proxy 口径纳入 / 解禁受控采集）——技术论证由 SPEC-4（v4）供稿，本文只挂占位与引用；**C** 外场暂停令解除与否。
4. 已知偏差表：吸收 §7.5 失效字样 4 条 + §7.6 差集 5 条，逐条给归宿（裁项/SPEC-4 承接/作废）。
5. 版本纪律：**本文可改写、版本号递增、每次修订记修订行**——显式区别于 v1.0 的"不随决策改写"制；v1.0 与 PLAN_ALIGNMENT 降级为历史文档（加横幅，不删除）。

**验收**：三大裁项全部有占位与决策所需的事实材料；现状总表每行有出处；README 指针落地。

### 1.2 决策请求一页清（`docs/DECISION_REQUEST_20260829.md`）
把三大裁项 + 诊断报告 §3 的 8 项待人清单合并为一页，沿用 07-31 / 08-20 两版已验证格式（那两版实证 ≤1 天获裁）。每项给"选项 + 各选项后果 + 推荐"，并写明：**"不给"也要显式入册**。

**验收**：格式对齐既有两版；8+3 项全覆盖；可直接交 PO。

### 1.3 测试执行总计划 v2.0（`docs/TEST_MASTER_PLAN_v2.0.md`）
整合四处散落的执行计划为一份，每项三列硬信息：**前置条件（对应一页清编号）/ 预计设备日 / 证据落点**：
- M2/wave-1 外场（M3_EXPANSION_ROUND_RUNBOOK_ADDENDUM；wave-1 = 2 点 ≈0.85 / 3 点 ≈1.28 外场日）；
- 扩展轮完整轮（160 run/0.75 天或 352 run/1.65 天两档）;
- E1–E4 实验（INSTRUMENTATION_SPEC §3.3、tools/e1、tools/e234——装置已 dry-run 就绪，缺真机窗）；
- 豆包战役先行批与 L3 批（DOUBAO_NETPERF_CAMPAIGN_PLAN_20260824，先行批仅卡 E-1）；
- 语音 M7 锚回核（既有预案，待首批真实语音语料）。

**验收**：任一执行会话拿到本文即可判断"今天设备在手能跑什么"，无需再翻 runbook 考古。
