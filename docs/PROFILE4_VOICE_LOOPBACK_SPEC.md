## §1 口径边界（最重要的一节，先于任何 KPI）

### 1.1 本 Profile 不测语音，测的是语音要走的网络承载

判据（实测，非推断）：

```
grep -rE 'AudioRecord|AudioTrack|MediaRecorder|RECORD_AUDIO' app/probe/src/main/**/*.kt
→ 零命中（仅 KDoc 中"模拟 Opus"字样）

grep permission app/probe/src/main/AndroidManifest.xml
→ INTERNET / ACCESS_NETWORK_STATE / CHANGE_NETWORK_STATE / READ_PHONE_STATE
  / ACCESS_FINE_LOCATION / FOREGROUND_SERVICE / FOREGROUND_SERVICE_DATA_SYNC
→ 无 RECORD_AUDIO
```

**App 从未接触麦克风、扬声器、编解码器。** 语音模式发的是按 20ms 节奏、160B 的小包
（`FRAME_INTERVAL_MS=20`、`FRAME_BYTES=160`，≈64kbps Opus 量级），测的是这串包的
往返与到达节奏。App 自己的 UI 文案已经是诚实的（`TestModeProfile.kt:500`：
「模拟 GPT-Live 语音互动的**网络承载**」）——本规格把这句话升格为**契约**。

### 1.2 可以声称 / 不可以声称

| 可以声称 | 不可以声称 |
|---|---|
| 20ms 帧节奏双工流在该网络下的往返、到达抖动、首响、轮次切换、打断响应 | 任何**语音质量**结论（MOS/POLQA/PESQ） |
| 「网络对口到耳时延的贡献」的一个**下界预算** | 「口到耳时延是 X ms」 |
| 应用层端到端观测 | VoLTE / IMS / 承载 QCI / 运营商语音网元的任何指标 |
| 同一设备跨网络/跨时段的**相对**比较 | 跨设备绝对可比（音频链路未测，见 §3 E_anchor） |

**红线继承**：D-24/D-61（不解 TLS、不 MITM 消费级 App）；语音 KPI 只作应用端到端声明。

### 1.3 评分归属

M 组**不进** v0.1 / v0.2 / Token AQS。经 `AqsScorer.scoreVoice` / `scoreVoiceSim` 独立出分
（`facet4`），属**观测/展示口径**。这一点已在实现中成立，本规格只是把它写下来。

Profile 4 有**两代口径**，共用 M1–M3 编号但**观测判据不同**，必须靠 `caliber` 字段区分：

权重（逐字取自 `spec/scoring/weights.yaml`）：

WEIGHTS_VOICE_SIM  (aqs-voice-sim-v0.1)  M1 .20  M2 .15  M3 .10  M4 .15  M5 .10  M6 .10  N1 .10  N2 .10

**上表初版漏了一个已登记的 KPI（对抗复核指出，已补）**：`client_profiles.json` 的

|---|---|---|---|---|
| **FRLOSS** | 帧丢失 | **`NOT_MEASURABLE`** | **`false`** | `null` |

## §3 三段式锚定义

格式：**语义真值**（我们真正想知道的）／**可观测判据**（代码实际测的）／**E_anchor**（两者之差）。
E_anchor 不是误差棒，是**判据与真值之间无法用更多样本消除的结构性距离**。

### M1 口到耳预算（v1，标 DERIVED）

- **语义真值**：说话人发声 → 对端听者耳中听到，墙钟时延。
- **可观测判据**：`RTT_P50 + max(上行帧抖动P95, 下行帧抖动P95) + CODEC_JB_BUDGET_MS(=60.0)`
- **E_anchor**：**三重、结构性、未闭合**——
  1. **音频链路整段不在测量内**。采集缓冲＋编码＋解码＋播放缓冲被一个名义常数 `60.0`
     顶替（KDoc 注为 codec ~20 + playout buffer ~40）。**该常数在本项目从未被实测过**，
     也没有出处引用。它是 M1 中权重最大的单一加项（典型 RTT_P50≈68ms 时占 ~45%）。
  2. **用往返顶替单向**。口到耳是「单向 + 对端处理 + 单向」，判据用 RTT 顶替，
     隐含**上下行对称**假设；CGNAT/非对称接入下该假设无据。
  3. **混分位相加**。P50 与 P95 相加不构成任何一个确定分位数的口到耳。
- **正确读法**：「**网络贡献的口到耳下界预算**」。
  **出处订正**：初版说「锚曲线注释已写明此意」——**不对**，`anchors.yaml` 的 M1 注释
  全文是「口到耳(语音,§4.1 对话自然度红线;v1=预算合成 DERIVED / v2=实测代理 PROXY 同锚)」，
  **无「下界」二字**。逐字写着这句的是 `VoiceRunner.kt:26`、`TestModeProfile.kt:521`
  与 `client_profiles.json:418`（M1 的 `definition`：「（网络贡献的口到耳下界预算，
  非真实音频链路实测）」）。本规格将其固化为**规格级**约束。

### M1′ 口到耳实测代理（v2，标 PROXY）

- **语义真值**：同 M1。
- **可观测判据**：末上行帧发出 → 首 ANED 帧到达，剥服务端驻留，加编解码常数，取 P50。
- **E_anchor**：比 M1 少一重（不再需要上下行对称假设，是真实单向链路的一次实测），
  但**仍含同一个未实测的 `60.0`**，且对端是模拟器而非真实 TTS 引擎。
- 与 M1 **共用同一条锚曲线**（`anchors.yaml: M1`）。这是刻意的（跨口径可比），
  但意味着**锚的标定从未针对 M1′ 单独做过**——列为待办（§5.4）。

### M2 下行帧间抖动 ／ M2′ 下行纯传输抖动

- **语义真值**：听者侧播放缓冲需要吸收的到达节奏不规则度。
- **可观测判据**：M2＝客户端 `arrivalNanos` 帧间隔对名义 20ms 的偏差 P95；
  M2′＝再用帧内嵌 `sched_us` 差分剥离服务端调度误差。
- **E_anchor**：**含客户端调度抖动**（Android 主循环唤醒、GC、线程调度），故为**上界**。
  M2′ 剥掉了服务端侧，**剥不掉客户端侧**——这是 M2′ 仍非"纯网络"的原因。
  **服务端侧的指示性份额已实测**：健康条件下 **40.7%**（见 §4.3 及其披露框——
  **这不是一次守恒的分解**，三列各是不同量的 P95、不可相加）。
  **且该数字属于缓冲研究语料（名义 25 ms），按 §7 不可迁移到语音**，
  此处引用它只为说明「M2′ 剥掉的那部分不是可忽略的小量」，**不作为语音的定量结论**。
- 锚：`M_FRAME_JITTER`（与 M3 共用）。注释已声明「与 N2 数值同但语义独立，单列防口径漂移」。
- **判据在「少而长的冻结」下会饱和（实测，见 §4.3／§5.6，机制已订正）**：
  判据是「帧间隔对名义节奏的偏差的 **P95**」。冻结产生的偏差**并不封顶**——
  实测 `nginx_run1` 单次最大偏差 **4523.9 ms＝名义的 181 倍**——但它们**只占 0.67%**，
  被最近秩 P95 **切在分位点之上**丢弃；剩余 ≥95% 的质量压在「间隔＝0」的平台上，
  于是 `|0−nominal| = nominal`。故 **20.000 ms 不是数学上限，而是「大间隔占比 < 5%」
  时的饱和值**（语音 200 帧下即**冻结 ≤9 次**；第 10 次起 M2 冲高，复核合成验证达 2180 ms）。
  实测证据：`nginx_run1/2` 出现 **4.55 秒的最大帧间静默**，M2 报 **25.000 ms＝该实验的
  名义节奏，一分不多**。（**口径**：4.55 s＝`max(帧间到达间隔)`；本稿初版此处误用了 §4.3 的
  `transport_spread`＝2.2 s，那是 `arrival−pre_flush` 绕中位数的 P95 离散度，
  **不是静默时长**，已订正。）

### M3 上行帧间抖动

- **语义真值**：上行链路对发送节奏的破坏程度。
- **可观测判据**：服务端 `/upload` 的 `chunk_us` 到达序列，帧间隔偏差 P95（服务端权威）。
- **E_anchor**：含 `uploadPaced` 自身的 sleep 精度误差 + 服务端读取粒度，故为**上界**。
  v2 中 M3 用 `SIM_M3_FRAMES=150`（3s 短段）单独跑，权威仍是 `/upload`。

### M4 TTS 首响（v2 独有）

- **语义真值**：用户说完 → 听到对方第一个音。
- **可观测判据**：`speech_commit` → 首 ANED 到达，**剥服务端驻留**，取 P50/P95。
- **E_anchor**：剥掉的驻留是**计划值**（`responseWaitMs=300`），不是真实 TTS 计算耗时。
  真实场景的 M4 = 本判据 + 真实 TTS 首字延迟。**故本判据是真实 M4 的下界。**
- 锚：`M4_TTFB`（0→100, 100ms→85, 250ms→70；显著严于 token TTFT，注释注明「对话自然度」）。

### M5 轮次切换（v2 独有）

- **语义真值**：一方说完到另一方开口的自然停顿。
- **可观测判据**：上轮 `turn_summary` → 下轮首 ANED，剥计划上行时长与驻留，取 P50。
- **E_anchor**：同 M4，剥的是计划值；真实场景需叠加真实端点检测（VAD）判停耗时。
- 锚：`M5_TURN_SWITCH`（0→100, 150→85, 300→70）。

### M6 打断停帧（v2 独有）

- **语义真值**：用户插话 → 对方**真正停止发声**的时延。
- **可观测判据**：`barge_in` 发出 → 末 ANED 到达，取 **max**（非分位数，刻意取最坏）。
- **E_anchor**：**方向明确的低估**。判据测的是「服务端停止发帧且末帧到达」，
  **不含播放缓冲中已缓存音频的排空时间**——真实场景用户在此之后**还会继续听到声音**，
  排空时长约等于 §3-M1 里那个未实测的 playout buffer。**M6 与 M1 的最大未知项是同一个。**
- 锚：`M6_STOP`（0→100, 80→85, 150→70；55 分档对应默认 `expectedStopWithinMs=250`）。

## §4 误差预算骨架与验证实验设计

### 4.1 预算骨架

对任一 M 组 KPI，观测值与语义真值之差可分解为（各项近似独立，平方和）：

```
E_total^2 ~= E_audio_chain^2 + E_clock^2 + E_sched^2 + E_server_sim^2 + E_sampling^2
```

| 项 | 含义 | 当前状态 | 量级 |
|---|---|---|---|
| **E_audio_chain** | 采集/编码/解码/播放缓冲时基 | **完全未测**，被常数 60.0 顶替 | **预期主导**（数十 ms，设备/ROM 相关）——**推断，非测量** |
| E_clock | 端间钟偏 | 已受控：同基客户端单调 us 两两相减免钟偏（KDoc 明写）；`/echo` 四时间戳同步 | 小 |
| E_sched_server | 服务端排定→冲刷的执行抖动 | **已实测**（§4.3） | **P95 中位 0.414 ms**（6 轮健康条件，范围 0.366–0.533） |
| E_sched_client + E_transport | 客户端线程调度 + 传输 | **已实测但两者不可分**（§4.3） | **P95 中位 0.517 ms**（范围 0.115–5.016） |
| E_server_sim | 模拟器 ≠ 真实 TTS 服务 | 结构性：驻留是计划值 | 与真实服务差异未知 |
| E_sampling | 分位数样本量 | 可控：帧数 200/200，M3 150 帧 | 小 |

**结论**：`E_audio_chain` 既是最大项、又是唯一完全未测的项，且**同时影响 M1、M1′、M6**。
它就是 Profile 4 的关键路径。实测已把调度/传输两项从「数 ms」的推断收紧到**亚毫秒**，
这反过来使 `60.0` 这个名义常数在 M1 中的占比更加突出。

### 4.2 验证实验设计（目标：把 60.0 从名义常数变成实测分布）

**实验 V1 · 设备内音频环回自测**

- **目的**：实测本机 `AudioTrack.write()` → `AudioRecord.read()` 的端到端时基，
  得到 `CODEC_JB_BUDGET_MS` 的真实值与分布，替换名义常数。
- **方法**：设备播放已知波形（如周期性脉冲/线性调频），同机录制，互相关求时延峰值；
  重复 N≥30 次取分布。**不需要服务器，不需要第二台设备，不产生任何网络流量。**
- **可测出**：采集缓冲 + 播放缓冲 + 编解码往返的合计时基，及其跨轮稳定性。
- **测不出**（诚实边界）：单向拆分（采集 vs 播放各占多少）；真实 Opus 编解码耗时
  （除非引入编解码器）；对端设备的音频链路。
- **前置**：需 `RECORD_AUDIO` 权限 → **PO 裁决项**（见 §5.3）。

**实验 V2 · 播放缓冲排空时长（闭合 M6 的低估）**

- **目的**：量出 M6 判据与语义真值之差。
- **方法**：在 V1 装置上，发出停止指令后继续录制，测「指令 → 扬声器实际静音」的时延。
- **依赖**：V1 成立即可，同一装置。

**实验 V3 · 上下行对称性核查（闭合 M1 的第 2 重 E_anchor）——本稿初版判断错误，已订正**

初版写「用现有语料即可做」。**实测后证伪，两条独立原因**：

1. **`chunk_us` 从未被归档**。它是 M3 的「服务端权威」，在仓内被点名 **20 处**
   （字节级逐文件计数，排除 `build/`、`.git/`、`__pycache__`）：

   | 处数 | 文件 |
   |---|---|
   | 5 | `app/…/engine/VoiceRunner.kt` |
   | 3 | `app/…/net/AnebClient.kt` |
   | 3 | `app/…/ui/TestModeProfile.kt` |
   | 2 | `spec/profiles/client/client_profiles.json` |
   | 2 | `app/probe/src/main/assets/spec_profiles/client_profiles.json`（运行时镜像） |
   | 1 | `app/…/data/Entities.kt` |
   | 1 | `app/…/scoring/AqsScorer.kt` |
   | 1 | `spec/scoring/weights.yaml` |
   | **1** | **`server/handlers_upload.go`** ← **产出方**：`ChunkUs []int64 \`json:"chunk_us"\`` |
   | 1 | `server/handlers_upload_test.go` |

   > **计数订正（对抗复核指出）**：初版写「15 处」并列了一份逐文件清单，

### 5.6 缺口（本次最重要的发现）：语音族对缓冲病态近乎失明

三条**各自独立实测**的事实，合起来构成一个结构性盲区：

> **本节已按对抗复核结论重写（2026-08-01，本稿第五、六处自我订正，两处都是 high）。**
> 初版的事实 1、事实 2 **机制说错、数字算错**，且错误已扩散进 D-377、任务板与一条已批准裁定，
> 已即时回报。**定性结论仍成立且更锐利**，但适用范围从「无条件」收窄为「少数长冻结」。
> 两处错的根因都是**量法**：读锚时用 `Select-String -Context 0,7`，恰好在第 2 个锚点处截断。

**事实 1（订正）— 盲区来自 P95 弃尾，不是「偏差有天花板」**

初版写「帧间隔塌到 ~0，偏差恰好等于一个完整名义节奏**且不再增长**」。**这是错的**：
冻结产生的偏差**不但增长而且巨大**——实测 `nginx_run1` 的最大单次偏差 **4523.9 ms
＝名义节奏的 181 倍**。真正的机制是：这些巨大偏差**只占 0.67%（4/599）**，
被**最近秩 P95 切在了分位点之上**（rank=570/599，top 29 全部丢弃），
剩下 ≥95% 的质量恰好压在「间隔＝0」那个平台上，于是 `|0−nominal| = nominal`。

**所以 20 ms 不是判据的数学上限，而是「大间隔占比 < 5%」时的饱和值。**
数学上 `|Δ − nominal|` 只在**塌缩侧**（`Δ ≤ nominal`）有界于 `nominal`，
`Δ > nominal` 一侧**无界**。语音 200 下行帧（199 个间隔、丢弃 top 9）下的条件是
**冻结次数 ≤ 9**；复核用语音真参数合成验证：9 次冻结 → M2 = 20.000，
**第 10 次起 M2 = 2180 ms**，上限被击穿 109 倍。

**这个订正让结论更值得担心，不是更轻**：盲区**恰好对准「罕见但致命」那一类**
——一次 4.5 秒的静默足以让对话结束，而它正因为罕见而被 P95 丢弃。
这是分位数统计的经典弃尾失明。

**事实 2（订正）— `M_FRAME_JITTER` 有五个锚点，20 ms 落在插值区不是 clamp 区**

实读三处一致（`AqsScorer.kt:219`、`spec/scoring/anchors.yaml`、`client_profiles.json` 的 target）：

```kotlin
AnchorMap(listOf(0.0 to 100.0, 10.0 to 85.0, 30.0 to 70.0, 80.0 to 55.0, 240.0 to 0.0))
```

初版称「只有两个点、任何 ≥10 ms 一律 85 分」——**错**。clamp 确实存在（`AqsScorer.kt:177`），
但它在 **240 ms**，语音段根本走不到。按分段线性，**M2 = 20 ms 得 77.5 分，不是 85**。
初版还把 85 说成档位「良」，而 `ResultFormat.kt:33-40` 的分档是 **≥85 优 / 70–85 良**
——85 是「优」；**反倒是正确值 77.5 才是「良」**。

**事实 3 — 语音路径没有任何缓冲信号通路（实读）**
`BufferingDetector` 接在 `TestEngine`（token/网络路径）；`VoiceRunner` 对
`buffering|stall` **零命中**；`scoreVoice(...)` / `scoreVoiceSim(...)` 的形参只有
N1/N2/M1–M6，**不含任何 buffering 项**，且内部构造的 `KpiResult` 把
`validity` 硬编码为 `VALID`。

**合起来的后果（算术，非推断；用真实五点锚重算）**

基线（健康流，抖动 ≈0.7 ms）：M2/M3 = **98.95**，M1（68+0.7+60=128.7 ms）= **87.13**。
典型 `RTT_P50 ≈ 68 ms` 取自今日 T1 实测。

**情形 A — 少数长冻结（≤9 次 / 200 帧窗），即 P95 弃尾生效的区间**

| 路径 | 得分 | 与基线之差 | × 权重 | 总分影响 |
|---|---|---|---|---|
| M2 | 20 ms → **77.50**（插值，非 clamp） | 21.45 | 0.20 | **4.29** |
| M3 | 同锚同值 **77.50** | 21.45 | 0.15 | **3.22** |
| M1 | 148 ms → **85.20** | 1.93 | 0.30 | **0.58** |

**一次 4.55 秒的语音流冻结，在 v1 语音 AQS 上总共只移动 8.09 分（满分 100），
M2 得 77.5＝档位「良」。** 且 **M1 硬否决拦不住**：M1 ≤ RTT_P50 + 80，
要触发 `>400 ms` 需 RTT_P50 > 320 ms——**在这一情形下缓冲病态无法触发语音的唯一否决。**

**情形 B — 冻结 ≥10 次，M2 冲出饱和区**

M2 = 2180 ms → 撞 240 ms 的 clamp → **0 分**；M1 = 2308 ms → 70 分且
**`M1 > 400 ms` 否决触发**（封顶 54）。总分影响 **39.77 分**。

**所以盲区不是全域的，而是精确对准「少而长」的冻结**——也就是**罕见但致命**的那一类：
一次 4.5 秒静默足以让对话结束，它却因为罕见而被 P95 丢弃。
**这比初版所述的「无条件失明」更值得担心，因为它专挑最坏的一类失明。**
（初版称总影响 5.9 分、M2 恒 85 分，均已作废，见本节开头订正框。）

**这为什么要紧**：缓冲病态正是 `evidence/phase1/` 整批语料要研究的对象，
也是 `BufferingDetector` 存在的理由。对话式语音恰恰是**最不能忍受**流冻结的业务
（4.55 秒静默 = 对话已经断了），而语音 KPI 族在情形 A 下对它的响应
（8.09 分，档位仍是「良」）与「对话已经断了」这个事实完全不成比例。

**建议（未擅自实施，属评分口径变更，需裁决。本段已随事实 1/2 的订正重排优先级）**

① ~~给 `M_FRAME_JITTER` 补末点~~ **作废**：该锚**本来就有五个点**、clamp 在 240 ms，
不缺末点。真正的丢失发生在**判据层**（P95 把 top 5% 丢了），**锚层改什么都救不回来**
——初版把病因定位在锚上，是事实 2 读错的连带产物。

② 把 `BufferingDetector` 接进语音路径，用**近零到达间隔占比**
（`NEAR_ZERO_ARRIVAL_US=1000µs`，`BufferingDetector.kt:45/167-168`）作为独立 KPI 或否决项。

③ 增设**「最长帧间静默」**KPI（`max` 而非分位数）。

**订正后的推荐：③ 为首选，② 为补充，两者一起做。** 理由随事实 1 的订正而变——
病因既然是 **P95 弃尾**，那么唯一在**构造上**免疫的统计量就是 `max`：它不丢尾，
量纲上也没有饱和平台。② 仍然值得做（它命名了机制＝批化投递、且复用既有判据），
但它是**比例量**，回答「有没有发生」；③ 是**时长量**，回答「有多严重」——
而 §5.6 的整个问题恰恰是**严重度传不到分数上**。

**②③ 已在真实语料上验过分离度（§4.4，非推断）**：健康 6 轮 vs 病态 2 轮——
`nearZeroArrivalRatio` **0.002–0.005 vs 0.993**（约 200 倍，无需调阈值）；
最大帧间静默 **26–77 ms vs 4549 ms**；而 M2 在病态侧报 25.000（饱和平台）。
