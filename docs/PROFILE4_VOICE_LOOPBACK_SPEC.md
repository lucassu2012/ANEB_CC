## §0 盘点结论：本任务的形状与预设不同

大脑派单假定 Profile 4 是**待建**能力（「`/v1/voice/echo` 端点现状」）。逐项盘点后，
结论是**反过来的**：

| 层 | 预设 | 盘点实况 |
|---|---|---|
| App 实现 | 待建 | **已实现两代**：`VoiceRunner.kt`(34.7KB)、`RealtimeSimSession.kt`(11.9KB)、`VoiceTestScreen.kt`(18.4KB) |
| 真机实测 | 无 | **已有**：D-38 记录真机总分 **79.8**，M1–M6 子分全部测出 |
| 评分规格 | 待建 | **已在 spec**：`anchors.yaml` 5 条 M 组锚、`weights.yaml` 两套权重、`vetoes.yaml` M1 硬否决 |
| 单元测试 | 无 | **已有**：`VoiceContinuityPlanTest`、`RealtimeWireTest`、`AqsScorerVoiceTest` |
| **Profile 描述文件** | — | **缺失**（见 §5.1，违反铁律 1） |
| **KPI/锚定义文档** | — | **缺失**——M 组定义只活在 Kotlin KDoc 里（本文补齐） |

## §1 口径边界（最重要的一节，先于任何 KPI）

### 1.1 本 Profile 不测语音，测的是语音要走的网络承载

判据（实测，非推断）：

```
grep -rE 'AudioRecord|AudioTrack|MediaRecorder|RECORD_AUDIO' app/probe/src/main/**/*.kt
→ 零命中（仅 KDoc 中"模拟 Opus"字样）

grep permission app/probe/src/main/AndroidManifest.xml
→ INTERNET / ACCESS_NETWORK_STATE / CHANGE_NETWORK_STATE / READ_PHONE_STATE
  / ACCESS_FINE_LOCATION / FOREGROUND_SERVICE / FOREGROUND_SERVICE_DATA_SYNC
→ 无 RECORD_AUDIO
```

**App 从未接触麦克风、扬声器、编解码器。** 语音模式发的是按 20ms 节奏、160B 的小包
（`FRAME_INTERVAL_MS=20`、`FRAME_BYTES=160`，≈64kbps Opus 量级），测的是这串包的
往返与到达节奏。App 自己的 UI 文案已经是诚实的（`TestModeProfile.kt:500`：
「模拟 GPT-Live 语音互动的**网络承载**」）——本规格把这句话升格为**契约**。

### 1.2 可以声称 / 不可以声称

| 可以声称 | 不可以声称 |
|---|---|
| 20ms 帧节奏双工流在该网络下的往返、到达抖动、首响、轮次切换、打断响应 | 任何**语音质量**结论（MOS/POLQA/PESQ） |
| 「网络对口到耳时延的贡献」的一个**下界预算** | 「口到耳时延是 X ms」 |
| 应用层端到端观测 | VoLTE / IMS / 承载 QCI / 运营商语音网元的任何指标 |
| 同一设备跨网络/跨时段的**相对**比较 | 跨设备绝对可比（音频链路未测，见 §3 E_anchor） |

**红线继承**：D-24/D-61（不解 TLS、不 MITM 消费级 App）；语音 KPI 只作应用端到端声明。

### 1.3 评分归属

M 组**不进** v0.1 / v0.2 / Token AQS。经 `AqsScorer.scoreVoice` / `scoreVoiceSim` 独立出分
（`facet4`），属**观测/展示口径**。这一点已在实现中成立，本规格只是把它写下来。

## §2 KPI 族：两套口径，不是一套

Profile 4 有**两代口径**，共用 M1–M3 编号但**观测判据不同**，必须靠 `caliber` 字段区分：

| 口径 | `caliber` 值 | 依赖 | 权重集 | KPI |
|---|---|---|---|---|
| **v1 paced-proxy** | `null` | `/api/v1/stream` + `/api/v1/upload`（**零服务端部署**） | `WEIGHTS_VOICE` | M1(DERIVED) M2 M3 N1 N2 |
| **v2 server-sim** | `server-sim(aneb-realtime-session-v1)` | `/api/v1/realtime-sim` WebSocket | `WEIGHTS_VOICE_SIM` | M1'(PROXY) M2' M3 M4 M5 M6 N1 N2 |

权重（逐字取自 `spec/scoring/weights.yaml`）：

```
WEIGHTS_VOICE      (aqs-voice-v0.1)      M1 .30  M2 .20  M3 .15  N1 .15  N2 .20
WEIGHTS_VOICE_SIM  (aqs-voice-sim-v0.1)  M1 .20  M2 .15  M3 .10  M4 .15  M5 .10  M6 .10  N1 .10  N2 .10
```

否决（`spec/scoring/vetoes.yaml`）：`M1 > 400.0 ms → total = min(total, 54.0)`，
cap 复用 `T4_VETO_CAP`。仅语音入口求值。

**口径漂移风险点（§2.14 形状）**：M2 在 v1 是「客户端 arrivalNanos 帧间隔 P95」，
在 v2 是「M2′ 剥离服务端 sched_us 后的纯传输抖动 P95」——**同名不同义**。
分析层跨口径汇池前必须按 `caliber` 分组，否则就是 §2.15 说的「汇池不交代成分」。

## §3 三段式锚定义

格式：**语义真值**（我们真正想知道的）／**可观测判据**（代码实际测的）／**E_anchor**（两者之差）。
E_anchor 不是误差棒，是**判据与真值之间无法用更多样本消除的结构性距离**。

### M1 口到耳预算（v1，标 DERIVED）

- **语义真值**：说话人发声 → 对端听者耳中听到，墙钟时延。
- **可观测判据**：`RTT_P50 + max(上行帧抖动P95, 下行帧抖动P95) + CODEC_JB_BUDGET_MS(=60.0)`
- **E_anchor**：**三重、结构性、未闭合**——
  1. **音频链路整段不在测量内**。采集缓冲＋编码＋解码＋播放缓冲被一个名义常数 `60.0`
     顶替（KDoc 注为 codec ~20 + playout buffer ~40）。**该常数在本项目从未被实测过**，
     也没有出处引用。它是 M1 中权重最大的单一加项（典型 RTT_P50≈68ms 时占 ~45%）。
  2. **用往返顶替单向**。口到耳是「单向 + 对端处理 + 单向」，判据用 RTT 顶替，
     隐含**上下行对称**假设；CGNAT/非对称接入下该假设无据。
  3. **混分位相加**。P50 与 P95 相加不构成任何一个确定分位数的口到耳。
- **正确读法**：「**网络贡献的口到耳下界预算**」。锚曲线注释已写明此意，本规格将其固化。

### M1′ 口到耳实测代理（v2，标 PROXY）

- **语义真值**：同 M1。
- **可观测判据**：末上行帧发出 → 首 ANED 帧到达，剥服务端驻留，加编解码常数，取 P50。
- **E_anchor**：比 M1 少一重（不再需要上下行对称假设，是真实单向链路的一次实测），
  但**仍含同一个未实测的 `60.0`**，且对端是模拟器而非真实 TTS 引擎。
- 与 M1 **共用同一条锚曲线**（`anchors.yaml: M1`）。这是刻意的（跨口径可比），
  但意味着**锚的标定从未针对 M1′ 单独做过**——列为待办（§5.4）。

### M2 下行帧间抖动 ／ M2′ 下行纯传输抖动

- **语义真值**：听者侧播放缓冲需要吸收的到达节奏不规则度。
- **可观测判据**：M2＝客户端 `arrivalNanos` 帧间隔对名义 20ms 的偏差 P95；
  M2′＝再用帧内嵌 `sched_us` 差分剥离服务端调度误差。
- **E_anchor**：**含客户端调度抖动**（Android 主循环唤醒、GC、线程调度），故为**上界**。
  M2′ 剥掉了服务端侧，**剥不掉客户端侧**——这是 M2′ 仍非"纯网络"的原因。
  **服务端侧占比已实测**：健康条件下约 **40.7%**（见 §4.3），即 M2′ 相对 M2 削掉约四成。
- 锚：`M_FRAME_JITTER`（与 M3 共用）。注释已声明「与 N2 数值同但语义独立，单列防口径漂移」。
- **判据自带天花板（实测，见 §4.3 与 §5.6）**：判据是「帧间隔对名义节奏的偏差」，
  当整条流被扣住再一次性放出时，所有帧间隔塌到 ~0，偏差**恰好等于一个完整名义节奏**
  而不再增长。故**语音 M2 的数值上限是 20.000 ms**，无论实际停顿多久。
  实测证据：`nginx_run1/2` 出现 **4.55 秒的最大帧间静默**，M2 报 **25.000 ms＝该实验的
  名义节奏 25 ms，一分不多**。（**口径**：4.55 s＝`max(帧间到达间隔)`＝两帧之间最长的一次沉默，
  是「冻结多久」的直接量；本稿初版此处误用了 §4.3 的 `transport_spread`＝2.2 s，
  那是 `arrival−pre_flush` 绕中位数的 P95 离散度，**不是静默时长**，已订正。）

### M3 上行帧间抖动

- **语义真值**：上行链路对发送节奏的破坏程度。
- **可观测判据**：服务端 `/upload` 的 `chunk_us` 到达序列，帧间隔偏差 P95（服务端权威）。
- **E_anchor**：含 `uploadPaced` 自身的 sleep 精度误差 + 服务端读取粒度，故为**上界**。
  v2 中 M3 用 `SIM_M3_FRAMES=150`（3s 短段）单独跑，权威仍是 `/upload`。

### M4 TTS 首响（v2 独有）

- **语义真值**：用户说完 → 听到对方第一个音。
- **可观测判据**：`speech_commit` → 首 ANED 到达，**剥服务端驻留**，取 P50/P95。
- **E_anchor**：剥掉的驻留是**计划值**（`responseWaitMs=300`），不是真实 TTS 计算耗时。
  真实场景的 M4 = 本判据 + 真实 TTS 首字延迟。**故本判据是真实 M4 的下界。**
- 锚：`M4_TTFB`（0→100, 100ms→85, 250ms→70；显著严于 token TTFT，注释注明「对话自然度」）。

### M5 轮次切换（v2 独有）

- **语义真值**：一方说完到另一方开口的自然停顿。
- **可观测判据**：上轮 `turn_summary` → 下轮首 ANED，剥计划上行时长与驻留，取 P50。
- **E_anchor**：同 M4，剥的是计划值；真实场景需叠加真实端点检测（VAD）判停耗时。
- 锚：`M5_TURN_SWITCH`（0→100, 150→85, 300→70）。

### M6 打断停帧（v2 独有）

- **语义真值**：用户插话 → 对方**真正停止发声**的时延。
- **可观测判据**：`barge_in` 发出 → 末 ANED 到达，取 **max**（非分位数，刻意取最坏）。
- **E_anchor**：**方向明确的低估**。判据测的是「服务端停止发帧且末帧到达」，
  **不含播放缓冲中已缓存音频的排空时间**——真实场景用户在此之后**还会继续听到声音**，
  排空时长约等于 §3-M1 里那个未实测的 playout buffer。**M6 与 M1 的最大未知项是同一个。**
- 锚：`M6_STOP`（0→100, 80→85, 150→70；55 分档对应默认 `expectedStopWithinMs=250`）。

## §4 误差预算骨架与验证实验设计

### 4.1 预算骨架

对任一 M 组 KPI，观测值与语义真值之差可分解为（各项近似独立，平方和）：

```
E_total^2 ~= E_audio_chain^2 + E_clock^2 + E_sched^2 + E_server_sim^2 + E_sampling^2
```

| 项 | 含义 | 当前状态 | 量级 |
|---|---|---|---|
| **E_audio_chain** | 采集/编码/解码/播放缓冲时基 | **完全未测**，被常数 60.0 顶替 | **预期主导**（数十 ms，设备/ROM 相关）——**推断，非测量** |
| E_clock | 端间钟偏 | 已受控：同基客户端单调 us 两两相减免钟偏（KDoc 明写）；`/echo` 四时间戳同步 | 小 |
| E_sched_server | 服务端排定→冲刷的执行抖动 | **已实测**（§4.3） | **P95 中位 0.414 ms**（6 轮健康条件，范围 0.366–0.533） |
| E_sched_client + E_transport | 客户端线程调度 + 传输 | **已实测但两者不可分**（§4.3） | **P95 中位 0.517 ms**（范围 0.115–5.016） |
| E_server_sim | 模拟器 ≠ 真实 TTS 服务 | 结构性：驻留是计划值 | 与真实服务差异未知 |
| E_sampling | 分位数样本量 | 可控：帧数 200/200，M3 150 帧 | 小 |

**结论**：`E_audio_chain` 既是最大项、又是唯一完全未测的项，且**同时影响 M1、M1′、M6**。
它就是 Profile 4 的关键路径。实测已把调度/传输两项从「数 ms」的推断收紧到**亚毫秒**，
这反过来使 `60.0` 这个名义常数在 M1 中的占比更加突出。

### 4.2 验证实验设计（目标：把 60.0 从名义常数变成实测分布）

**实验 V1 · 设备内音频环回自测**

- **目的**：实测本机 `AudioTrack.write()` → `AudioRecord.read()` 的端到端时基，
  得到 `CODEC_JB_BUDGET_MS` 的真实值与分布，替换名义常数。
- **方法**：设备播放已知波形（如周期性脉冲/线性调频），同机录制，互相关求时延峰值；
  重复 N≥30 次取分布。**不需要服务器，不需要第二台设备，不产生任何网络流量。**
- **可测出**：采集缓冲 + 播放缓冲 + 编解码往返的合计时基，及其跨轮稳定性。
- **测不出**（诚实边界）：单向拆分（采集 vs 播放各占多少）；真实 Opus 编解码耗时
  （除非引入编解码器）；对端设备的音频链路。
- **前置**：需 `RECORD_AUDIO` 权限 → **PO 裁决项**（见 §5.3）。

**实验 V2 · 播放缓冲排空时长（闭合 M6 的低估）**

- **目的**：量出 M6 判据与语义真值之差。
- **方法**：在 V1 装置上，发出停止指令后继续录制，测「指令 → 扬声器实际静音」的时延。
- **依赖**：V1 成立即可，同一装置。

**实验 V3 · 上下行对称性核查（闭合 M1 的第 2 重 E_anchor）——本稿初版判断错误，已订正**

初版写「用现有语料即可做」。**实测后证伪，两条独立原因**：

1. **`chunk_us` 从未被归档**。它是 M3 的「服务端权威」，在源码与规格中被点名 15 处
   （`VoiceRunner.kt`×4、`AnebClient.kt`×3、`TestModeProfile.kt`×3、`AqsScorer.kt`、
   `Entities.kt`、`client_profiles.json`×2），但对 `evidence/` 全部 **30 份 jsonl** 逐词扫描
   （**分开数、不用交替式 grep**——交替式会让 `sched_us` 的命中冒充 `chunk_us` 的命中）：
   `chunk_us` **0 份**，`sched_us` 8 份，`arrival_us` 8 份。
   **上行权威序列被就地约简成一个 P95 后丢弃，从未落盘**，故 M3 无法从任何语料复核。
2. **即便两侧都在，也算不出单向时延**。`sched_us`(服务端) 与 `arrival_us`(客户端) 是**两个时钟**，
   其差含钟偏；`/echo` 的四时间戳正是为解钟偏而设，但**未逐帧落盘**。
   钟偏在会话内近似恒定，故**差分后的抖动**可算，**绝对单向时延不可算**。

**故 V3 按原设计不可做。** 但同一份语料能回答另一个也未闭合的问题——见 §4.3。

**新增待办 V4 · 归档 `chunk_us`**：若要让 M3 可复核，需把上行到达序列（或其分位数摘要）
写入结果记录。属 P1b 生产端改动，**不在本 lane**，登记待派。

### 4.3 已执行：下行帧抖动三段分解（V3 的可做替代）

**语料**：`evidence/phase1/calibration/*.jsonl`，8 份 × 600 帧，四种代理配置各 2 轮。
**这是全仓唯一同时持有服务端与客户端逐帧时戳的语料**：`seq / sched_us（服务端排定）/
pre_flush_us（服务端冲刷前）/ arrival_us（客户端到达）`。

**口径边界（先说清）**：该语料是**缓冲研究**（`/stream` 过四种代理），**不是语音批**，
名义节奏 **25 ms**（50 tps）而语音是 20 ms。`/stream` 帧路径与语音 v1 的 M2 是同一条，
故**分解方法可迁移**；**绝对数字属于那次实验的网络，不属于任何语音测试**。

| 条件 | n | M2(客户端观测) | 服务端排定抖动 | 服务端执行抖动 | 传输+客户端 |
|---|---|---|---|---|---|
| clean_run1 | 600 | 0.729 | **0.000** | 0.397 | 0.134 |
| clean_run2 | 600 | 0.609 | **0.000** | 0.366 | 0.115 |
| nginx_nobuf_run1 | 600 | 0.924 | **0.000** | 0.399 | 0.379 |
| nginx_nobuf_run2 | 600 | 1.113 | **0.000** | 0.430 | 0.654 |
| proxied_run1 | 600 | 2.614 | **0.000** | 0.533 | 1.811 |
| proxied_run2 | 600 | 8.842 | **0.000** | 0.504 | 5.016 |
| ~~nginx_run1~~ | 600 | **25.000** | 0.000 | 0.390 | **2225** |
| ~~nginx_run2~~ | 600 | **25.000** | 0.000 | 0.389 | **2225** |

全部为 P95，单位 ms。**汇池口径（§2.15）**：下方统计**只含 6 轮健康条件**，
**排除 2 轮**（`nginx_run1/2`，缓冲饱和，见下）；排除判据由数据导出而非写死清单——
「M2 恰等于名义节奏」即饱和签名。

- M2 客户端观测 P95：中位 **1.018**（0.609–8.842）
- 服务端执行**变异** P95：中位 **0.414**（0.366–0.533）
- 传输+客户端 P95：中位 **0.517**（0.115–5.016）
- **服务端占 M2 约 40.7%**——这就是 M2′ 相对 M2 削掉的那部分，**首次被量出**。

**量法上的一处自我订正**：初版把「服务端执行滞后的**绝对** P95」（0.78–1.06 ms）
直接与 M2 比，得出「45.4%」。**这是错的**：M2 是帧间**差分**量，恒定滞后对它贡献为零，
两者不可相减。改用滞后的**变异**（绕中位数的 P95）后才同量纲，结果 40.7%。
脚本中已把两列并列打印并注明不可比，防止下一个人再踩。

**两条诚实的肯定**：
1. `服务端排定抖动 = 0.000`，八轮全部——服务端的**意图**是完美等距，
   与 `VoiceRunner` KDoc 所称「`/stream` 实测输出精确帧节奏」一致。**该断言被独立复核通过。**
2. 饱和签名：`nginx_run1/2` 的**最大帧间静默达 4549 ms**，而 M2 报 **25.000 ms＝名义节奏，一分不多**。
   **这不是巧合，是判据的数学天花板**（帧间隔塌到 0 → 偏差＝一个完整节奏）。后果见 §5.6。
   （上表 `传输+客户端` 列的 2225 是 `arrival−pre_flush` 的**离散度**，与「静默多久」是两个量，
   初版曾把前者当后者叙述，已订正。）

### 4.4 两个候选判据在同一份语料上的分离度（为 §5.6 建议提供依据）

同一 8 份语料，把 M2 与两个候选量并排（`NEAR_ZERO_ARRIVAL_US = 1000 µs`，
取自 `BufferingDetector.kt:45`；`nearZeroArrivalRatio` 的算式为
`count(帧间隔 ∈ [0, 1000µs)) / n`，见 `BufferingDetector.kt:167-168`）：

| 条件 | M2 P95 (ms) | nearZeroArrivalRatio | 最大帧间静默 (ms) |
|---|---|---|---|
| clean_run1 / run2 | 0.729 / 0.609 | 0.002 / 0.002 | 26.6 / 25.9 |
| nginx_nobuf_run1 / run2 | 0.924 / 1.113 | 0.002 / 0.002 | 28.8 / 30.6 |
| proxied_run1 / run2 | 2.614 / 8.842 | 0.003 / 0.005 | 58.6 / 76.5 |
| **nginx_run1 / run2** | **25.000 / 25.000** | **0.993 / 0.993** | **4548.9 / 4549.3** |

**读法**：M2 对健康与病态给出 0.6–8.8 vs 25.0（且 25.0 是**撞顶**，不是「差 3 倍」）；
`nearZeroArrivalRatio` 给出 0.002–0.005 vs 0.993，**分离约 200 倍且无需调阈值**；
最大帧间静默给出 26–77 ms vs 4549 ms，**量纲上没有天花板**。
两个候选量都看得见 M2 看不见的东西——这是 §5.6 建议②与③的实测依据，**不是推断**。

### 5.6 缺口（本次最重要的发现）：语音族对缓冲病态近乎失明

三条**各自独立实测**的事实，合起来构成一个结构性盲区：

**事实 1 — M2/M3 判据有数学天花板（§4.3 实测）**
判据是「帧间隔对名义节奏的偏差 P95」。流被扣住再一次性放出时，帧间隔塌到 ~0，
偏差**恰好等于一个完整名义节奏**且不再增长。语音名义 20 ms ⇒ **M2/M3 上限 20.000 ms**。
实测：最大帧间静默 **4549 ms** 的两轮，M2 报 25.000＝该实验名义节奏，一分不多。

**事实 2 — 锚在末点 clamp，不外推（`AqsScorer.kt:176-177` 实读）**
```kotlin
if (value >= anchors.last().first) return anchors.last().second
```
`M_FRAME_JITTER` 只有两个点 `[0→100]`、`[10→85]`。**任何 ≥10 ms 的 M2 一律得 85 分。**
语音 M2 的上限 20 ms ≥ 10 ⇒ **无论流被扣多久，M2 恒得 85 分（档位「良」）。**

**事实 3 — 语音路径没有任何缓冲信号通路（实读）**
`BufferingDetector` 接在 `TestEngine`（token/网络路径）；`VoiceRunner` 对
`buffering|stall` **零命中**；`scoreVoice(...)` / `scoreVoiceSim(...)` 的形参只有
N1/N2/M1–M6，**不含任何 buffering 项**，且内部构造的 `KpiResult` 把
`validity` 硬编码为 `VALID`。

**合起来的后果（算术，非推断）**

| 路径 | 最坏情形得分 | 与完美流之差 | × 权重 | 总分影响 |
|---|---|---|---|---|
| M2 | 85（clamp） | 15 | 0.20 | **3.00** |
| M3 | 85（clamp，同锚） | 15 | 0.15 | **2.25** |
| M1 | RTT_P50+20+60 ⇒ 典型 148 ms → ~85 | ~2 | 0.30 | ~0.60 |

**一次 4.55 秒的语音流冻结，在 v1 语音 AQS 上总共只移动约 5.9 分（满分 100）。**
且 **M1 硬否决也拦不住**：M1 ≤ RTT_P50 + 80，要触发 `>400 ms` 需 RTT_P50 > 320 ms——
**缓冲病态本身永远无法触发语音的唯一否决。**

**这为什么要紧**：缓冲病态正是 `evidence/phase1/` 整批语料要研究的对象，
也是 `BufferingDetector` 存在的理由。对话式语音恰恰是**最不能忍受**流冻结的业务
（4.55 秒静默 = 对话已经断了），而语音 KPI 族对它的响应比对一次几毫秒的抖动还平缓。

**建议（未擅自实施，属评分口径变更，需裁决）**：三选一或组合——
① 给 `M_FRAME_JITTER` 补末点（如 `[20→40]`），让 clamp 发生在有意义的分值上；
② 把 `BufferingDetector` 接进语音路径，用**近零到达间隔占比**
（`NEAR_ZERO_ARRIVAL_US=1000µs`，`BufferingDetector.kt:45/167-168`）作为独立 KPI 或否决项；
③ 增设「最长帧间静默」KPI（max 而非 P95，量纲上无天花板）。

**②③ 已在真实语料上验过分离度（§4.4，非推断）**：健康 6 轮 vs 病态 2 轮——
`nearZeroArrivalRatio` **0.002–0.005 vs 0.993**（约 200 倍，无需调阈值）；
最大帧间静默 **26–77 ms vs 4549 ms**；而 M2 在病态侧**撞顶** 25.000。
① 未验：补末点能改善分值曲线，但**改不掉 M2 撞顶这件事**——20 ms 之后的信息在判据里
已经丢了，补锚只是把「撞顶」映射到一个更低的分，仍分不出 4.5 秒和 20 秒。

**推荐 ②**：判据已存在、无需新增测量、只需接线，且分离度最干净。
**②③ 不互斥**：②给的是「有没有发生」的比例量、③给的是「有多严重」的时长量，
若只取一个，读者拿不到严重度。
