## 2. 出口 IP 协变量位：预埋 CGNAT 会话级分配假说的应对（承 D-437/D-439）

D-437/D-439 用真机数据发现：四次独立 NR_SA 观测出现四个不同出口 IP（各自组内
稳定、组间必换），"制式与出口完全共线"这个此前的假设已经不成立；出口更像是
**逐批（甚至逐会话）的协变量**，不是可以忽略或假定恒定的东西。扩展轮网格设计
必须把这个应对预埋进去，而不是等外场真正跑出双出口再现场发明处理方式。

**已有的接线，直接复用，不新造**：

- **机器字段**：`network_snapshot.server_observed_addr`（契约必填，D-376/T9 起
  `radio_rollup.egress_ip()` 已读，D-431 起发布门也检查它是否读得出来）——
  **不需要额外采集动作**，逐 run 逐场景自动落盘。
- **告警机制**：`radio_rollup.render_markdown()` 的 `MIXED_EGRESS:N` 标记
  （D-376）——**同一格（point_id×carrier×time_band）若跨批出现多个出口 IP，
  这个标记会自动触发**，不需要网格配置层面加任何新开关。
- **发布门**：`publish_check.py` 的"出口 IP"检查（D-431）——批内出口读不出来
  时 WARN，读得出来但同格跨批出现多个值时，`MIXED_EGRESS` 由 `radio_rollup`
  的渲染面承担告警，两者分工不重叠。

**网格配置层面要写清楚的，是"怎么读这个信号"，不是"怎么采它"**——采集侧
零改动。收工清单（ADDENDUM §5）建议追加一句解读纪律（供 §6 并入基座 runbook
时一并带上）：

> **同格多批若出口不同，按 `MIXED_EGRESS` 纪律分段呈现，不池化平均**：一个格
> 若因为多次外场日测量而累计了两个不同的出口 IP，报告不得把这些数据当成"同
> 一路径的重复测量"合并成一个中位数——按出口分段呈现（同 `MIXED_SERVING_CELL`
> 的既有处理方式），并在归因段如实交代"该格测量横跨了至少两次 CGNAT 会话"。
> 这不是新判据，是把既有的 `MIXED_EGRESS` 标记接进"分段呈现"这条动作里
> （目前它只是一个渲染标记，没有绑定"因此要怎么处理"的操作指令——这条空白
> 由本段填上）。

**如实标注边界**：本节只是"预埋应对位"，不是"已验证的处理流程"——`MIXED_EGRESS`
触发后具体怎么分段呈现（按时间切、按出口切、两种都给）本节没有设计细节，留给
真正遇到这个情况的那份报告去决定，那时候会有真实数据可依据，现在设计容易
拍脑袋出一个不合用的形状。

## 3. 工时重算：新基数 = 8 点位×2 运营商×2 忙闲 = 32 格，n≥15 + 取证子集每格 5 轮

**不沿用旧基数**（D-312 教训——D-312 本身就是"数字换了、转述它的地方没跟着换"
的实例，这里再核一遍，确认这次没有重蹈）：

- ~~D-312 时代的 `n=11`~~ → 现行 `n≥15`（试点报告 §4 建议 1 / D-372，依 s1/s3
  网络侧 CV 5.5%/5.9% 定）。
- ~~三层级 96 格~~ → 单层级 32 格（D-48 三层级取消，8 点位×2 运营商×2 忙闲）。
- **发现一处内部不一致，此处订正**：ADDENDUM §4.3 写"取证子集 8 格 ⇒ 约
  +52 min"，隐含"每格只加 1 条 run"；但同一文件另一处（D-388 旁证）明确算术是
  "8 格 × 5 = 40 run"（每格 **5** 条 run，D-379 裁定）。**+52min 是 D-379（每格
  5 轮）落地前的残留数字，没有跟着改**——本条按 D-379 的 5 轮/格重算，不采用
  +52min 这条过期数字（如实记录这处发现，不代 ADDENDUM 改那一行，属主另处理）。

**quick 主体**（32 格 × 16 run/格 = 15 计入 + 1 预热丢弃）：

```
512 run × 72.4s/run = 37,068.8s ≈ 10.297 小时（纯测量）
```

**取证子集**（8 格代表性子集 × 5 轮/格，D-379）：

```
40 run × 6.5min/run = 260min ≈ 4.333 小时（纯测量）
```

**合计**：

```
纯测量 10.297 + 4.333 = 14.630 小时
+40% 现场开销 → 20.482 小时
÷ 6 小时/外场日 → 3.414 外场日
```

**与既有的"quick-only 下界 2.4 外场日"对照**：ADDENDUM §4.3 已给出的 2.4 天
是**quick 单独、不含取证子集**的下界（其原文自己标注"此下界不含取证序位块的
额外时长"）——本条 3.414 天补上了这部分，两个数字不矛盾，是同一账本的两个
不同范围。

**若真实点位数不是 8**（PO 可能只给 6 或 7 个）：quick 部分按点位数线性缩放
（`点位数 × 2 运营商 × 2 忙闲 × 16 run × 72.4s`）；取证子集**不建议线性缩放**
——8 格取证子集的设计意图是"每个点位至少一个代表格"，点位数变少时取证子集
格数应等于新点位数（每点位仍留 1 个代表格），不要机械按比例缩到 6 或 7 格
以下的小数——代表性覆盖的完整性比省下几十分钟更重要。
