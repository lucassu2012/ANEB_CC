## §0 一句话

**加一个 `M7 最长帧间静默`（`max`，不是分位数）承担「有多严重」，
把 `nearZeroArrivalRatio` 降为不计分的标注承担「为什么」，
权重从被证明失明的 M2/M3 身上各匀出来，评分版本号跟着跳一级。**

## §1 为什么是 `max` —— 病因决定药方

D-390 订正后的病因是**分位数弃尾**，不是锚曲线不够低：

- 冻结产生的偏差**巨大且真实存在**（`nginx_run1` 单次最大 **4523.9 ms ＝名义的 181 倍**），
- 但它们**只占 0.67%（4/599）**，被最近秩 P95 **切在分位点之上丢弃**，
- 于是 M2 报 25.000（＝名义节奏的饱和平台），**读者拿不到「4.5 秒」这个数**。

**凡以分位数为判据的量，都会在「罕见但致命」这一类上失明**——而对话式语音的
致命形态恰恰就是罕见的长静默。`max` 是唯一**在构造上**免疫的统计量：它不丢尾、
没有饱和平台、量纲直接可解释（「最长一次沉默有多久」）。

**这不是把 M2/M3 换掉**：M2/M3 在未饱和区确实随病情变化
（`proxied_run2` M2＝8.842 ms，其最大静默 76.5 ms，见规格 §4.4），
它们回答「常态抖动有多大」，仍然该留。M7 回答的是另一个问题。

## §2 第一问：独立 KPI 还是否决项？

### 2.1 M7 —— **计分 KPI，不设否决**

| 项 | 提案 |
|---|---|
| KPI id | `M7` |
| 名称 | 最长帧间静默 |
| 字段名 | `m7_max_frame_gap_ms` |
| 判据 | 下行帧到达序列的 `max(相邻帧到达间隔)`，ms |
| 统计量 | **`max`**（刻意不是分位数，理由见 §1） |
| 方向 | `lower_better` |
| 可度量性 | `MEASURABLE`（客户端 `arrivalNanos` 已有，无需新增采集） |
| 计分 | **是** |
| 否决 | **否**（理由见下） |

**为什么不设否决**：M1 已有一条硬否决（`>400 ms → cap 54`）。再加一条会出现
**同一次冻结触发两条否决**的叠加（`vetoes.yaml` 注释明写「多否决可叠加取更严 cap」），
而 M1 的口到耳预算里本来就含帧抖动项——**同一物理事件被罚两次**。
锚曲线在 1000 ms 处已给到 0 分，惩罚已经足够陡。

### 2.2 ② `nearZeroArrivalRatio` —— **标注，不计分、不否决**

| 项 | 提案 |
|---|---|
| 字段名 | `voice_near_zero_arrival_ratio` |
| 来源 | 复用 `BufferingDetector` 的 `NEAR_ZERO_ARRIVAL_US = 1000 µs`（`BufferingDetector.kt:45`），算式 `count(间隔 ∈ [0,1000µs)) / n`（`:167-168`） |
| 计分 | **否** |
| 呈现 | 结果页 + CSV 列 + 一条渲染标记（建议 `VOICE_BATCHED_DELIVERY:<ratio>`，阈值待定，见 §5） |

**为什么不计分**：
1. **会与 M7 双计**——同一次批化投递既抬高 M7 又抬高该比例；
2. **比例量难锚**：0.002 vs 0.993 分得开，但 0.30 该给几分**没有依据**，
   而给一条无依据的锚正是 D-390 那类错误的温床；
3. **它的价值是「为什么」不是「多严重」**：M7 说「最长静默 4.5 秒」，
   它说「因为帧是批着到的」——这是**归因**，归因不该进分数。

实测分离度（规格 §4.4）：健康 6 轮 **0.002–0.005** vs 病态 2 轮 **0.993**，约 200 倍。

## §3 第二问：锚怎么定

**原则：不发明新数字。** 五个锚点尽量取自仓内已有的、有出处的门限：

| 静默时长 (ms) | 分 | 这个数字从哪来 |
|---|---|---|
| 0 | 100 | 完美 |
| **60** | 85 | `VoiceRunner.CODEC_JB_BUDGET_MS = 60.0` —— **名义抖动缓冲深度**；低于它，缓冲吸收得掉，听者无感 |
| **150** | 70 | `PROFILE_FRAMEWORK §4.1`「口到耳 **<150**/300/400 ms（对话自然度红线）」第一档 |
| **400** | 40 | 同上第三档，亦即 `vetoes.yaml` 的 `M1_VETO_THRESHOLD_MS = 400.0` —— 已被本仓认定为「一票否决」的量级 |
| **1000** | 0 | 1 秒静默＝对话已断（**唯一一个没有仓内出处的点**，见 §5 待裁 A） |

```yaml
  M7_MAX_GAP:
    # 最长帧间静默(D-390 §5.6 订正后的首选判据):max 而非分位数,理由=P95 弃尾
    # 门限出处: 60=CODEC_JB_BUDGET_MS; 150/400=PROFILE_FRAMEWORK §4.1 对话自然度红线
    # 1000=待裁(提案 §5-A)
    unit: ms
    direction: lower_better
    points:
      - [0.0, 100.0]
      - [60.0, 85.0]
      - [150.0, 70.0]
      - [400.0, 40.0]
      - [1000.0, 0.0]
```

**代入实测语料自检**（规格 §4.4 的 8 轮）：

| 条件 | 最长静默 | M7 得分 | 对照：M2 |
|---|---|---|---|
| clean_run1 / run2 | 26.6 / 25.9 ms | **93.35 / 93.53** | 0.729 / 0.609 |
| nginx_nobuf_run1 / run2 | 28.8 / 30.6 ms | **92.80 / 92.35** | 0.924 / 1.113 |
| proxied_run1 / run2 | 58.6 / 76.5 ms | **85.35 / 82.25** | 2.614 / 8.842 |
| **nginx_run1 / run2** | **4548.9 / 4549.3 ms** | **0.00 / 0.00** | **25.000 / 25.000（饱和）** |

**这正是 M2 做不到的分辨**：同一批语料上 M2 给病态 25.000（撞饱和平台，且它在锚上
只落到 77.5），M7 给 **0.00**——而健康四轮 M7 仍在 92.35–93.53，**没有误伤**。

> **本表的分值是用提案锚曲线跑脚本算的，不是手算。** 初稿曾手算成
> 「健康 93.5–96.0 / proxied_run2 82.5」，**两处都错**（实为 92.35–93.53 / 82.25）。
> 这正是 D-390 那条教训的当场复发与当场拦截：**凡要印出去的数字，让机器算一遍。**

### 权重：从被证明失明的那两项身上匀

| 权重集 | 现行 | 提案 | 变化 |
|---|---|---|---|
| `WEIGHTS_VOICE` | M1 .30 / M2 .20 / M3 .15 / N1 .15 / N2 .20 | M1 .30 / M2 **.15** / M3 **.10** / **M7 .10** / N1 .15 / N2 .20 | M2−.05、M3−.05、M7+.10；**Σ=1.00** |
| `WEIGHTS_VOICE_SIM` | M1 .20 / M2 .15 / M3 .10 / M4 .15 / M5 .10 / M6 .10 / N1 .10 / N2 .10 | M1 .20 / M2 **.12** / M3 **.08** / **M7 .05** / M4 .15 / M5 .10 / M6 .10 / N1 .10 / N2 .10 | M2−.03、M3−.02、M7+.05；**Σ=1.00** |

**为什么从 M2/M3 匀而不是整体归一化**：M7 覆盖的正是 M2/M3 漏掉的那部分语义，
从它们身上匀，等于**把已经付过的权重重新分配到能看见的量上**，
不改变「帧到达行为」这一族在总分里的总份额（v1 仍是 0.35，v2 仍是 0.25）。
整体归一化会连带稀释 N1/N2/M1，那是**无关的改动**。

## §4 第三问：历史 79.8 分怎么标 caliber

**问题**：D-38 记录的真机 79.8 分是用 `aqs-voice-sim-v0.1` 算的。加了 M7、动了权重之后，
**新旧分数不可比**——而 79.8 已被写进决策日志、被当作「语音已跑通」的证据反复引用。

**盘点先行的结论：这一问比预想的小得多，而且 App 侧已经是对的。** 实读四处：

| 事实 | 出处 |
|---|---|
| `scoreVoice`/`scoreVoiceSim` **只在 UI 与测试里被调用** | 全 `app/` 扫描：`VoiceTestScreen.kt:317/328` + `AqsScorerVoiceTest`，**无第三个生产调用方** |
| 出分的输入是**实时样本**，不是库行 | `VoiceConclusionCard(sample: VoiceRunner.Sample)`（`VoiceTestScreen.kt:309`） |
| **分数从不落库**：`VoiceResultEntity` 只存原始 KPI（`caliber`/`rttMs`/`mouthEarProxyMs`/… 共 18 个字段），**无分数、无评分版本号** | `Entities.kt:416` 起全字段 |
| **历史页刻意不重算分** | `VoiceTestScreen.kt:271-273` 逐字：「只展示 `VoiceResultEntity` 落库实测值，**不重算分**」；`HistoryScreen.kt:209-213` 的语音行同样只显口到耳值 |

**于是本来最怕的那个风险根本不存在**：本可能出现「打开一条旧记录、被当前代码按新版本重算、
分数悄悄变了而无人知」——**App 从不这么做**。这是 D-42 那一轮就定下的诚实设计。

**提案（两步，都只动文字）**：

1. **版本号跳级，不复用**：`aqs-voice-v0.1 → v0.2`、`aqs-voice-sim-v0.1 → sim-v0.2`。
   `weights.yaml` 的 `version_id` 是已有机制（`SpecScoringParityTest` 已对拍），沿用即可。
2. **引用侧加一句口径横幅**：**79.8 这个数今天只活在散文里**（D-38 决策条目，
   当时是从屏幕上读下来记入的）。凡引用它的地方（D-38、`PLAN_ALIGNMENT`、任何报告）
   补注 **「`aqs-voice-sim-v0.1`，M7 引入前口径，不与 v0.2 后的分数比较」**。
   这是 D-301 的纪律：**判据换了，转述它的每一处跟着换**。

**明确不做，且理由要说准**：不追溯重算历史 run。
初稿写的理由是「原始数据未落盘所以物理上做不到」——**这个理由是错的**：
多数 KPI（M1′/M2′/M3/M4/M5/M6/N1/N2）**都在库里**，重算它们做得到。
**真正做不到的只有 M7**：它的输入是逐帧到达序列的 `max`，而库里只存了 P95 抖动，
**原始序列从未落盘**（与规格 §4.2 的 `chunk_us` 同一形状）。
所以历史行**永远拿不到一个完整的 v0.2 分**，任何为它们补算的分都是缺 M7 的残分——
**这才是不重算的理由。**

## §7 本提案的边界（R-10）

- **未实施任何改动**，未碰生产码、未碰 spec、未碰设备。
- §3 的自检分值（93.5–96.0 / 85.4 / 82.5 / 0.0）是我**按提案锚曲线对规格 §4.4 已有实测值代入算出的**，
  不是新的测量；语料仍是缓冲研究批（名义 25 ms ≠ 语音 20 ms），**绝对分值不可外推到语音**，
  可迁移的只有**分辨力**这一结论。
- **本提案没有真实语音语料可验**：全仓零语音记录（规格 §2 已证），
  故 M7 的锚在**真实语音分布上是否合适，今天无法判定**——这是它与 D-390 那类错误
  最接近的地方，特此写明。**第一批真实语音数据出来后必须回头核对锚。**
- 权重表的 **Σ=1.00 已由脚本核过**（两表均为 1.00），但实施时仍应由对拍测试重算确认
  ——手算与脚本算的差别，本文 §3 那条订正框已经演示过一次了。
- **本提案自身出现过一次手算错误并被当场拦截**（§3 订正框）。它不是花絮：
  D-390 的两条 high 全部源于「看起来完整的中间结果没有被独立复算」，
  而本文写作过程中同一形状在一小时内复发。**结论：凡要印出去的数字，让机器算一遍。**
