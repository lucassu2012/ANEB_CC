## 1. 主命题

### P1（主）生产解析器数出的 token 数 == 服务端 `usage.completion_tokens`

`OpenAiSseAdapter` 的计数规则写死在它自己的 docstring 里：**`choices[0].delta.content` 为非空字符串才记 token 到达**（首帧 role 帧的 `content:""` 与结束帧空 delta 不算），`data: [DONE]` 不算 token 不算错误。服务端尾帧给出 `usage.completion_tokens`。**两者应当相等。**

⚠ **为什么这条只能在真端点上做、在 mock 上做没有意义**：mock 的 `usage` 与它的 token 流**出自同一段代码**，一致是**构造保证**的——那正是本仓「**同一缺陷喂出两个假独立方法**」。真端点的 usage 来自独立实现，**才算互证**。

⚠ **不等时不预设哪边对**：至少两种解释——①我们的计数规则漏计/多计（量法缺陷）；②GLM 的 `completion_tokens` 口径与 delta 边界不同（分词口径差）。**报告须两种并列**；单次不等不足以定性。

### P2（主）真端点的 wire 形态不会让生产解析器**静默**产出错值

判据全部取自解析器自己的输出字段，不另立：
- `parseErrors == 0`；
- `protocolError == null`；
- **原始 SSE 字节全量留存**，任何判读事后可重解。

⚠ 危险的不是解析失败——那会计数。危险的是**解析成功而结果是错的**。故本条真正的判据是 P1；P2 只排除「连解析都没成」这一层。

### P3（次，**只描述不判定**）真端点的 TTFT 与瞬时 TPS 形态

模拟端点 `server/tokengen.go` 写着六条显式假设：TTFT 注入驻留／非平稳 `RateSchedule`（前快后慢）／SSE 帧合并 `TokensPerFrame`／每模型字节直方图／流内 think 停顿／burst。真端点能告诉我们**哪几条像、哪几条不像**。

⚠ 本批 n 小，**只出描述与区间，不出「模型该改成什么」的结论**。

## 1b. 负载选型

- **固定 prompt**，逐字写死在采集脚本里并随证据包留存——不同 prompt 的输出长度与分词分布不可比。
- **输出要足够长**才看得出 rate 形态：目标 `completion_tokens ≥ 200`，用 `max_tokens` 兜住上界。
- ⚠ **`temperature` 一律不发（F-5 订正，比 v4 提出时更强）**：生产探针
  `requestBodyJson` **刻意不发它**，源码注释写明各 OpenAI 兼容服务商约束不一
  （Moonshot 仅接受 `temperature=1`，显式传 0 会 **400**）。我若为「可比」加上它，
  抓到的 wire 就**不是生产会拿到的那份**——本批的立足点当场塌掉。
  ⇒ **本批放弃「输出可复现」这个便利**，换「与生产同构」这个前提。
  **下游动作写死**：两笔同参输出不同 ⇒ **如实记为观察，不作异常、不去追**
  （否则下一个人会去追一个不存在的 bug）。

- **第三方内容入仓的显式判断（F-4）**：原始 SSE 含模型输出正文，而本仓刚立
  「第三方内容不入仓」。**本批判定可入仓**，理由三条：①prompt 由我们写死、
  内容是我们自己请求的产物；②它是**证据本身**——P1 的分流要求原始字节可重解，
  删正文等于删掉复核这条分流的能力；③不含任何第三方私有材料或用户数据。
  ⚠ **写出来才算判断过**：没写＝没判断，而不是「显然没问题」。

## 2. 逐条展开（判据与**判过没过**的规则）

> F-2：本节此前整节缺失。**症状不是编号**：P1 只写「两者应当相等」，

### P1 判据（**本批唯一有对照量的一条**）

| 结果 | 判词 |
|---|---|
| **全部有效笔 token 数 == usage** | **P1 成立**（限定：本模型、本 prompt、本参数、n 笔） |
| **有 ≥1 笔不等** | **P1 不成立**，且**不判定谁错**——进入下面的分流 |
| 有效笔 < 3 | **NOT_EXECUTED**（样本不足以支撑任何一侧） |

**不等时的分流（不预设哪边对，两解并列写进报告）**：
- **差值恒定/成比例** ⇒ 偏**分词口径差**（GLM 的 completion_tokens 与 delta 边界不同）；
- **差值随笔跳动、或只在个别笔出现** ⇒ 偏**量法缺陷**（漏计/多计某类 delta）；
- 两者都不像 ⇒ **如实记「不可归因」**，不硬选。
⚠ **任一分流都要求原始字节留存可重解**——否则事后连复核这条分流的机会都没有。

### P2 判据
三条可机检，全绿才算成立：`parseErrors == 0`、`protocolError == null`、原始字节全量留存。
任一不满足 ⇒ P2 不成立，且**P1 的结果一并降级为不可采信**（解析都没走完，数出来的量无意义）。

### P3 判据
**只描述不判定**：给出 TTFT 与瞬时 TPS 的观察值与区间，逐条对照 `tokengen.go` 的六条假设
标注「像 / 不像 / 本批看不出」。**不出「模型该改成什么」的结论。**

### P4（顺带产出，**非本批立项理由**）生产探针不请求 usage

实核（读源码，非推断）：`ApiProbe.requestBodyJson` 的 OPENAI_COMPAT 分支**不发
`stream_options`**；而解析器 `OpenAiSseAdapter` **知道**有 include_usage 尾帧（注释点名）；
**mock 端点却无条件发 usage** ⇒ **所有既有测试都走不到这条路**。
⇒ 「生产在**需要该开关**的端点上拿不拿得到 usage」**从未被验证过**。
⚠ **本批不断言 GLM 属于哪一类**——那正是 §3 闸门两笔要答的。
⚠ 也**不推广到其他 provider**：一家的默认不代表另一家。

## 4. 本批**事先声明不回答**的

1. ⚠ **TTFT 量法的「正确性」**。真端点**没有 timing 的地面真值**：TTFT 是多少，除了我们客户端自己量的那个数之外无从对照。**能验证 timing 量法正确性的恰恰是模拟端点**（它知道自己排的时刻表）。
   ⇒ **本批任何结论都不得被读成「TTFT 量法已在真端点上验证」。** 写下这条，正因为它极易被这么读。
2. **GLM 与豆包／DeepSeek 的横比**——不同模型、不同部署、不同分词，不可比。
3. **网络诉求**——本批是装置/量法对照，不是网络测量。
4. **模型该改成什么**——见 P3，n 小只描述。
