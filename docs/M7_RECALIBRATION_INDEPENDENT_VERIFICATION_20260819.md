## 2. T65 的三条核心推理站不住（落点不变，理由要换）

### 2.1 【最重】构造性失明：T65 的核心判据是无效论据

T65 §4 的判读原文：「签名清晰——**RTT / 抖动 / 上行三项全部正常**，异常全部集中在下行」，
并据此判"这是一次真实的下行卡顿事件"。

**但这三项在构造上就不可能反映第 7 轮里的一次冻结**。`runSim` 的相位顺序
（`VoiceRunner.kt:297-448`）是 **Ping(:303-312) → Uplink M3(:317-330) →
Handshake(:332-341) → Turns(:348-401)**：
- `rttMs`/`jitterMs` 产自 Ping 相位的 12 次 echo（约 1s，会话最开头）；
- `upFrameJitterMs` 产自 Uplink 相位的 150 帧 `/upload`（约 3s，仍在 Turns 之前）。

**三者的采集窗都在 8 轮 Turns 开始之前就关闭了。** 它们不是"没反映这次事件"，
是**够不着**。拿"够不着的仪器读数正常"去论证"异常集中在下行"，是无效论据。

真正带信息量的只有 Turns 内的四项：`ttfbP95Ms` / `mouthEarProxyMs` /
`turnSwitchP50Ms` / `bargeStopMaxMs`。

### 2.2 T65 与它自己的表冲突："除 M7 外没有任何语音指标反映"是假的

T65 §4 结论句：「**除 M7 之外没有任何一个语音指标反映出这次卡顿**」。
**而 T65 自己的表里就印着** `downNetJitterMs` 3.01 → **19.87** → 2.78（6.6×）。

该字段**就是 AQS 的 M2 输入**（`VoiceTestScreen.kt:331` → `AqsScorer.kt:469`，
锚点 `M_FRAME_JITTER_ANCHORS`，v2 权重 **0.12**）。逐条复算三轮子分：

| KPI | id31 | **id32** | id33 | Δ | 权重 | 加权 Δ |
|---|---|---|---|---|---|---|
| **M2**（downNetJitter） | 95.48 | **77.60** | 95.83 | −18.06 | 0.12 | **−2.17** |
| **M7** | 91.74 | **23.48** | 91.36 | −68.07 | 0.05 | −3.40 |
| AQS 总分 | 88.10 | **82.99** | 88.79 | | | |

M2 掉 18 分、加权贡献 −2.17，与 M7 的 −3.40 **同一量级**。这句判词直接假。
（这与 D-497 订正 T46「73/73 excellent」是同一红线族：**印出来的数字与旁边那句
判词对不上**。）

> **但正确的版本比 T65 想说的更强，也更该写进回核报告**：id32 的 M2 子分 **77.60**，
> 恰落在 **11 个完全没有长冻结的蜂窝会话产出的 [77.58, 78.19] 区间之内**。
> 即：**M2 察觉到了"投递被批化"，却给出一个与常态蜂窝逐位难分的读数——
> 它答得出"有没有"，答不出"有多严重"。** 这正是 `anchors.yaml` 引入 M7 的原话
> （P95 会把罕见但致命的长冻结当尾部弃掉）**首次在真实语料上被兑现**。
> T65 把一件可以精确说的事，说成了一件更响亮但错误的事。

**连带一条**：`downNetJitterMs` **整列有天花板**——全 35 行 min 1.335 / max 19.898 /
**≥20.000 的行数为 0**，分布双峰（22 行 ≤11.542，13 行 ∈[18.803,19.898]，中间 7.3ms
完全空档），天花板恰是 `FRAME_INTERVAL_MS = 20`。机制可从源码直接推出
（`:411-413` dev=|Δarrival−Δsched|，帧被整格错位时 dev≈20；`:440` 取 p95，
一次 647ms 偏差在 ~663 个间隔里占 0.15%，被 p95 整个切掉）。
故 T65 表里"6.6×"那一行**不是严重度证据**，19.87 就是天花板本身。

### 2.3 分位数口径被换掉：T65 报的 p99 在语料里根本不存在

T65 §2 的 `p90=141.6 / p95=163.7 / p99=509.6` 是**线性插值**分位数（numpy 默认）。
而仓内一律用**最近秩**（`KpiCalculator.kt:594-602`；`VoiceRunner.kt:644-649` 同法），
且 D-390 关于"P95 弃尾"的全部论证正建立在最近秩上。

按仓内口径重算 n=30：**p90 = 140.148 / p95 = 171.250 / p99 = 647.752**。

差别不是修辞：**仓内口径下 p99 就是那个极值本身**，而 T65 报的 **509.566ms
是语料里根本不存在的数**——它是 171.250 与 647.752 之间插出来的产物，恰好落在
400–1000 斜坡正中。一份主题就是"尾部统计量"的报告，在自己的尾部数字上换了约定。

**并须如实标注**：n=30 时 `rank(p99)=ceil(29.7)=30`、`rank(p95)=ceil(28.5)=29`，
**p95/p99 完全由最大的两个次序统计量决定**，不是尾部形状的独立描述，
读者不应把它们当两条证据。

## 3. 四项 T65 够不到的延伸

### 3.1 647.752ms 的**位点无法归因给"网络"**（本文最重要的延伸）

分三层给判定，强度不同：

| 层次 | 判定 | 依据 |
|---|---|---|
| 是不是"协议/轮间隙伪影" | **判决性排除** | 源码+数据双链，见下 |
| 静默是否真的发生了 | **判决性确认** | 四字段独立咬同一事件 |
| 静默发生在"网络"上 | **证据不足，无法区分** | 四候选位点签名相同 |

**排除轮间隙伪影（判决性）**：`downRawIntervalsUs` 按**轮内** `zipWithNext` 池化
（`VoiceRunner.kt:416-418`），`l.frames` 只收 `turnIndex == i` 的帧（`:373`）——
**跨轮那一对在构造上根本没被造出来**。数据侧独立佐证：跨轮间隙 ≥1.8s
（75×20ms+300ms），而全语料 M7 都在 24–171ms。另用 `voiceNearZeroArrivalRatio`
反解分母，**29/29 行整除吻合 `framesRecv−8`**（另测 offset 0–16，只有 offset=8
得 32/32，其余每个 offset 仅 3/32——该检验确有判别力），证明 `framesRecv=671`
是**真的多收了 19 帧**，不是计数器错位。

**但归因到"网络"这一步没有证据**：四个候选位点——服务端写循环 / 网络 /
设备接收栈 / **App 进程的 OkHttp 读线程**——在本语料产出**完全相同的签名**
（测量点就在 App 进程内）。能区分它们的三样东西，本次采集一样都没留下。

→ **准确表述**：「647.752ms 是一次**真实发生**的下行帧长静默事件，不是口径伪影；
但把它归因为**网络**事件没有证据，本语料在构造上分不出网络侧与本机接收侧。」
T65 §4 的"**不是测量伪影**"后半句越了本仪器的界。

### 3.2 L4（App 进程停顿）不是"理论可能"，是这台设备**有档案的**

`APP_JANK` 的历史读数**就在同一个库里**（`voice30_aneb-probe.db`）：
**9229 条 / 19 个 run**，`gap_ms` min 30 / p50 48 / p90 50 / p99 52 / **max 505**
——距 647ms **只差 1.3 倍**。按带 env 的 run 时长估算速率外推到 n=30 语音语料
（≈16.5 分钟 App 进程时间）：**λ≈0.036–0.21，P(≥1)≈3.5%–19%**。
而语音批还多背了 token 批没有的并发负载（每 ~5s 一次全量 `uiautomator dump`
+ 每 30s 一次 `adb getprop`），故语音侧真实速率**只会更高**。

另：`lowConfidence` **35/35 恒为 1**，其语义是 `session.queueSize() > 0`
（"App 进程的 WS 写队列积压过"）——库里唯一的进程内排队信号，与 L4 同族，
且它经 `VoiceTestScreen.kt:336` 直接盖在 **M7 自己**的 `KpiValue` 上：
**本次回核的每一个 M7 读数都带低置信戳**。

### 3.3 这反过来影响 T65 §7 的"~150 会话"外推

T65 §7 用"≥400ms 频率 = 1/30"外推"要观测 5 次需 ~150 会话"，并称这是
"预案自己邀请的更好的依据"（§1 原文允许用观察到的极值频率重定门槛）。
**但若 id=32 的位点归不给网络（§3.1），这个 1/30 就是"未知来源事件"的频率**，
不能当作"网络级长静默的频率"去重定采样门槛。
→ **建议：T65 §7 的 ~150 外推降格为"待位点定位后方可采信"**，不作为门槛依据。

### 3.4 情形 A 的免责前提，在 `spec/README.md` 里**根本不存在**

预案 §3 情形 A 称：原地改 `anchors.yaml` "不违反 `spec/README.md §3` 的
『只增不改不删』纪律，因为那条纪律要保护的是『已经盖着这个版本戳的历史分数可重算』"。
**核实结果：`§3` 一个字都没这么说**——该规则逐字点名了"锚点表"，且是**无条件的**。
那个"因为"是**预案自己补的推理**，不是 README 的原文。

另一项独立核实：**`aqs-voice-v0.2` 这个版本戳至今零真实分数**——全部真实数据
走 sim 支路，两张 v0.2 表共用同一个 `M7_MAX_GAP_ANCHORS`（`AqsScorer.kt:607`）。
故"落库/对外引用"这条字面判据**写窄了一个 facet**。

→ **但当下不需要拍板**：D-507 已裁"1000ms 不改"，**改锚级尚未启动**，
情形 A/B 的分岔是"真要改锚那天"的问题。本条只登记这个前提缺陷，
**建议大脑择期订正预案 §3 的这句推理**，别等到真要改锚时才发现免责不成立。

## 4. 第二问「蜂窝 vs WiFi 差异」：形状明显不同，但**不下因果**

| 条件 | n | min | p50 | max | 极差 | 落档 |
|---|---|---|---|---|---|---|
| 蜂窝 NR_SA（id15-25） | 11 | 117.175 | 125.024 | 154.423 | **37.2ms** | 60-150:10 / 150-400:1 |
| WiFi（id5-9,11-14,26-35） | 19 | 24.381 | 83.280 | 647.752 | **623.4ms** | <60:6 / 60-150:11 / 150-400:1 / **400-1000:1** |

蜂窝批 11 个值全部挤在一条 37.2ms 的窄带里，WiFi 批横跨 24–648ms，
**唯一进入 400–1000 斜坡的观测出自 WiFi 批**。这在预案 §1"为什么要覆盖至少两种
网络条件"上是**正面印证**——若只跑蜂窝批，会得到"M7 极其稳定"的完全不同结论。

**但必须如实标注三条限制，不下因果**：
1. **网络条件归属在库内查不到**：`voice_result` 19 列**无任何网络/SSID/RAT 字段**、
   无 `runId`；`test_run` 表在 2026-08-04 后零新增；`radio_sample.tsNanos` 是开机
   相对时钟，无法与 `tsEpochMs` 对齐。**唯一来源是任务板 `:84,:85` 的窗口记载。**
   （唯一的库内旁证很弱：批内会话间隔稳定 48.3–52.5s，唯独 id25→id26 之间是
   83.7s，形状上与"两批之间执行 `svc wifi enable` 并等待回连"吻合——旁证非证明。）
2. **WiFi 组内部本身就是混杂的**：跨 3 个批次、至少 2 个 SSID
   （Huawei-Guest / Ascott Star Rewards）、日期跨 08-04~08-15（其间还有 D-494
   的时钟校正事件），不是一个干净的"WiFi 条件"。
3. **共线未被压到一条**：切 transport 必然换出口（D-393 已判定出口与制式完全共线，
   且 `voice_result` 不记服务端/出口，连"两批是否打同一个服务端"都无法核对）；
   另 DW-05 WiFi 批内 14:01:17 起有 NR_SA→LTE 的驻留态变化。
   → 这一对**是本语料最接近受控的比较，但不是"只剩一条共线项"**。

## 5. 第三问「[1000→0] PROVISIONAL 升级与否」：**不升级**

维持 PROVISIONAL 标记，理由：
- 判据 3「中间地带」= "未发现需要调整的证据"，**不等于"已被证实合适"**；
- 400–1000 斜坡 30 个会话只命中 1 次、**1000 末点一次没被触及**（最大值距末点
  还差 352.248ms，斜坡 58.7% 未被走过）；
- 且那唯一一次命中的**位点无法归因**（§3.1）、并有一个同量级的进程内候选解释
  （§3.2）。**拿一个位点未定的孤例去把 PROVISIONAL 升格为已标定，正是预案 §4
  第四条明禁的"事后包装成科学"。**
