## 2. 两个特别镜头的裁决（大脑先看这里）

### 2.1 特别镜头 A —— e1 判读脚本的「第三个缺陷」在哪

派单问的是：dry-run 已自曝两个缺陷（正则不匹配真 logcat；选错图层却不报错），第三个在哪。
**三个镜头各自独立给出了一个答案，三个都被验证 CONFIRMED，彼此不冲突——它们是三个不同的缺陷。**
按危害排序：

1. **【最重·已修 D-392②】采集器订的 logcat 标签根本没有生产者。**
   `e1_collect.py` 订 `AnebAdapter`，而 `AnebAccessibilityService.kt:361` 的 `TAG` 是 `AnebProbe`；
   `logcat -s <tag>:I` 是排他过滤 ⇒ **通道 A 结构性恒零行**。实证：两次 dry-run 的 `adapter.log`
   **都是 0 字节**，而报告把「通道 A 未判读」归因给 `:probe` 缺时戳——**一句在本次运行中没有任何
   证据支持的诊断**。即便 v2 明天补了时戳，标签不改照旧一行采不到，**真机窗那一轮会白烧**。
   离线 44 条反例抓不到它，因为**夹具自己发明了那个不存在的标签**（`I/AnebAdapter:`）——正是同一次
   提交刚为 `E1_STIM` 正则庆祝抓到的 D-309 形状，在同一个文件的另一半原样复发。

2. **【待办】被截断的时戳解析成合法整数 ⇒ 时钟段静默印出错值，并被自己的判词命名为「深睡」。**
   `_int()` 只挡「读不出来」，不挡「读出来但是错的」。实测三种截断：样本数一个不少、退出码 0、
   零告警，而 `spread` 从 21 400 ns 变成 **8 263 秒**，紧跟着的一句是「跨度不是噪声，是这段时间里
   设备深睡了多久」。**非法字节那一路反而是安全的**（`int()` 抛→丢弃）——现有防线的方向反了。

3. **【待办】第三个缺陷不在解析层，在判读层**（特别镜头 B 的独立回答）：
   - `gate_verdict` 对通道 A 是**单边**的（`p99 <= frame_ms`），而通道 A 量的 `t_event − t_present`
     **期望方向就是负**。实测同一个 500 ms 滞后：C 报 FAIL、**A 报 PASS**。M3 门对通道 A 名存实亡。
   - `align_present` / `_analyze_channel_a` 允许**多次翻转对到同一帧 / 复用同一条事件**：3 次 commit
     + 1 帧 ⇒ `n=3, dropped=0, PASS`。一次物理上屏被算成 3 个样本（D-335「汇池前提无守卫」同形）。

### 2.2 特别镜头 B —— DTO 派生键集在 DTO 演进下正确吗

**结论：主线演进全部正确且 fail-closed；有 4 类形态会让它「静默给出错的键集」，其中一类正落在
v2 明天要加的那个字段上。** 30 例沙箱实验（另一镜头带对照组独立复现其中最重的一条）：

| DTO 演进形态 | 判定 |
|---|---|
| 新增必填 / 可选 / 带默认值字段 | ✅ 正确（有无默认值正确决定 required） |
| 类型变更 `String→Int` / `String?→String` / `String→List<String>` | ✅ 正确（当场 A4 报错） |
| 新增嵌套 `data class`（同文件，含 `List<X>` / `Map<K,List<X>>` / 声明在 `object` 内） | ✅ 正确（自动递归，内部未知键被咬） |
| `@SerialName` 重命名 / 字段删除 | ✅ 正确（A1+A2 双报 / A1 报未知键） |
| **嵌套类型是 `class`（非 data）/ `enum class` / `typealias` / 声明在别的文件** | ❌ **0 违规，整块静默不查** |
| **默认值字符串里带 `//`、`)`、`>`** | ❌ **下一个字段整个从键集里消失** |
| **`var` 代替 `val`** | ❌ **该字段既不在 allowed 也不在 required** |
| **注解里带冒号的字符串**（如 `@Deprecated("a:b", level = …)`） | ❌ 必填字段被判成可选 |
| `parse()` 里某条 `require` 被重构走 / 新增一条 | ❌ 判据静默变窄 / 静默不覆盖 |

**最要紧的一条**：`_check_value` 末尾「认不出的类型：不判。凭猜测报违规比漏一格更糟」——
**同一份文件里其余三处都拒绝真空通过**（`:187` A2「refuses to pass rather than pass vacuously」、
`:280`、`:292`），只有这一处例外，**而它是唯一会被明天的改动踩到的那处**。沙箱实测：v2 把
`VersionStampDto` 声明在另一个文件里 ⇒ 内部写一个严格解析器必拒的键，**门印 OK、零违规**。
现有反例 `test_an_unknown_key_INSIDE_the_future_version_stamp_is_caught` 覆盖不到——它的夹具把新 DTO
追加进**同一份源码字符串**，恰好落在能下钻的那一支（D-335「夹具落在另一分支，守卫看着在守、实则一次没走到」）。

> **给 v2 的一句话**：明天落 `validated_against_version` 时，`VersionStampDto` **必须是
> `AdapterSpec.kt` 同文件内的 `data class`**，否则这道门对该段一个键都不查。序列名请照用
> `version_name` / `version_code` / `captured_at` / `source`（R21b–e 是手写字面量，改名会让门对一份
> **设备接受**的合法文件报四条违规）。字段**带默认值** ⇒ 门自动放行；**不带** ⇒ 四份 JSON 当场全红
> ——这个方向是对的，它把 README 的「先 DTO 后 JSON」顺序约束变成了机器可判。
