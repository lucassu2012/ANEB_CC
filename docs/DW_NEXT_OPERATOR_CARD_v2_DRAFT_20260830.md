## 1. dump 周期：**用公式算，不要抄那个数**（D-599／D-600）

    界(ns) = 127 × 「该批 sf_latency.txt 首行的那个数」
    要求：dump 周期(换算成 ns) < 界(ns)

**照做三步，全程不需要你做任何判断**（口径由大脑 2026-08-30 夜裁定为此，**不换算赫兹、不舍入**）：

1. 打开该批 `sf_latency.txt`，**看第一行**——它是一个纯数字（刷新周期，单位 ns）；
2. **乘 127**，得到界（ns）；
3. 把你要用的 `--framestats-period-s` **乘 10 的 9 次方**换成 ns，**必须小于界**。

**本批实测的样子**（十格 ＋ 四个作废格，**十四个目录首行全是同一个数**，我逐个查过）：

    首行 16666666  →  界 = 127 × 16666666 = 2,116,666,582 ns ≈ 2.117 s
    period 1s = 1,000,000,000 ns  <  界   ✅ 通过，余量约一半

- **环深 ＝ 127 帧**（`dumpsys SurfaceFlinger --latency` 恒返回 127 行，实测十四个目录无例外）。**⚠ N6：这个 127 是这台设备实测的，不是常识——换设备必须重验**（读 `sf_latency` 时顺手数一次 dump 的帧行数，零成本）；
- **⚠ 不许拿设备铭牌率代入**——必须读该批实测首行（60Hz 与 90Hz 给出的界差 1.5 倍）；
- **⚠ fail-closed 守卫**：**若首行不是纯数字**（空文件／报错输出／换了设备），**停下，不要猜刷新率**。
  「读不到」与「读到了一个正常值」在下游长得一样，而这条公式整个吊在这一个数上。

**为什么这条值得占一整节**：周期 20s 时，相邻两次 dump **要么完全相同、要么完全不相交**，
几乎没有中间态。**逐格全表见 `evidence/doubao_wave0_20260830/FINDINGS_RAW.md` §1e**（六格中间态占 **0–20%**；`cell_f2` 30 对＝相同 14／重叠 4／不相交 12，**v3 独立复核一字不差**）。⚠ **本句此前写「恰好为 0」，已改**——**「恰好」是漂亮数的签名**；`wifi_f1`／`cell_f1` 的 0 **是那个 0–20% 连续谱的下端，不是孤立巧合**。
不相交那些之间的帧**永远丢了**，而**丢帧与思考静默在去重后的序列里长得一模一样**。
⇒ **周期 ＜ 界之后**（**N1：严格小于，与公式行一致；打平处不算通过**），**环装得下、必然重叠，「环之间有洞」和「一轮只拿到一个环」同时消失**——
**它们是同一个溢出机制的两个症状，别当成两件事去修**。

| `ttft_cluster_ms` 有值 | **该轮最长内容事件间隔是否 > 门限** | **全程小于门限 ⇒ 簇窗不闭合 ⇒ 值兜底成驱动器下一次点屏**，再可能被 `TTFT_CEILING_MS=30_000` 静默转 `null` |

**⇒ `null` 是一个合并 token**：「没形成次簇」／「形成了但超上限被删」／「形成了但没播报」**在日志里长得一模一样**。
**任何「没有出现 X」的结论，先去源码查这条链上有没有过滤器/上限/节流把 X 吃掉。**

### 5a. 🔴 标记↔事件的匹配一律用最近邻，**不得假设 `turn_start` 在该轮一切之前**（D-617 ⑤）

**打字斜坡与 `turn_start` 的先后，在不同格里是反的。** 逐格实测（`EditText` 的 `txt_len` 递增段末尾 相对 `turn_start`，负＝打字在标记之前）：

| 格 | 中位偏移 | 驱动器版本 |
|---|---|---|
| `wifi_f1` / `cell_f1` | 大多数轮**该轮内根本没有斜坡**（标记在打字之前），首轮 **+1.3～1.5s** | 首版 |
| `wifi_f2` | **+1.36s**（打字在标记**之后**） | 首版 |
| `cell_f2` / `cell_f1b` / DW-02 全部五格 | **−2.00s**（打字在标记**之前**），逐轮极稳 | 改版 |

**⚠ 归因订正（我实测后与 D-617 ⑤ 原述不同，已报大脑）**：原述把它归给**功能**（F6 vs F1）。
**但 F2 在两个驱动器版本下都跑过，而它的符号是相反的**（`wifi_f2` **+1.36s** vs `cell_f2` **−2.00s**）
⇒ **决定符号的是驱动器版本，不是功能。** 首版是「先打标记再打字」，改版是「先打字再打标记」（`sleep(1.8)` ＋ adb 开销）。

**⇒ 后果比原述更严重**：这个偏移是**采集脚本的性质**，**会在两个窗之间静默改变**，
而且**光看数据认不出来**——你得去看那一版驱动器。⇒ **两条硬要求**：
**① 匹配一律最近邻**（这条无论成因为何都成立，D-617 ⑤ 的操作结论我全额采纳）；
**② 每格 README 记下本格用的驱动器版本／提交哈希**，否则事后无法判定该格的偏移方向。
📌 **v3 第一次对拍就因为假设「`turn_start` 在前」得出「偏移 +102s、检测失效」的假结论，差点报废一个好锚。**

⚠ **并记我自己在核这条时的一次险些误报**：我第一次量只看了标记前后**各 8 条事件**，
那个窗口里全是 `txt_len=0` 的 UI 抖动，于是我差点回报「我的数据里根本没有打字斜坡、该现象不存在」。
**斜坡在窗口之外。** ⇒ **用一个太窄的窗口没找到某物，不等于它不存在**——与「零命中先证明量法」同族。
