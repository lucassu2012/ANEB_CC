## 2. 出口 IP：第三次独立 NR 观测，出现第三个不同的出口 IP

逐 run 逐场景读 `network_snapshot.server_observed_addr`（剥端口）：

| 观测 | 时间 | 出口 IP | 场景数 |
|---|---|---|---|
| 07-31 试点 NR 窗（既有记录，`nr_timeline_20260802/README.md` §2） | 07-31 下午 | `106.92.23.196` | （未知，历史记录） |
| pounce#1（D-424/D-426，本次批采前） | 08-02 16:46 | `106.80.108.105` | 9（与 LTE 四窗同址） |
| **今天 15 个批采 run（本条新增）** | 08-03 09:09–11:44 | **`106.83.173.55`** | **135**（15 个 run **全部**同一 IP，逐场景验证，零例外） |

**三次独立 NR_SA 观测，三个互不相同的出口 IP，但每次观测内部（跨场景、跨 run）
完全稳定**。这与"制式与出口完全共线"的既有框架（一个 RAT 对应一个固定出口）
**对不上**：如果出口 IP 是 RAT 决定的，三次 NR 观测应该收敛到同一个（或至少重复
出现）出口，而不是三次三个。**更像**出口 IP 是 CGNAT 会话级分配（每次蜂窝数据
连接建立/重建时由运营商网关分配，与 RAT 无必然关系），今天这 2.6 小时窗口里设备
全程保持同一个蜂窝数据会话（135 个场景零变化），出口自然稳定；但重建会话（比如
今天 09:09 这次批采相对昨天 pounce#1 是一次新的会话）会拿到不同的出口。

**如实标注**：这仍是**三个观测点**（n=3 个独立 NR 会话），不构成统计显著性检验，
不排除"NR 与出口有某种更复杂的关联，只是这三次都恰好赶上了会话重建"这类替代
解释。LTE 侧目前只核实过"四个窗同址"（D-393），没有专门核过"LTE 是否也会话级
换出口"——若 LTE 侧同样能观测到跨会话换出口，则"共线"框架更彻底地站不住；若
LTE 侧稳定不变而 NR 侧三次三样，那差异本身也值得追问（但这需要专门设计的对照，
不是本条能回答的）。

## 3. STRADDLED 核对 + 52 分钟停顿：DB 地面真值确认零丢失

批日志（`nr_batch_brain_20260802.log`）自报 `ratStart=NR_SA ratEnd=NR_SA` +
`CLEAN single-RAT` 逐 run 出现，`grep -c STRADDLED` = **0**（15/15 全清洁，
日志自身说法与 grep 结果一致）。

**52 分钟停顿（RUN 8 END 10:04:27 → RUN 9 STARTED 10:57:09）**：按大脑的方法论
指示——不从日志侧猜，查 DB 地面真值：

```sql
SELECT runId, startedAtEpochMs FROM test_run
WHERE startedAtEpochMs BETWEEN <10:04 本地> AND <10:56 本地>;
-- 0 行
```

**该区间内 `test_run` 表零记录**——不是"有一个半截 run"，是**压根没有任何 run 尝试
启动过**。结合两侧唯一的信息来源都指向同一个空区间（DB 无记录、日志无 RUN 9
之前的任何行），最合理的解释是**批脚本本身在这段时间里没有触发新一轮采集**（可能
在轮询/重试逻辑里卡住，或某个判定条件迟迟不满足），而不是"run 启动了但数据丢了"。
**无数据丢失**，但这 52 分钟本身是一次真实的批采效率问题，值得脚本属主关注（本文件
不诊断脚本内部逻辑，只确认数据侧干净）。

## 4. NR 侧首次 CV：与 LTE 侧同量级

逐 run 取 `n1RttP50Ms`（N1 网络侧 KPI）场景内中位数，按 profile 分组，15 个 run
作为 15 个独立样本点算 CV：

| profile | n（run 数） | 均值 (ms) | 标准差 (ms) | **CV%** | LTE 侧对照（试点，既有记录） |
|---|---|---|---|---|---|
| s1_chat | 15 | 57.842 | 3.708 | **6.41%** | 5.5% |
| s3_multimodal | 15 | 59.544 | 3.594 | **6.04%** | 5.9% |

**同量级**：NR 侧两个 profile 的 CV（6.41%/6.04%）与 LTE 侧（5.5%/5.9%）差距在
1 个百分点以内，均落在个位数百分比区间。**登记，不下声称**：这不代表"NR 比 LTE
波动大"（差距在这个尺度下不足以下此判断，且未做显著性检验、未控制忙闲/时段等
混杂因素）；能登记的是——**n≥15 这个判据在 NR 格上暂无理由认为需要显著放大**，
两条制式的离散度在同一数量级，扩展轮把 NR 也按同一采样量惯例设计是有实测支撑的，
不是凭空沿用 LTE 的经验。

## 5. mPci 观察：两条 PCI 读取路径能力不同，实测证实

`rat_watch.tsv` 第 6 列（PCI）在 NR_SA 期间恒为 `2147483647`
（`CellInfo.UNAVAILABLE` 哨兵——`telephony.registry` 的 `mPci` 字段在这台设备
NR_SA 状态下不可得，大脑已在续派消息里订正此前"屏超时残留"的误读）。

**radio_ctx（`RadioCollector` 走 `CellInfoNr` 路径）在同一时间窗口读到的 PCI**：

```
135/135 个场景，PCI 恒为 672（单一整数值，非哨兵）
```

**两条路径能力确认不同**：`telephony.registry`（rat_watch 轮询的路径）在 NR_SA
下读不到 PCI，`CellInfoNr`（radio_ctx 采集走的路径）读得到、且整个 2.6 小时窗口
稳定为同一个值（672，与设备全程未换服务小区吻合）。这不是矛盾，是两条系统 API
在这台设备/这个 ROM 上对 NR 的支持深度不同——`radio_ctx` 的设计（D-284/D-367/D-368）
选择走更完整的 `CellInfoNr` 路径这个决定，在这次真实数据上得到了直接印证：如果
当初采集器也走了 `telephony.registry`，今天的批采会拿不到任何 NR 场景的 PCI。

## 6. NR 信号质量：首份真实语料

`radio_ctx` 里 NR 场景的 rsrp/sinr 分布（135 个场景，全部 `rat=NR`、单一服务小区
`pci=672`）：

| 量 | n | min | median | max |
|---|---|---|---|---|
| `rsrp_dbm` | 135 | −90.0 | **−85.0** | −81.0 |
| `sinr_db` | 135 | 15.0 | **20.0** | 24.0 |

数值量级合理（RSRP −90~−81 dBm 属中上信号强度、SINR 15–24 dB 属良好信噪比，
非哨兵、非占位），且波动范围窄（RSRP 极差 9dB、SINR 极差 9dB）——与"全程同一
服务小区、设备静止未移动"的场景吻合。**这是仓库里第一份非空的真实 NR 信号质量
分布**（此前所有 radio_ctx 真机验证要么是 LTE，要么是 NR 但仅 2/9 场景的孤立点，
D-424）。仅登记数值分布，不据此判断"信号好不好会不会影响 KPI"——那需要专门的
相关性分析，不在本条范围内。

## 7. 本文件明确没有做到的（诚实缺口清单）

1. 出口 IP 三次观测的"会话级分配"解释是**推断**，没有拿到运营商侧或系统侧任何
   直接证据（比如一次蜂窝数据会话的建立/重建事件日志）证实这个机制，只是从
   "组内稳定、组间不同"这个模式反推最简解释。
2. LTE 侧是否同样存在"会话级换出口"现象，本文件没有专门核实（D-393 的四窗
   同址观测本身没有设计成"检验会话是否重建过"）。
3. 52 分钟停顿的**根因**（批脚本内部为什么卡住）本文件没有诊断，只确认了数据侧
   干净——这需要读脚本自身的轮询/重试逻辑，不在本次判读范围。
4. NR CV 的两个百分点（6.41%/6.04%）与 LTE（5.5%/5.9%）差距是否有统计学意义，
   本文件没有做显著性检验（也不具备条件——两组样本特性、混杂因素都未对齐）。
5. mPci 差异背后的具体系统 API 行为原因（是华为 ROM 定制、还是 Android 平台在
   NR_SA 下 `telephony.registry` 本身的已知限制）本文件没有深入，只确认了现象。
