## 3. rat_watch 粒度：如实标注，不能声称精确同步

自己重新数了 `rat_watch.tsv` 里 16:45–16:53 这段的采样间隔（非转录"31 秒"这句话）：

```
16:45:29 ON
16:46:00 ON   (+31s)
16:46:33 ON   (+33s)
16:47:05 OFF  (+32s)
16:47:35 OFF  (+30s)
```

**确认粒度约 30–33 秒，不是逐秒**。这意味着"屏幕 16:47:05 灭"这句话的准确写法是
"屏幕最迟在 16:47:05 已经是灭的，最早可能在 16:46:34 就已经灭了"——**真实息屏时刻
是一个 32 秒宽的未知区间，不是一个已知的精确时刻**。

本文件独立算出的数据边界（16:46:58.4~59.0 之间）落在这个 32 秒区间的**后半段偏晚
位置**（区间跨度 16:46:33→16:47:05，边界落在距区间起点约 25–26 秒、距区间终点约
6–7 秒处）——比起"区间中点"更接近"区间终点"，这个位置本身弱支持"数据边界≈真实
息屏时刻"（若边界远离两端、卡在区间正中，反而更可疑是巧合）。**但仍然只是"更像"，
不是证明**：32 秒的定位精度不足以排除"数据边界与息屏是两个各自发生、只是碰巧接近
的独立事件"这一可能性。

## 4. §4 stayon 矛盾：深挖但未能完全判别，新发现一处更具体的异常

### 4.1 独立发现：配置的息屏超时是 600 秒，而实际息屏发生在约 50 秒内

```
$ adb -s 8MY0221126002537 shell settings get system screen_off_timeout
600000    # 600 秒 = 10 分钟
```

run 起于 16:46:14.943；rat_watch 确认屏幕在 16:46:33（run 起后 **18.1 秒**）仍为 ON，
到 16:47:05（run 起后 **50.1 秒**）已经是 OFF。**配置的超时是 600 秒，实际息屏落在
run 起后 18–50 秒之间的某个时刻——只用了配置超时的 3%–8%。**

**这比"stayon 为什么没挡住普通超时"是一个更精确、更值得追的问题**：即使完全不考虑
stayon，**普通的 10 分钟不活动超时本身也不足以解释这次息屏**——10 分钟内不该自然
超时。这说明起作用的**不是**"stayon 没能压过普通超时"这条最简单的解释，而是有
某个**独立于普通超时机制**的东西让屏幕在不到一分钟内灭了。

### 4.2 stayon 的实际调用时机：已定位脚本源码，精确核实

`nr_pounce_log.txt` 在 run 窗口内只有这些行，本身没有一行显式记录"设置了 stayon"：

```
16:45:55  NR DETECTED ... -- preflight
16:45:57  wifi_on before=1
16:46:14  RUN STARTED (single run) ratStart=NR_SA
16:53:15  RUN_END run_id=019fc1a6... status=completed
16:53:27  wrap-up: wifi_on=1 stayon=0
```

**订正**：本文件初稿在此处写"未能找到 `nr_pounce.ps1` 脚本源码"——后续定位到它落在
另一会话的本地 scratchpad（`...\E--G-Project-ANEB\c7bc03db-.../scratchpad\nr_pounce.ps1`，
路径本身不受权限限制，只是此前没搜到），已读取全文核实。**关键序列（脚本
:98-112，逐行摘录）**：

```powershell
adb ... input keyevent KEYCODE_WAKEUP                    # 唤醒
Start-Sleep -Milliseconds 800
adb ... input swipe 540 2200 540 600 300                 # 滑动解锁
adb ... svc power stayon usb                              # ← stayon 在此设置
adb ... svc wifi disable
Start-Sleep -Seconds 5
... logcat 落盘设置 ...
Start-Sleep -Seconds 2
adb ... am force-stop com.aneb.probe
Start-Sleep -Seconds 2
adb ... am start -n com.aneb.probe/.ui.MainActivity --es mode forensic ...   # ← RUN STARTED
```

**确认**：`svc power stayon usb`（不是 `stayon true`）在 `am start` 之前约 9–11 秒
（5+2+2 秒显式 sleep 加数次 adb 往返）被调用，即约 **16:46:03–16:46:05**。到 rat_watch
确认的最早息屏时刻（16:46:34，区间起点）之间，stayon 已经生效**至少 29–31 秒**；到
本文件算出的数据边界（16:46:58 左右）之间，已生效约 **53–55 秒**。**这排除了"stayon
命令还没来得及执行/生效"这类时序竞态解释**——它确有充分的生效窗口。收尾脚本
:143 查询的正是同一个 `stay_on_while_plugged_in` 设置（与本文件 §4.3 独立验证的
命令一致，两处互相印证）。剩下能解释"设置生效了但屏幕还是灭了"的，只剩 §4.4
三个候选里的 B/C，A（时序竞态/命令未执行）**在此确认排除**。

### 4.3 当前 USB 供电状态：现在为真，历史无法回溯确认

```
$ adb -s 8MY0221126002537 shell dumpsys battery | grep -i usb
USB powered: true
```

**现在**（复核时刻）设备确实通过 USB 取电，`svc power stayon usb` 这类设置在**此刻**
应该是有效前提。但 `dumpsys battery` 不提供历史记录，**无法回溯确认 16:46–16:47 那
段时间 USB 供电状态是否也是 true**——如果当时曾短暂掉电或被系统判定为"仅数据线未
供电"，`stayon usb` 的生效条件就不成立。这个候选**既没被证实也没被证伪**。

### 4.4 三个候选机制并列，如实标注哪个更可能、哪个说不通

| 候选 | 与"18–50 秒内息屏"这个观测吻合吗 |
|---|---|
| A. 普通超时（600s）压过了未生效/时序竞态的 stayon | **排除**——理论上就说不通（600 秒超时不该在 50 秒内触发）；§4.2 找到脚本源码后进一步确认 stayon 在息屏前至少 29–31 秒已生效，时序竞态解释也被排除 |
| B. EMUI 智能息屏/AI 电源管理（独立于 `screen_off_timeout` 设置的另一套机制，常见于华为设备） | **吻合**——这类机制常常比普通超时短得多、且不受 `stay_on_while_plugged_in` 约束，因为它走的不是同一条判断路径 |
| C. USB 供电在 run 期间短暂中断，stayon 条件失效，叠加某种更短的有效超时（如"未充电时"的另一档超时设置） | **部分吻合但纯推测**——没有查到"未充电超时"这一档的具体配置值，无法验证 |

**本文件的判断**：候选 B（EMUI 自有的、不受标准 `stayon` 约束的息屏机制）与观测最
吻合，因为它是唯一能同时解释"配置超时 600 秒"与"实际 50 秒内息屏"这个数量级落差
的候选——A 在数量级上就不成立，C 目前没有可验证的具体机制支撑，只是排除法剩下的
"如果 A/B 都不对"的兜底猜测。**但这仍是判断，不是证据链完整的结论**：本文件没有拿
到任何一行"某个 EMUI 息屏子系统在 16:4x 触发了息屏"的直接证据（logcat 已滚出缓冲区，
见 §5），只能从"配置值 vs 实测值差两个数量级"这个间接证据反推。

## 6. 修复方向的建议（供大脑裁定，不代批）

**如果候选 B（EMUI 自有息屏机制）成立**，修复不该继续在"调对 `stayon` 参数"这条路上
加码——`stayon`/`screen_off_timeout` 都是标准 AOSP 机制，而候选 B 恰恰是"绕过标准机制
的另一套开关"。更稳的修复方向是**应用层直接持有屏幕**：`PowerManager.WakeLock`
（`SCREEN_BRIGHT_WAKE_LOCK` 或等价的 `FLAG_KEEP_SCREEN_ON`）在 run 开始时获取、run
结束时释放——这条路径不依赖 USB 供电状态、不依赖系统级 `stayon` 设置是否被 EMUI
覆盖，是 Android 官方为"前台任务需要屏幕常亮"这个精确场景设计的机制。**这条建议本身
未经真机验证**，下一个真机窗如果要验证，最直接的方法是：run 开始时额外记一行
`dumpsys power | grep mWakefulness/mHoldingWakeLockSuspendBlocker` 之类的即时状态，
或者干脆先加 wake lock 再跑一次同样的 NR 窗口，看 44 秒边界还在不在。
