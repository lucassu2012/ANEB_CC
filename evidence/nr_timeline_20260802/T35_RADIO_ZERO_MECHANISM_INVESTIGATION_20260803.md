## 1. 两脚本逐行差分：只有一处结构性差异

`nr_pounce.ps1`（v2，`C:\...\E--G-Project-ANEB\c7bc03db.../scratchpad\`）与
`nr_batch_brain.ps1`（大脑，同名模式下另一 session 的 scratchpad）逐行核对：

| 环节 | pounce | batch | 是否有差异 |
|---|---|---|---|
| 唤醒/解锁序列 | `KEYCODE_WAKEUP`→800ms→`swipe 540 2200 540 600 300` | 逐字符相同 | 无 |
| `stayon`/`wifi disable` 时序 | 每次 pounce 前设一次 | 循环前设一次（15 run 共用） | 无实质差异（两者都是"发射前已生效"，不影响单次 run 内部） |
| `am start` 参数 | `--es mode forensic --es transport cellular` 等 | 逐字符相同 | 无 |
| 发射前 sleep | wake 800ms + stayon/wifi 后 5s + logcat 后 2s | 逐字符相同 | 无 |
| 单 run 超时 | 12 分钟 | 12 分钟 | 无 |
| **发射时机相对 RAT 切入的新鲜度** | **检测到 NR 后 ~10-15 秒内发射**（轮询 20s 一次，检测到即走完几个 adb 预检+唤醒+等待就发射） | **窗口已开数分钟到数小时后才发射**（脚本本身是在窗口已稳定 2.6+ 小时后才被人工启动，且循环内 15 个 run 全部发生在窗口早已稳定之后） | **唯一结构性差异** |

**结论**：两脚本在"怎么发射一个 run"这件事上逐行相同（wake 序列、`am start`
参数、`stayon`/wifi 时序、单 run 内部超时/轮询逻辑全部一致）——**唯一的
系统性差异是"这次发射距离 RAT 刚切入 NR 有多久"**，不是脚本写法本身的 bug。

## 2. 精确到 tick 的故障定位（比"2/9 场景"更细的一层）

逐 tick 查 `radio_sample`（1Hz，`stale`/`networkType`/`nrState`/`rat`/`pci` 五列）：

| run | 总 tick 数 | 健康 tick | 崩溃点（offset） | 崩溃后 |
|---|---|---|---|---|
| `019fc1a6` | 413 | **0–43（44 个，前 44 秒）** | **第 44 秒（idx=44）** | 44–412（369 个）**永久 stale**，直到 run 结束 |
| `019fc520` | 360 | **0–31（32 个，前 32 秒）** | **第 32 秒（idx=32）** | 32–359（328 个）**永久 stale**，直到 run 结束（与 D-439/T30 已引用的"360 行 328 stale"逐位吻合） |

**不是渐变，是硬切换**：两发 run 都是"前 N 秒逐 tick 100% 健康 → 第 N+1 秒起
逐 tick 100% stale，一次性归零，此后 5-6 分钟一次都没恢复过"——没有中间态，
没有偶发波动，是一次性、不可逆的转变。

**故障范围比想象中窄**：崩溃后的 tick，`networkType` 与 `nrState` **仍然正确
（`NR`/`nsa_unknown`），不受影响**；只有 `rat`/`pci`/`tac`/`arfcn`/`rsrp`/`rsrq`/`sinr`
这一组字段永久归 null。对照代码（`RadioCollector.kt`）：`networkType`/`nrState`
分别来自 `tm.dataNetworkType`（:284）与 `readNrState(tm)`（:398，读
`tm.serviceState`）——**两条独立、不经过 `requestCellInfoUpdate`**；而
`rat`/`pci` 等全部来自 `pickCell(cellInfos)`（:306），`cellInfos` 只有一个
来源：`requestCellInfo()`（:235）里的 `tm.requestCellInfoUpdate()` 异步回调，
超时或失败才退到 `tm.allCellInfo`（同步缓存）。**这精确圈定了故障范围——
不是整个 `TelephonyManager` 实例坏了，是 `requestCellInfoUpdate`/`allCellInfo`
这一条管线单独卡死，且卡死后再没自愈过**。

## 3. 正面处理"方向矛盾"：不是"刚切入就采"本身导致数据差，是撞上了一次性瞬态窗口

大脑指出的矛盾原文："NR 刚切入就采 vs 稳定后才采"是首要怀疑变量，但两发
坏 run 都是场景 0/1（约 32-44 秒）健康后才死，**不是一发射就死**——如果
"切入太早、信号/服务还没稳"是直接原因，理应从 tick 0 就表现异常，不该是
"前 32-44 秒完全正常，然后突然死"。

**这条矛盾不需要否定"发射时机"这个变量，需要把它从"绝对时间点"精化成
"是否撞上一次性瞬态窗口"**：

- 两次崩溃点（idx=44、idx=32）虽然 tick 数不同，但都**接近"场景 0+1 合计
  耗时"**——`report_body` 里 `sampled_n`（idx=0/1 累计非 stale tick 数）：
  `019fc1a6` 是 26+18=44（与崩溃点 idx=44 **完全吻合**）；`019fc520` 是
  26+5=31（与崩溃点 idx=32 相差 1，同一量级）。**崩溃点不是固定墙钟时刻，
  是跟场景 0/1 实际耗时高度相关的一个"事件边界"**，不是巧合。
- **重新表述的假说**：RAT 刚切入后，telephony 框架内部（RIL 请求队列/
  ServiceStateTracker 重建/CellInfo 子系统再初始化）需要一段时间完成自己的
  收尾——这段收尾**不是在切入瞬间完成的**，而是在切入后大约 30-45 秒左右
  （与场景 0/1 的耗时量级吻合）内部触发一次**一次性**的状态重置/清理。
  **pounce 因为发射早（切入后 10-15 秒内），它的 `requestCellInfoUpdate`
  请求管线在这次一次性清理发生时刚好处于"活跃/有在途请求"状态，被这次
  清理连带清空/孤立，此后再也没人重新初始化它**；batch 因为发射晚（窗口
  已稳定数分钟到数小时），这次一次性清理早已在批采开始前完成，批采的请求
  从来没有处于"清理正在发生"的那个时间片内，所以从不撞上。
- **这个重新表述与观测到的现象完全一致**：①解释了为什么前 30-45 秒健康
  （清理还没发生）；②解释了为什么之后永久 stale（清理把在途请求管线弄
  坏，且没有任何自愈/重试机制去恢复它）；③解释了为什么只有 CellInfo
  子系统受影响、`networkType`/`nrState` 不受影响（这次假设的"清理"具体
  作用在 CellInfo 请求队列这一层，不影响 ServiceState 广播这条完全独立的
  路径）；④解释了为什么 batch 的 15 个 run 全部零故障（发射时机永远晚于
  那次一次性清理）。

**如实标注**：这仍是**候选机制**，不是已证实的根因——"telephony 框架在
RAT 切入后 30-45 秒左右做一次性内部清理，且这次清理会孤立在途的
`requestCellInfoUpdate` 请求"这条具体机制没有 AOSP/RIL 层面的直接证据支撑，
是从"故障范围精确圈定在 CellInfo 管线"+"崩溃点与场景 0/1 耗时高度相关"
+"batch 从不撞上"三条观测反推的**最简解释**，不排除其他候选（比如 RIL
在 RAT 切入后确实有个已知的"多个并发 `requestCellInfoUpdate` 互相卡住"
问题，与"多久之后"无关，只是"这台设备切入 NR 后第一次高频轮询恰好撞上"
那类候选）——§4 的诊断日志就是用来把候选收窄到能证实的程度。

## 4. 诊断日志建议：现有代码在这条故障路径上是完全静默的

**关键事实**：`requestCellInfo()`（`RadioCollector.kt:235-266`）从崩溃发生的
那一刻起，每一秒都会命中 `withTimeoutOrNull` 超时或 `tm.allCellInfo` 失败，
但**这条路径没有任何 `Log` 调用**——不是异常，`guardTick`（D-434/D-435 新加
的 `RADIO_SAMPLER_TICK_FAILED`/`consecutiveExceptionTicks`）**完全捕不到这个
故障**，因为 `requestCellInfo()` 从不抛异常，它总是"成功"返回一个
`(空列表或缓存, stale=true)` 的正常值——这是**另一种"静默失败"的形状**：
不是异常被吞，是异常从来没发生过，只是数据一直是坏的。

**建议在下一次诊断版 APK 里补一次性诊断日志，区分四种目前无法区分的状态**：

1. `withTimeoutOrNull` 超时返回 `null`（`onCellInfo`/`onError` 都没被调用——
   真正的"回调再也不来了"）；
2. `onError(errorCode, detail)` 被调用（框架明确报错，`errorCode` 本身就是
   诊断信息）；
3. `onCellInfo` 被调用但传回空列表（框架应答了，但没数据）；
4. 上面三种都失败后，`tm.allCellInfo` 本身也抛异常或返回空（兜底也失效）。

**只在状态发生变化时打一行**（不是逐 tick 打，避免刷屏——参照
`guardTick.onError` 已有的"仅真异常时打印"设计），成本低、诊断价值高：能
直接回答"崩溃到底是回调不来了、还是回调说了'error'、还是回调说了'没有'"，
这三种在 AOSP/RIL 层面对应完全不同的已知问题类别，光看现在的 `stale=true`
无法区分。**建议采纳，随下次诊断版 APK 一起装**——这是一次性诊断代码，
不建议进正式发布分支，装完这次 pounce 窗口验证完就可以考虑移除或用 flag
关掉，避免长期存在一条"只为一次调查而生"的日志（D-428④拒绝"陈旧连击"
日志的同一条纪律：不为可能只用一次的诊断长期背成本，但这次是"即将真机
验证"的诊断需求，与 D-428 拒绝的"没有真机验证计划"的情形不同）。

## 5. 诚实缺口清单

1. **"30-45 秒一次性清理"机制没有直接证据**——是反推的最简解释，§4 的
   诊断日志装机后如果再撞上一次崩溃，能把候选收窄，但这次没有做到"证实"
   这一步。
2. **只有两个失败样本**（`019fc1a6`/`019fc520`），且都发生在"pounce 发射"
   这一种时机下——没有对照组能验证"如果 pounce 故意晚发射（比如切入后
   2 分钟才发）会不会就不崩"，这个对照本身需要专门设计一次实验，本文件
   没有做。
3. **`sampled_n` 累计与崩溃点的吻合（44 vs 44、31 vs 32）是从两个样本反推
   的模式，n=2 撑不住"崩溃点=场景 0/1 耗时"这个精确对应关系**，只是方向性
   支撑，不是确证。
4. **本文件没有改动任何代码**——诊断日志建议留给大脑/下一次改动决定是否
   采纳与如何实现，本文件只给判断，不代做安装（设备操作按大脑要求归大脑）。
