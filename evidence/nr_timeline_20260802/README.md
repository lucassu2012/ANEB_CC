# 设备制式(RAT)切换时间线 · 2026-08-02 01:3x 抓取

**来源**：P40 一次只读 `dumpsys telephony.registry`（257,674 B，原始 dump 同目录归档）。
**为什么必须归档**：registry 的事件历史是**滚动缓冲**，不存就随时间被冲掉；
而它是目前**唯一**能回答「某个批次跑在什么制式上」的东西——`radio_rollup` 只覆盖批次运行期间，
**批与批之间的制式它看不到**。

## 0. 触发经过：一次「NR 机会窗」的误判，与它带来的真收获

大脑 00:5x 只读探测报告「`accessNetworkTechnology` 同时出现 LTE 与 **NR**，可能正驻 NR」，
急令跑 NR 对照批。**核实结果：设备当时并不在 NR。**

`dumpsys telephony.registry` 的输出是**「当前状态 + 滚动历史事件日志」混在一起**的，
`grep accessNetworkTechnology` 会把历史里的 NR 当成现在。三个只反映此刻的量法一致：

| 量法 | 读数 |
|---|---|
| `getprop gsm.network.type` | **`LTE,Unknown`** |
| 当前 `mServiceState` 第一条 | **`getRilDataRadioTechnology=14(LTE)`**、`CellIdentityLte{mPci=420}` |
| 同上 | **`isNrAvailable = false`**、`mNrFrequencyRange=0` |

**故没有跑那个批**——此刻跑只会再产出一个 LTE 批，还可能被贴上「NR 对照」的标签，比不跑更糟。
**这是量法红线 §2.16 的新一例，形状是新的**：
**对一份「当前状态 + 滚动历史」混在一起的输出做 grep，命中的可能是历史。**

**但同一份 dump 里有远比一个批次值钱的东西**——完整制式时间线，见下。

## 2. 两条实测结论

**① 07-31 试点批确实跑在 NR_SA 上——D-349 的现场推断被测量证实。**
该批（07-31 下午，暖轮 RTT **53.21**）落在 **07-30T20:37 → 07-31T21:24 那段 24.8 小时的连续 NR_SA** 内。
而 **07-31T23:04 的闲时探针**（RTT **69.71**）落在 21:24 之后，即 **LTE**。
**于是「NR 53 ms vs LTE 69 ms」这条对比，两端的制式现在都有测量支撑**，
不再是「一端推断、一端实测」（D-374/D-393 记的那个困难就此消掉一半）。

**② 唯一未分离的仍是出口 IP。** NR 期出口 `106.92.23.196`、全部 LTE 期出口 `106.80.108.105`——
两者仍完全共线。**要分开，仍须在 NR 上跑出一个批并看出口。**

## 3. 对「NR 蹲守」的硬约束（这是本文最该被读到的一段）

**NR 段时长分布（分钟，13 段）**：
`0.03 × 4、0.04 × 2、0.11、0.17、0.24、2.24、3.65、8.96、1487.6`

- **一个 run ≈ 6.5 分钟；一个 4-run 批 ≈ 27 分钟。**
- **13 段里只有 2 段装得下哪怕一个 run**：那段 24.8 小时的（已过去），
  与 **08-01 13:33 的 9.0 分钟**那段。
- **没有任何一段装得下一个完整 4-run 批。**
- 自 07-31 21:24 那段长窗结束后，NR 基本是**秒级瞬闪**。

**所以「看到 NR 就开跑」这条路走不通**——2 秒级的窗口，检测到时已经结束了。
**可选路线（本文只列，不擅自选）**：

| 路线 | 说明 | 风险 |
|---|---|---|
| **A 常驻监听、只记不跑** | 后台持续记录制式切换，先摸清长窗是否有规律（如是否与某时段/位置相关） | 零风险，可今晚就开；但可能几天都等不到长窗 |
| **B 单 run 拼批** | 每逮到一个 ≥7 分钟的窗就跑**一个** run，跨窗凑够 n | 引入「不同时刻」新共线，与要排除的东西打架 |
| **C 强制驻留 NR** | 改设备首选网络模式锁 5G | **属设备设置变更**，需 PO 裁；且锁定后是否还能代表「真实用户体验」要先想清楚 |
| **D 接受一个批跨制式** | 让 radio 八字段如实标注，事后按制式切分 | KPI 归因作废（同一批内制式不同，任何汇池都违反 §2.15） |

**倾向 A 先行**（零风险、零裁决、可立即开始，且它产出的正是选 B/C 所需的依据）。

## 3.9 `rat_watch.tsv` 有一段 62 分钟的空白，是真的空白

**`2026-08-02T11:33:42` → `2026-08-02T12:36:06` 之间没有采样**，这段时间的制式**无人测量**。
该缝**没有回填**：给一个没人量过的时段编出行来，是对一份「某分钟无线在做什么」的时间线
所能做的最坏的事。用这份 TSV 做任何跨该时段的判断时，请把它当作数据缺失，不是「无变化」。

**成因与处置**：首次布防的监听是交给 shell 工具后台执行的**内联循环**，采样九小时后在
`11:33:42` 停止——**没有报错，没有收尾行**。它只能靠「拿末行时戳去比当前钟」才发现，而这
恰是这份时间线本身要排除的那种失明。同一个早上以 `-File <脚本>` 方式布防的 `nr_pounce.ps1`
当时仍在运行，两者唯一的差别就是这个，故监听已改为脚本文件重新布防（`scratchpad/rat_watch.ps1`，
18 小时期限，续写同一个 TSV 而不另开文件——两个文件会让读者更容易漏看某个时段根本没被覆盖）。

> 一条可复用的判据：**守望进程的到期时刻，要和它要守的事件时刻一起核。**
> 同一天早些时候已经踩过一次相邻形状——旧监听的 11 小时期限落在 `13:17:25`，
> 比它要守的历史 NR 窗 `13:33` 早 16 分钟，日志里看不出任何异常。

## 4. 复现

```
adb -s <serial> shell "dumpsys telephony.registry" > telephony_registry_dump.txt
```

解析口径见 §1 的读法说明：按 `notifyServiceStateForSubscriber` 行取
`getRilDataRadioTechnology=NN(NAME)`，合并连续同制式事件，
**每段时长 = 到下一条不同制式事件的时间差**。

**边界**：本文全部结论只来自**一台设备、一个点位**的 registry 历史；
`nrState` 字段在该 ROM 上被打码为 `****`，故**无法区分 NSA 与 SA 的细分状态**，
只能用 `getRilDataRadioTechnology` 的 `NR_SA` 标签。
