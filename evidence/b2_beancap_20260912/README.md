## 0. 一句话结论

`--up` **会生效，但只对工具每次启动后的第一条流**；第二条起完全不受限。
16 次上行里，3 次「首流」被限（0.353／0.355／0.820 Mbps），其余 13 次跑 10.9–16.3 Mbps
——**工具自己数到 3365 KB/s，是它被令其限到的 125 KB/s 的 27 倍**。
⇒ **不是「落不进带、改常数」那种失败**，D-843 那条处置（改 `125` 不改档名）**对本失败形态不适用**。

## 2. 量法（两个独立读数，且服务端那个不经我的时钟）

`POST https://120.79.148.0:8443/api/v1/upload`，载荷 4 MiB。该端点**读完 body 才写响应**
⇒ 客户端以「收到响应头」为终点，**测不到写进本机 socket buffer 的假吞吐**。
- 客户端 goodput ＝ P / (`time_starttransfer` − `time_pretransfer`)
- 服务端 goodput ＝ P / (`recv_end_us` − `recv_start_us`)（服务端自报）
- 每次都核 `bytes == 4194304`；不等即判「本次速率无意义」，不进统计。

⚠ **强制 HTTP/1.1**：h2 的流控窗口自己会限住上行（window/RTT），那会把**协议的限**测成**整形器的限**。

## 4. 三阶段实测（阶段三存在的唯一理由＝时间漂移对照）

| 阶段 | 整形 | 三次客户端 Mbps | 中位 | 判定 |
|---|---|---|---|---|
| 一 基线 | 无 | 14.83 / 10.30 / 5.44 | **10.30** | 判据① 过 |
| 二 整形中 A | `cap_up_1mbit_e01` | **0.355** / 14.01 / 14.82 | **14.01** | **未落带** |
| 二 整形中 B（同一实例续跑） | 同上 | 12.76 / 16.29 / 11.95 | **12.76** | **未落带** |
| 三 收尾后 | 无 | 13.19 / 13.70 / 13.29 | **13.29** | 回基线，极差仅 0.5 |

- **预登记带 [0.85, 1.20] Mbps**：整形中位 14.01／12.76 **远在带外，高侧**。
- **分离判据**（整形中位须 < 基线中位的 1/2 ＝ < 5.15）：**不成立**，整形中位反而高于基线中位。
- 阶段三极差 0.5 Mbps 比基线（5.4–14.8）**更稳** ⇒ 阶段二那些高读数**不是时间漂移**。

起停留痕（脚本自己写的，证参数就是菜单里那串）：

```

```

驱动（判据④，三个时刻）：`1060 服务不存在` → `TYPE 1 KERNEL_DRIVER / STATE 4 RUNNING` → `1060`。
工具自报配置：`{"up": 125.0, "dst_ip": "120.79.148.0", "buffer": 1000.0, "filter": "out", "latency": 0, "loss": 0}`；
`matcher dst_ip: 120.79.148.0`（与生效过的延迟档同一形式）。

**工具自己的计数器**（`bean.log`，2 秒采样）：整形期间 `up=` 峰值 **3365.5 KB/s**。
**它一边自述 `up: 125.0 / dst_ip: 120.79.148.0`，一边数着 27 倍于该帽的出站流量通过。**

## 5. 🔴 那个 0.355 Mbps 的慢次：我没当噪声抹掉，它是**确定性可复现的**

它在 `bean.log` 里是**连续 90 秒稳定在 40–66 KB/s**（t=42–132s），不像随机抖动。
⇒ 提出「只限首流」假设并**重起复跑**：

| 重起 | 首流 | 次流起 |
|---|---|---|
| #1 | 4 MiB → **0.355** Mbps（94.61 s） | 14.005 / 14.818 |
| #2 | 4 MiB → **0.353** Mbps（94.94 s） | 13.652 |
| #3 | **256 KiB** → **0.820** Mbps（2.56 s） | 紧接 4 MiB → **10.876** |

**#3 是判决性的**：首流故意只打 256 KiB，它**照样被限**（基线该是约 0.16 s）；而**仅 0.26 MB
通过之后**的下一条流就满速 ⇒ **是「按流」一次性，不是「按时长／字节耗尽」**。
⇒ 3/3 次重起，首流被限；5/5 次后续流不受限。两次 4 MiB 首流的读数
（0.355／0.353 Mbps，94.61／94.94 s）**三位有效数字吻合**。

**且即便首流，执行的速率也不等于设定值**：
- 长传（4 MiB）稳态 ≈ **44.2 KB/s ＝ 设定 125 KB/s 的 0.354 倍**；
- 短传（256 KiB）平均 ≈ **102 KB/s**（突发桶抬高短传均值）。

⇒ **达成速率不是设定值的稳定函数**，它还随传输长度变。这比「只限首流」更要紧：
即便用「每次重起只测一发」绕过前者，**这个量也不能当刻度用**。

## 6. 隔离对照：缺陷在 `--up`，不在工具／驱动／部署／菜单

限速档失败后**数分钟内**，同一二进制、同一驱动、同一部署脚本、同一菜单通道跑延迟档：

```
delay_lat200:  223.5.5.5  11ms -> 213ms -> 12ms      对照 223.6.6.6  12ms 不动
驱动: 1060 -> STATE 4 RUNNING -> 1060        进程残留: 无
```

⇒ **工具此刻健康**。若没有这一条，「限速不生效」与「今天整个工具坏了」在证据上同形。
顺带一条区分：延迟对**所有**包生效（10 个 ICMP 全被抬），限速只对**第一条流** ⇒ 两个机制
作用范围本身就不同，不是同一段代码。

## 7. 判据③（作用域对照）：判**不可判**，不宣称已验

跑前写死的灵敏度前提是「饱和的桶会把目标 IP 的 ICMP 也排到桶后 ⇒ 目标 RTT 应暴涨」。实测
（与首流同一时间窗，各 100 次）：

| IP | 基线 | 整形中 |
|---|---|---|
| 目标 120.79.148.0 | 34 ms | median 35, p90 36, max 128, **>200ms 的 0 个** |
| 对照 223.6.6.6 | 12 ms | median 12, p90 12, max 125, **>200ms 的 0 个** |

**目标自己都没涨** ⇒ 前提为假 ⇒ 「对照没涨」**什么也证不了**。
这正是延迟档里 `114.114.114.114` 的形状（对照本来就没有读数），故判**不可判**，
**不记作「作用域已验」**。作用域精确到 IP 在延迟档与丢包档各已独立验过，与本判无关。

## 9. 我自己这一份的缺陷与边界（含两个我差点犯的）

1. 🔴 **`schtasks /Run` 被 Git Bash 的路径转换吃成 `C:/Program Files/Git/Run`，整形根本没起**
   ——而「起了没生效」与「压根没起」在上行读数上**完全同形**。逮住它的不是警觉，是判据④
   把「查驱动态」钉在起跑之后那一步（当时 `sc query` 仍 1060、无进程、`start.log` 停在上一档的 STOP）。
   后续一律走 `powershell -NoProfile -Command "schtasks.exe ..."`。
2. 🔴 **我差点把结论建在 `rate=0` 与 `peak_queue=4` 上**：这两个计数器的语义**工具没有文档**，
   我是从名字推的。改为只用**它自己数出来的吞吐**（`up=` 达 3365 KB/s）当判决证据
   ——那个不依赖我对计数器的猜测。`rate=`／`queue=` 全程为 0 只作旁证登记，不承重。
3. **客户端与服务端读数系统性不一致**：服务端恒报更高（如 2.26s vs 1.66s，极端一次 6.17s vs 1.66s）。
   成因未查清（服务端 `recv_start` 打在 handler 入口，其前的等待不计入）。本份一律**以客户端
   （更保守、含全程）为主判**，服务端读数作交叉核对——两者对本结论同向，差异不改变任何一条判定。
4. **每阶段 n=3**，且基线自身离散（5.44–14.83）。这对判据① 够（三次全过 3 Mbps 门限），
   对「落带」也够（读数高出带约 12 倍，不是边界情形）；但**不足以刻画链路本身的分布**。
5. **「每次重起只测一发」不是可用绕法**：见 §5 末——达成速率随传输长度变（44 vs 102 KB/s），
   它能让档**跑起来**，不能让它**当刻度**。是否另寻限速手段属战役／PO 范围，不由本份决定。
6. **未查**：`--rate-schedule`、`--down`（下行限速是否有同样的首流缺陷）、`--filter both` 是否改变行为。
   本份只判被部署到菜单里的那一档。

## 10. 复现命令

```powershell
# 起（非提权会话；注意 Git Bash 会吃掉 /Run，必须走 powershell）
[IO.File]::WriteAllText('E:\tools\aneb-shaper\profiles\current.args','cap_up_1mbit_e01',(New-Object Text.UTF8Encoding($false)))
schtasks.exe /Run /TN ANEB-Shaper-Start
sc.exe query WinDivert                 # 须 STATE=4 RUNNING，否则根本没起
# 量：关键是 --http1.1 与 4 MiB 载荷；终点取 time_starttransfer（服务端读完 body 才回响应）
curl -k --http1.1 -H "Expect:" --data-binary @payload.bin -o resp.json -w "%{time_pretransfer} %{time_starttransfer}" https://120.79.148.0:8443/api/v1/upload
# 判「只限首流」：重起后连打两发，第一发应约 0.35 Mbps、第二发应满速
schtasks.exe /Run /TN ANEB-Shaper-Stop
sc.exe query WinDivert                 # 应回 1060
```
