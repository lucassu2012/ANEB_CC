# T90 真机验证 · 通道 C 图层自愈（`D-644`／`D-648` 放行）

**目的**：`wifi_f6_b_VOID1` 暴露的失效——图层被重建后采集器一直拿旧名字 dump，
**569 次里 524 次取空，而每一层都无错可捕**（合法空响应、退出码 0、判读侧丢弃空段）。
v3 已加自愈（连续 2 次空且出过帧且距上次重挑 ≥5s ⇒ 重挑图层）＋ `sf_layer_probe.jsonl` 落盘。
**本包验的是：自愈真的触发、真的换名、换完真的恢复取帧。**

**不烧额度**：不跑驱动器、不发任何一轮对话。静止的 App 照样返回环缓冲
（健康格里那 413 段「相同」正是如此）。

## 触发器怎么选的（实测，不是猜）

| 动作 | 图层号 | 可否作触发器 |
|---|---|---|
| 退桌面再拉起（不 force-stop） | `#2916` → `#2916` **不变** | ❌ |
| `force-stop` 再拉起 | `#2916` → `#2925` **变了** | ✅ **本包用它** |

⚠ 对被测 App 用 `force-stop` 不违 D-611——**该裁定护的是提供无障碍服务的自家探针**，
豆包没有。**本包全程不碰探针。**

## 判据（跑完看这四样）

1. `collect_notes.json` 的 `sf_dumps`：`issued` / `with_frames` / `empty_streak_max` / `relists`；
2. `sf_layer_probe.jsonl`：每次重挑一行，含 `old` / `new` / `switched` / `list_has_pkg` ＋ `--list` 原文；
3. **触发后 `with_frames` 要继续涨**——只重挑不恢复不算数；
4. `e2_precheck` 的 `dump存活`。⚠ **两项须同看**（D-646 ②），且**两项沉默即健康**。

## 结果（2026-09-01 00:08–00:11，`relist1`）—— **三项判据全过**

`collect_notes.json` 的 `sf_dumps`：
`issued` **139**、`with_frames` **133**、`empty_streak_max` **6**、`ever_had_frames` **true**、
`layer_initial` ＝ `…AliasActivity1#2968`。

`sf_layer_probe.jsonl` 两条：

| dump# | old | new | switched | list_has_pkg |
|---|---|---|---|---|
| 83 | `#2968` | `null` | **false** | **false** |
| 87 | `#2968` | `#2988` | **true** | true |

逐段帧数：`…127 ×80 ， 0 0 0 0 0 0 ， 127 ×…` —— **零帧段恰为 6 段（序号 81–86）**，
此后完全恢复，**最后 6 段全 127**。

### 为什么是 6 段空而不是 2 段：数据把两个常数都照出来了

- `SF_EMPTY_DUMPS_BEFORE_RELIST = 2` ⇒ 第 **83** 次就试了第一次重挑；
  **但那一刻 App 正被 force-stop，`--list` 里根本没有它**（`list_has_pkg=false`）⇒ 重挑失败，
  而**采集器保留旧名继续重试，没有把 layer 置空停摆** —— 这个边角以前没人验过。
- `SF_RELIST_MIN_INTERVAL_S = 5.0` ⇒ 下一次只能在 5 秒后，按约 1.2s/段正好落在第 **87** 次。

**⇒ 空窗代价 6 段约 7 秒；同一失效在没有自愈时是 524 段（`wifi_f6_b_VOID1`）。**

### 判读侧（`e2_precheck`，加 `PYTHONIOENCODING=utf-8` 跑）

`⚠dump存活=95.7%(发出139/有帧133)　逐段行数=0/127/127(min/p50/max)`
**两项都出声**；存活 **95.68% ≥ `DUMP_SURVIVAL_FLOOR` 0.95** ⇒ **出声但不拦**，与设计一致。

> 🔴 **本包订正了速查卡 1c 的一个分支——而那句是我照抄 D-646 措辞时没验它能不能出现。**
>
> 原写法：「**`逐段行数` 满 127 而 `dump存活` 低 ＝ 图层死了**」。
> **这个组合不会出现。** 图层一死，`--latency` 的响应只剩刷新周期头，
> **行数是 `0`，不是 127**（本包实测 `min=0`，且零帧段与存活缺口是同一批 dump）。
> ⇒ **这两个数在这种病里必然同向，是同一件事的两面，不是两个独立证据。**
>
> **真正只看一个数会漏掉的是另一种病**：`min > 0` 而各段深浅不一 ——
> 那时 **`dump存活` 仍是 100%**，因为 `_sf_frame_rows(txt) > 0` 就计入 `with_frames`，
> **工具只问「有没有帧行」，不问几行**（读源码所得，非推测）。
> **这才是「两项须同看」的真正理由**；卡已按此改，**分辨点写成 `min`**。

### 未验的，如实标

- **根因仍未定。** 本包是**用 `force-stop` 人为触发**图层重建，
  **不是复现 `wifi_f6_b_VOID1` 当时那个未知成因**（那次 App 进程全程活着）。
  **本包验的是「自愈管不管用」，不是「那次为什么会坏」。**
- **A 侧无数据**：`adapter.log` 0 字节（`--no-marks` ＋ App 大部分时间静止），
  故判词 `CANNOT_TELL`、退出码 1 —— **与自愈无关，是不跑驱动器的必然结果**。
- **触发器不等于成因**：实测「退桌面」不换图层号、`force-stop` 才换，
  **说明原失效不是由「切走再回来」造成的**——但这只排除了一个候选，**没有证成任何一个**。
