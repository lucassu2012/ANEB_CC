# WinDivert 两层可见性探针：判据（**跑前写死**，2026-09-12）

> **唯一用途**：区分 `c_ics_forward_dryrun_20260912` 判定表的**第 2 行**（驱动没把转发包交上来／层不对）
> 与**第 3 行**（交上来了但没命中／filter-matcher）。那一轮的对照 B 因**信噪比 2.9%** 不可判。
> 🔴 **本份不靠提高信噪比，靠换观测层**：filter 按 IP 收窄后**背景根本进不来**，不需要大流量。

> ⚠ **本份只判「可见性」，不判「可整形性」。** 可见 ≠ 可整——整形还要能改包并重新注入，
> 那是另一件事。**若把「可见」读成「可整」，就是又一次把适用范围写宽一格。**

## 0. 为什么**不用** pydivert（两条实测，非推断）

| 实测 | 后果 |
|---|---|
| 本机 `pydivert` 2.1.0 的 `WINDIVERT_ADDRESS` ＝ **12 字节、3 个字段**（`IfIdx`/`SubIfIdx`/`Direction`），而 WinDivert 2.x 的地址结构是 **64 字节** | 用它去收 2.2.2 的包 ＝ **让驱动往 12 字节缓冲区写 64 字节**。不是「结果不对」，是**内存越界** |
| `pydivert/windivert_dll/__init__.py` 里 `DLL_PATH = os.path.join(here, "WinDivert64.dll")` —— **硬编码，无环境变量覆盖点** | 「显式指向部署那份 2.2.2」在 pydivert 里**做不到**，只能猴补私有属性 |
| pydivert 自带 `WinDivert64.sys` ＝ `9026147943bd…`（47560 B），部署那份 ＝ `8da08533…`（94144 B） | 用 pydivert 就是**加载一份没验过的驱动**，而 D-837 那条穷举比对防的正是这个 |

⇒ **改用 ctypes 直接绑已验的 2.2.2**，且**只用不解析地址结构**（只数 `Recv` 成功次数），
地址缓冲区给足 128 字节。⇒ ABI 风险为零，驱动是被验过的那一份。

## 0b. 🔴 事后补的**前提**（2026-09-12 15:4x；只加前提，**不动任何判定**）

**本节是「进不进得了实验」，不是「结果怎么读」。§3 的三格门槛、`>=5`、VOID 逻辑一律不变。**

**为什么必须补**：原判据与脚本里 `ip route get`／`192.168.137`／热点**全部零命中**
——**一次都没查出口**。而 PC 热点已于 `14:46:53` 关闭、设备已切到别的 WiFi。
此时开跑，**B、C 两格必然为 0**：那**不是**「两层都看不见转发包」，是**根本没有流量经过 PC**。
A 格正对照只证明 `NETWORK` 层对 **PC 自发**流量活着，**证明不了手机在走 PC**。
⇒ 会得到一个**漂亮、可复现、完全错误**的「ICS 路径判死」。

**P2-pre（开任何句柄之前）**：`adb shell ip route get 223.5.5.5` 须同时满足
**`dev wlan0`** 且 **`via 192.168.137.1`**（或 `src` 落在 `192.168.137.0/24`）。
⚠ **只看 `dev wlan0` 不够**——设备在别的 WiFi 上同样是 `wlan0`，**那一格分不开两张网**。
不满足 ⇒ **`NOT_EXECUTED`：不加载驱动、不开任何句柄、不数任何包**，打印当前实际出口即退出。

**P2-post（三格跑完之后再查一次）**：仍须满足，且 `via`/`src` 与 P2-pre **一致**；
不一致 ⇒ 整轮 **VOID**。承 D-880：**凡随动作变化的量，前提只查一次就等于没查那段时间。**

**输出要求**：三格计数旁**并印 P2 两次的原文**——**让读者不必相信我们，就能自己看出前提在不在。**

⚠ **这条不靠「PO 记得先开热点」**（那是靠记性的形态）。脚本已经在驱动 adb，守卫焊在脚本里。

## 1. 安全约束（写死在脚本里，非配置）

- 🔴 **`WINDIVERT_FLAG_SNIFF | WINDIVERT_FLAG_RECV_ONLY`，只数不改。**
  **不带 SNIFF 打开句柄会把匹配流量从协议栈上摘走**——那会真的掐断设备的网络。这条是安全关键。
- **零参数**：filter 字符串、层、时长全部写死在脚本里，**不接受任何用户输入**
  ⇒ 注入面为零（与 D-840 菜单化同一理由）。
- **加载前比对哈希**：`WinDivert64.dll` ＝ `c1e060ee…d9a2`、`WinDivert64.sys` ＝ `8da08533…ddc2`
  （`B2_SHAPER_VERIFICATION_20260907.md` §1 登记值）。**不符即拒跑**，不加载。
- 需要**管理员**（`WinDivertOpen` 的要求）⇒ 由 PO 跑一条命令；我这侧不提权。

## 2. 三格设计（**正对照写在第一格，不是附注**）

三格**共用同一个 filter 字符串** `ip.DstAddr == 223.5.5.5`——**共用才使正对照有意义**，
否则「第三格数到 0」可能只是 filter 写错。

| # | 句柄层 | 谁在打流量 | 计数含义 |
|---|---|---|---|
| A | `NETWORK` | **PC** | 🔴 **正对照**：>0 才证明 ctypes/DLL/filter/句柄这条链是活的 |

## 3. 判定表（**跑前写死**）

| A | B | C | 判定 | 处置 |
|---|---|---|---|---|
| **＝0** | 任意 | 任意 | 🔴 **VOID：量法没活** | 整轮作废，**不得据此判任何事**；先查 DLL 加载与 filter |
| >0 | **>0** | 任意 | **第 3 行：交上来了但没命中** | 可修方向＝查 `--dst-ip` 匹配的是 NAT 前还是 NAT 后地址 |
| >0 | ＝0 | **>0** | **第 2 行：工具没开转发层** | 性质是**工具的局限**，不是「Windows 做不到」 |

**计数门限**：每格各打 **20 个 ICMP**（约 20 s）。判「>0」的门槛取 **≥5**，不取 ≥1
——**单个计数可能来自无关的重传或残留**，5 个给出方向而不给出精度。
⚠ 这个门槛**在看到任何计数之前定**。

### 5b. 🔴 事后订正（2026-09-12 16:4x；原文照留，**仍不动 §3 判定**）

上面括号里那条前提——「**句柄关闭后驱动自卸**」——**本机实测不成立**：PO 那轮
`16:16:02` 装载、三格句柄均已关闭，而 SCM 日志里**此后没有任何 UNLOAD**，至今
`STATE 4 RUNNING` 且**无进程持有**。⇒ §5 的判定是 **FAIL**，不是「不可判」。

🔴 **而 FAIL 之所以被读成「达成」，是脚本的一行输出**：原文把「1060 ＝ 已卸载，符合判据 §5」
**写死在格式串里**，于是 `rc=0` 也照印那句解释。**固定标签焊在变量旁边，读起来就像结果**，
那行输出因此传进了转述、再进了裁定。⇒ 新增一条通则：
**凡把读数与解释印在同一行，解释必须由读数算出来，不许先写死。**

**订正后的 §5**：
1. 收尾**印实际 `rc` 与由它算出的结论**（`1060 ⇒ 已达成` / `0 ⇒ FAIL：驱动未卸`）。
2. 若 `rc != 1060`，脚本**只收拾自己装的那一份**：须同时满足
   ① 本轮**确实成功打开过句柄**（否则这驱动不是它装的，不许动）、
   ② **`BeanNetworkTester` 未在运行**（否则 `sc stop` 会掐掉别人的整形）；
   两条都满足才 `sc stop` ＋ `sc delete`，并**复核后再印一次 `rc`**。
3. 「**不得自行 `--cleanup-driver`**」**不变**——那仍是另一个工具的子命令，不属本探针；
   本条新增的是**清理本脚本自己造成的服务残留**，两者不是一回事。

⚠ **范围**：本节只改收尾（§5），**§0b 前提、§2 三格、§3 判定表与门槛一律未动。**

### 5c. 🔴 「应回 1060」是**通道相关**的：同一个退出码，三条通道读出两个值

实测同一次 `sc query WinDivert`（服务不存在）：

```
bash  $?                 = 36      <= 被截断
PowerShell $LASTEXITCODE = 1060
python subprocess .returncode = 1060
算术自证: 1060 & 0xFF = 36 ; 1060 // 256 = 4
```

⇒ **POSIX 的 `$?` 只有 8 位**，`1060` 在 bash 里恒显示为 **36**。
**判据若只写「应回 1060」，在 bash 里核的人会看到一个对不上的数**，
而最省事的读法是「那就是没回 1060 ⇒ FAIL」——**一个真达成被读成未达成**。

**订正**：§5 的 `1060` 判据**只在「python `subprocess.returncode`」或
「PowerShell `$LASTEXITCODE`」两条通道上成立**；**不得用 bash `$?` 核它**。
脚本自己走的是 python 通道（`driver_rc()`），故脚本内判定不受影响；
受影响的是**人手复核**那一步。

⚠ 同族：这属「读取器／序列化层」——**我以为只是搬运一个整数的那一步**。
与「静态括注」那条并列：一个是解释先写死，一个是数值被通道改写；
**两者都让读数看起来像另一回事。**
