## 3. 🔴 那个 2×（A=40、C=40，而每格只打 20 个 ping）：**本份不解释，给可判决的分解**

**这不是脚注，是「可整」检验的前置**：若每包被看见两次而重注入两次，
**要么延迟翻倍（看起来像整形生效了），要么在线路上制造重复包**。两者都是错的，
而前者**长得像成功**。⇒ 必须先知道那两次是什么，再谈改包。

**四条互斥假设，以及各自的判决性 filter**（全部仍是 `SNIFF`，零风险）：

| # | 假设 | 判决性 filter | 预期读数 |
|---|---|---|---|
| H1 | **NAT 前后各见一次**（源地址被改，**目的地址不变** ⇒ 两份都匹配） | `… and ip.SrcAddr == 192.168.137.129` 与其补集各跑一次 | **20 / 20** |
| H2 | **两个接口各见一次**（入 WLAN、出以太） | 同上 | **40 / 0** 或 **0 / 40**（两份源地址相同） |
| H3 | **request ＋ reply 都匹配** | `… and icmp.Type == 8`（仅 echo request） | 40 ⇒ 排除；20 ⇒ 成立 |
| H4 | **A 与 C 的 2× 不同因** | A 格加 `outbound` | 20 ⇒ A 的 2× 是方向性的 |

🔴 **H4 必须单列**：A 在 `NETWORK`、C 在 `NETWORK_FORWARD`，**两个都是 2× 不等于同因**。
把它们当成一个现象解释，就是今天已经犯过的「从一层外推到下一层」。

⚠ **我对 H3 的先验是「不该成立」**（回程包的 `ip.DstAddr` 是 `192.168.137.129`，不是目标 IP），
**但先验不是读数**——H3 照样进表，且它若成立，说明我对 filter 字段方向语义的理解是错的，
那会连带影响「可整」脚本里每一条 filter。

## 4. 边界（**不得外推**）

- 🔴 **只证「可见」，未证「可整」。** `SNIFF` 只复制不摘走；整形要**摘走→改→重注入**，
  是另一件事。**D-789 那个形状（证了一层就外推到下一层）今天已经栽过一次。**
- 未证「转发层能否**重注入**」、未证「重注入后设备侧是否真的看到延迟」。
- 未证任何**档位语义**（延迟／丢包／限速在转发层各自是否成立）。
- 单次、单机、单 ICS 配置、单目标 IP。
