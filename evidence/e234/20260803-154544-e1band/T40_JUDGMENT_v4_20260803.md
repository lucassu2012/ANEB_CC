## 1. 诊断订正：真实根因是 `--stim-file` 遗漏，不是多 dump 解析失败

**复现实验**（用当前未改动的代码，即本条改动前的 HEAD）：

```
$ python tools/e1/e1_analyze.py --run-dir evidence/e234/20260803-154544-e1band \
    --out-md /tmp/nostim.md
翻转总数 / 可用 = 0 / 0
BOOTTIME − MONOTONIC 偏移中位数 = — ns（n=0）
通道 C：n=0 dropped=0 NOT_EXECUTED — 缺分布或缺实测刷新率
```

与归档 `e1_report_band.md`（生成时的原始内容）逐位一致：`翻转总数=0/0`、
`偏移=—ns(n=0)`、`通道C n=0 dropped=0`。原因：CLI 默认 `--stim-file` 是
`stim.log`（T7 时代的向后兼容默认值），这窗的刺激源日志是
`stim_through.log`（`--pin-through-session` 产出，D-407 时已经记过这个
命名差异，`--stim-file` 旗标本就是为了解决它——这次是**没传旗标**，不是
旗标本身失效）。

**独立验证 `parse_sf_latency` 本身没问题**：

```python
period, frames = ea.parse_sf_latency(sf_text)   # sf_text = 全部 1950 行
# period = 16666666，frames 长度 = 1178（不是 0，不报错）
```

15 段 dump 各自的周期头（单独一行 `16666666`）在 `for line in lines[1:]`
里因为 `len(parts) < 3` 被安全跳过（一个数字 split 后只有 1 个 token），
**不会污染数据行**——真正的三列数据行（`desired actual ready`）不管来自
哪一段 dump，格式都一样，照样被正确解析。补 `--stim-file stim_through.log`
后重跑，翻转总数=167/166、通道 C n=160/dropped=6/**FAIL**（p99=32.333ms）——
链路本身完全正常。

## 2. 多 dump 去重升级（`dedup_sf_latency_frames`，additive）

**真缺口**：1178 行解析结果里唯一 `actual_ns` 只有 164 个。已加
`dedup_sf_latency_frames()`（`tools/e1/e1_analyze.py`），签名不动
`parse_sf_latency`（避免破坏 `e234_common.py` 等既有调用方的解包约定），
按 `actual_ns` 精确去重，`analyze()` 接入后新增 `sf_frames` 字段
（`raw`/`deduped`/`duplicate_dropped`，渲染层已读，不落入 D-276"只写不读"）。

**实测去重前后判定完全一致**（脚本核算）：

| | n | dropped | p50 | p90 | p99 |
|---|---|---|---|---|---|
| 去重前 | 160 | 6 | 19.308 | 26.130 | 32.333 |
| 去重后 | 160 | 6 | 19.308 | 26.130 | 32.333 |

原因：`align_present` 对每次翻转只取"commit 之后最近一帧"的单一匹配
（`next()`），重复行的 `actual_ns` 值相同，不改变匹配到的时刻本身。去重
解决的是**另一件事**——不去重时"1178 行"会被误读成"捕捉到 1178 个不同
的帧"，实际只有 164 个，是一处会误导读者的计数，不是一处会算错判据的
bug。渲染面已加对应说明行（仅在 `duplicate_dropped>0` 时出现，单 dump
报告不受影响，4 条新反例含"零重复不冒出这行"）。

**顺带核实 `framestats` 支路本就没有这个问题**：`dedup_framestats_present_times`
（D-416 既有函数）对本窗数据独立核算，141 行原始 → 48 行去重后，**已经
在正常工作**，这次没有发现新缺口。`e234/e2_analyze.py` 自己的
`ec.dedupe_by(frames, "actual_ns")`（`e234_common.py` 既有通用去重）也
已经在处理 `--latency` 支路（`evidence/.../e2_result.json` 里
`frames_total=164/frames_duplicate_dropped=1014` 与本条独立复算逐位吻合）
——**本条修的缺口只在 `tools/e1/e1_analyze.py` 自己的 `analyze()` 里**，
`e234` 那条判读链路本来就没有这个问题，两条链路现在口径一致了。

`tools/e1` 反例 **76/76** 全绿（新增 4 条），`tools/e234` 82/82 零回归，
`test_docs_commands.py` exit=0。

## 5. E2 through 模式"合成钉桩"设计判断——技术可行，判断不做

**技术可行性**：`clock_pin()` 要的是"同一批 E1 刺激源翻转，前后两段各自
算出的 BOOT−MONO 偏移，看漂移是否超 1 帧"。`stim_through.log` 里每次翻转
本身就同时打了 `t_commit_boot_ns`/`t_commit_mono_ns`（`clock_offset_ns()`
逐条能用）——取前 N 个翻转当"合成·前"、后 N 个当"合成·后"，分别喂
`clock_offset_ns()`，理论上能得到与真正分段钉桩同样语义的漂移读数。这条
本身没有技术障碍。

**判断不做，理由**：
1. **不解决 E2 结构性缺口的另一半**：即便"合成钉桩"让 `clock_pin` 变
   PASS，`channel_a_vs_c` 对**这份数据**依然会 NOT_EXECUTED——本窗的 167
   次内容变化事件间隔约 1.8 秒，远大于 `v3_anchors` 用的 400ms 簇分割
   门限，每次翻转天然各自成簇（`turn_method=whole-run`，`turns_total=1`，
   `e2_result.json` 已实测证实），`v3_anchors` 需要"至少两簇"才能给出
   A2，e1stimulus 这种打点节奏永远给不出第二簇。合成钉桩只能修好输入的
   一半，另一半是数据形状本身的问题，不是钉桩方式的问题。
2. **真实 E2 窗不需要这个功能**：T37 协议已明确真实 E2 窗**不**用
   `--pin-through-session`（该旗标本就是"仅用于刺激源自测"），走标准
   `_pin_before`/`_pin_after` 两段式，`clock_pin` 在那条路径上本来就会是
   PASS（前提是两段各自采到够用的 commit 时戳对）——合成钉桩要解决的
   问题，在真实 E2 窗的标准流程里根本不存在。
3. **成本产出比**：实现"合成钉桩"是一段新代码+新反例，产出是一个没有
   消费方的诊断信号（不改变本窗 E2 的最终判定，不被真实 E2 窗需要）——
   本仓一贯纪律是不为没有读者的功能加代码（D-276 反面教材同族）。

**如果未来有人需要它**：场景是"想单独核实某次 through 模式采集期间设备
时钟有没有异常漂移"（跟 E2 判定无关，是装置自身诊断）——到那时再按需
实现，本条不预先造。

## 6. 诚实缺口清单

1. **framestats 支路本窗仍 NOT_EXECUTED**（n=0/dropped=166）——不是多
   dump/去重问题（既有 `dedup_framestats_present_times` 已正确处理），是
   framestats 采样密度太稀疏：48 个去重后的 present_ns 覆盖 92.2 秒，
   落在这段窗口内的翻转（49 次）到最近 framestats 帧仍普遍差 ~1800ms，
   远超 66.7ms 容差——与 D-416 run3 时的发现同一根因，本条只是在更大
   样本上复现，没有新增诊断。
2. **候选 C 带宽的"维持"判断只基于 2 个窗**——双峰形状一致是好迹象，
   但样本仍不算多，第三个独立 E1 型窗若给出显著不同的分桶比例，本条
   判断需要重新核对。
3. **E2 真实 |t_A−t_C| 依然完全 NOT_EXECUTED**——本条判读的是 E1 型窗，
   不是真实目标 App 窗；T37 协议已交付，真实数据仍等 PO 人工段。
4. **通道 A 冒烟自检只证明"链路通"，不证明"数据准"**——167 条
   `ADAPTER_EVT` 与 167 次翻转一一对应这件事本身没有做时间戳精度层面
   的核对（那是 E2 真机窗的职责），本条只看数量对应关系。
