## 一、D-411：head -N 截断成因论证——未发现漏洞

**核查方法**：不满足于重读 D-411 的转述，直接打开被它解释的原始材料
`evidence/e1_realdevice_20260802_run2/BRAIN_PID_PROBE_SUPPLEMENT.md`，以及被它引用作证据的
`evidence/e234/20260802-173031/framestats.txt`，独立核对三件事。

1. **"进程专属段表头恒在第 4 行"这个结构性前提，本备忘用 run3 的真实 `framestats.txt`
   独立复核过，成立**：逐行读取该文件开头四行——
   第 1 行 `Applications Graphics Acceleration Info:`、
   第 2 行 `Uptime: ...`、
   第 3 行为空行、
   第 4 行 `** Graphics info for pid 21036 [com.aneb.e1stimulus] **`——
   与 D-411 §7 描述的结构逐行一致。这不是引用 D-411 自己的转述，是本备忘独立重新数的行号。

2. **`head -3`/`head -5` 的截断效果与补录转写的文本吻合**：`head -3` 只到第 3 行（空行），
   必然看不到第 4 行的进程段头；`head -5` 到第 5 行，必然包含第 4 行。补录
   `BRAIN_PID_PROBE_SUPPLEMENT.md` 转写的"按包名"输出只有全局头两行、"按 pid"输出多出
   `** Graphics info for pid 16519 [com.aneb.e1stimulus] **` 一行——与这个截断效果精确对应。

3. **复现方法论上站得住**：D-411 §7 用的是**已经验证逐字节相同**的按包名/按 PID 完整原始
   输出（JUDGMENT_v3.md §1 记录的 84 行 `diff` 一致）做事后截断实验，而不是重新发一次
   实时命令。这个做法比"重新跑一次 head -3/head -5"更严格——它排除了"两次查询之间设备状态
   变化"这个额外变量，因为截断前的源数据本身已经证明过是同一份东西。

**未发现逻辑漏洞。找到两处措辞层面的精度提醒（不影响结论，值得记录）**：

- D-411 §7"`gfxinfo <target> framestats` 的真实输出结构……**永远**是同一个形状"这句话，
  证据基础是本设备上的**有限次**真实观测（JUDGMENT_v3.md §1 一次、run3 一次、外加被解释的
  补录转写一次，共三次相互印证），不是穷举过的普适规律。用"永远"这个词描述一个基于三次
  观测归纳出的结构，比证据能撑住的强度略高；更精确的写法是"本次实测的历次输出中一致如此"。
  这不影响 D-411 的核心因果论证（该论证只需要"这三次观测彼此一致"这个更弱的前提就成立），
  纯粹是用词精度问题。
- D-411 没有解释"为什么大脑当时对两条命令用了不同的 `head -N` 深度"——但这不是该条决策
  需要回答的问题：因果论证要证明的是"这个不对称会不会产生转写里看到的那个假象"，而不是
  "这个不对称是怎么发生的"（后者的最平常解释就是手误，无需专门论证）。这里是范围划定
  合理，不是遗漏。

## 二、run3：77 翻转 / 0 失败 与 W-2 PASS——对得上，且核对到了原始产物

**核查方法**：不满足于 `JUDGMENT_v3.md` 的转述数字，直接打开三份原始产物逐条核对。

| 声称的数字 | 独立核对方式 | 结果 |
|---|---|---|
| 77 次真实 FLIP/COMMIT，配对完整 | 逐行读 `stim_through.log`，数 `FLIP seq=` 与 `COMMIT seq=` 行 | seq=1…77 全部两两配对，无缺失 |
| 横跨 61.4s（16:30:33.381→16:31:34.771） | 首末两行时间戳相减 | 61.390s，与声称的"61.4s"一致 |
| `framestats.txt` 0 次"No process found" | 全文搜索该字符串 | 零命中；改为 3 段完整 `** Graphics info for pid 21036 [com.aneb.e1stimulus] **` |
| 23 行真实 PROFILEDATA | 逐段数 `---PROFILEDATA---` 区块内的数据行 | 3+10+10=23，与声称一致 |
| 图层非 null | 读 `collect_notes.json.layer` | `"com.aneb.e1stimulus/com.aneb.e1stimulus.StimulusActivity#26282"`，非空 |
| 通道 C n=53 dropped=23 p50/p90/p99=16.512/28.748/29.427ms **FAIL** | 读 `e1_report_through.md`（`e1_analyze.py` 的**原始输出文件**，不是判读文档的转述） | 逐字一致，独立确认 |

**关键判断——W-2 与「装置渲染管线 FAIL」不是同一个问题，这个区分不是 run3 才发明的**：
核对了"W-2"这个提法在四份独立判读文档里的定义，发现无论是 v4 的两次判读
（`E1_JUDGMENT_v4.md`/D-408、`E1_JUDGMENT_v4_run2.md`/D-409）还是 v3 的这次
（`JUDGMENT_v3.md`/D-410），"W-2"逐字定义都是**「通道 C 在 P40 的可用性」**——问的是
"这个采集通道能不能拿到真实数据"，不是"这次测到的渲染延迟数字是否达标"。D-408/D-409 里
W-2 判"仍不可判定"（进程没在跑，探测不到数据），run3 里 W-2 判"PASS——可用"（进程在跑，
拿到了真实数据）；而**同一批 run3 数据里，通道 C 的 M3 门限判定是 FAIL**（p99 超过 1 帧
门限）——这是两个不同粒度的问题各自的独立答案，逻辑上不冲突：前者问"仪器好不好用"，
后者问"这次测出来的数字达不达标"。

`JUDGMENT_v3.md` §0 汇总表的"验证"那一行**没有把这两件事混着说**——原文在同一句话里
既写了"77 次真实 FLIP/COMMIT""0 次 No process found"，也紧接着写了"判定 **FAIL**（p99 超
1 帧）——这是装置本身的判定，不是任何真实 App 的 KPI 结论"，读者不需要翻到 §3.2 才能看到
FAIL 这个字。**没有发现刻意用"PASS"掩盖"FAIL"的痕迹。**

**发现一处值得记录、但不影响本次结论的表述风险**：`JUDGMENT_v3.md` §3.2 那张三行表里，
"PASS"/"FAIL"/"NOT_EXECUTED"这组词在三行里分别承载了三种不同语义——W-2 可用性判断（在
§0，本文档未直接列在这张表里）、M3 门限达标判断（通道 C 一行，FAIL）、**以及通道 B 那行
"PASS（装置意义，检出翻转 0/77）"**——通道 B 检出了 77 次翻转中的 0 次，这在"有没有测到
目标事件"这个意义上几乎是完全失败，但因为它"产出了一个有效的采样周期统计量"（不判定时间
误差，只报周期）便标为 PASS。文档正文对每一处都做了消歧注释，逐条读下来不会误解；但如果
只扫这一列词而不读旁注，容易把"PASS"读成"检出成功"。这是记录在案的表述风险，不构成本次
复核要处理的错误，也不建议现在动手改——`spec §2.2` 早已独立确认通道 B 的采样周期
（p50/p90/p99 = 3050.987/4829.546/5089.520ms）远粗于 800ms 的翻转间隔，此处标 PASS 的
真实含义历来是"这条支路本身在跑、拿到了周期统计"，不是"检出准确"，与既有认知一致，只是
用词上的一个已知负担。
