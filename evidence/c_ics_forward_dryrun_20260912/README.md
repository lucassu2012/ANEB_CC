## 1b. 🔴 事后核出的一个缺口，以及它的闭合（2026-09-12 15:2x 追记）

**缺口**：§1 的 P2（出口必须走热点）**我只在 T0 查了一次**，把一个**会在跑动中变化的量**

## 3. 🔴 对照 B **不可判**——而且失效的是**我预登记的判据本身**，不是执行

判据 §2-③ 写：W0（双侧静默 30 s）量背景包率，W1（仅 P40 打 ping）量信号，
**W1 增量 ≥ 3×W0 且 ≥ 50** 记「涨」。实测：

```
W0  pkts 23433 -> 28522   delta = 5089     (背景, 30 s, 双侧静默)
W1  pkts 28522 -> 33343   delta = 4821     (仅 P40, 150 ping 全收, 29.9 s)
3*W0 = 15267 ;  W1 = 4821  =>  倍数门 FAIL, 绝对门 PASS
```

**按判据的字面，结论是「不涨」。本份拒绝这么记。** 理由：

- **信号只有约 150 个包，背景是 5089 个包 ⇒ 信噪比 2.9%。** 一个分辨不出 3% 变化的量法，
  它给出的「没涨」**不是「没有」的证据，是「看不见」的证据**。
- 我那两个门是为「背景小」的世界写的：**倍数门防的是背景高时假阴，而它在背景高到
  淹没信号时会直接把真信号也判成阴**——**这正是它本该防的那个失效，只是我把它写成了
  「背景高」而不是「背景高到信噪比 3%」。判据的适用范围我自己也写宽了一格。**
- ⇒ 正确的记法：**对照 B NOT_EXECUTED（量法分辨率不足）**，判定表第 2 行与第 3 行
  **均未被排除**。两行处置方向相反（第 2 行「别改菜单或 filter」，第 3 行「可修」），
  **故不得择一**。

⚠ **背景为何这么高未查**：双侧静默时 PC 出站 ≈170 包/秒。它可能是 PC 自身后台，
也可能**正是被转发的设备流量**（若真如此，反而说明转发包被看见了）。**这两种成因在
本份的数据上不可分**，而分开它们需要一个能压过背景的流量源——见 §6。

## 9. 本份能支撑与不能支撑的结论

**能**：
- 经 PC 转发的设备流量，**在本工具当前配置下不被整形**（同一时刻 PC 自发流量被整形 +202 ms）。
- 因此 **B2 搭建单第 8 步那一类验证（从设备侧观察到注入）在 ICS 路径上不成立**。
- 延迟档与丢包档此前的「通过」**只对 PC 自发流量成立**，**不构成战役可用**。

**不能**：
- **不能**判根因是层（`NETWORK_FORWARD`）还是匹配（NAT 前后地址）——对照 B 不可判。
- **不能**据此判 gnirehtet 路径可行与否（另一条路径、另一份验证）。
- **不能**据此重开三选一——那需要根因，且属大脑裁定范围。

## 10. 要往下走需要什么（不由本份决定）

分开第 2 行与第 3 行，需要**一个能压过背景（≈170 包/秒）的设备侧流量源**，
使信噪比至少到数倍而非 3%。本份**未试**，因为大脑交代「任一步不过就停，不试参数」。
可选方向（均需先裁）：①设备侧持续大流量（需确认设备上有可用的生成手段）；
②改用**字节**口径而非包数（仍受同一背景问题制约，须先量背景字节率）；
③在 PC 侧用独立抓包工具按 IP 过滤（`pktmon` 系统自带，但要管理员窗）。
