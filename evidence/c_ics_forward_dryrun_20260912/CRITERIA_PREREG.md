## 0. 前提检查（跑前，只读；任一不成立则判 **NOT_EXECUTED**，不得记为「转发不可整形」）

| # | 检查 | 通过条件 | 不通过时的判定 |
|---|---|---|---|
| P1 | `adb devices` | 有且仅有 P40 一台 | NOT_EXECUTED（设备未连） |
| P2 | 🔴 `adb shell ip route get 223.5.5.5` | **`dev wlan0`**，且 `src` 在热点子网（Windows ICS 典型 `192.168.137.x`） | NOT_EXECUTED。**若走 `rmnet0`（蜂窝）⇒ 流量压根没经过 PC**，此时「RTT 没抬」为真却与 WinDivert 的层毫无关系 |
| P3 | PC 侧 `arp -a` | 能看到 P40 的热点地址 | NOT_EXECUTED（**先证对端在网，再谈路径上的过滤器**） |
| P4 | P40 现态 | 华为桌面为焦点、无残留 VPN/抓包进程、无残留隧道（我自己只读复验，不采信转述） | 不干净则停下协调，不得覆盖未知会话 |
| P5 | `sc query WinDivert` | **1060 服务不存在**（干净起点） | 先查上一轮是否未收尾 |

🔴 **P2 是本份最容易被跳过、而跳过就会得出错结论的一格**：P40 完全可能一边连着热点、一边
仍走蜂窝出网（Android 的连接选择不保证跟着 WiFi 走）。**不先钉住出口，整轮的阴性结果没有意义。**

## 1. 量法

- **设备侧 RTT**：`adb shell ping -c 20 -W 2 223.5.5.5`，解析 `time=` 取**中位数**，同印 min/max。
  （Android 的 ping 输出是英文，可安全文本解析；**PC 侧不解析 ping 文本**——中文环境会乱码，改用
  `Test-Connection` 取 `ResponseTime` 数组。两侧量法不同是刻意的，各取该侧最稳的那种。）
- **PC 侧 RTT**：`Test-Connection 223.5.5.5 -Count 20` → `ResponseTime` 中位数。
- **LAN 段分离**：另测 `adb shell ping -c 10 <热点网关>` 中位数。**没有这一项，「P40 抬了 200ms」
  无法判断抬在 P40↔PC 这一段还是 PC↔上游这一段。**
- **档位**：`delay_lat200` ＝ `--filter out --dst-ip 223.5.5.5 --latency 200`（已部署、已验两次）。

## 2. 判据

**① 仪器判据（必须先成立，否则整轮作废）**：**PC 侧中位必须抬 +200±30**。
PC 不抬 ⇒ **这次整形压根没起** ⇒ 判 **VOID 重跑**，**不得记为「转发不可整形」**。
（这一条是从今天限速档那次学来的：`schtasks /Run` 被路径转换吃掉时，「没起」与「起了没生效」
在读数上完全同形。）

**② 主判据**：P40 侧中位应抬 **+200±30** ⇒ 落 `[基线+170, 基线+230]`。

**③ 对照 B（`pkts=` 计数）**——两个**等长**窗口，顺序 W0→W1：
- **W0（30 s）**：P40 与 PC **双侧静默** → 量**背景包率**（PC 自己的后台流量不为零，必须先量）；
- **W1（30 s）**：**仅 P40** 打 `ping -c 100 -i 0.2 223.5.5.5`（若非 root 不允许 `-i 0.2`，
  退为 `-i 1` 并把窗口延到 **100 s**，判据规则不变）；PC 侧保持静默；
- **判据（两个门都要过）**：W1 的 `pkts` 增量 **≥ 3 × W0 增量** **且** **≥ 50**。
  倍数门防背景高时假阴，绝对数门防背景接近 0 时倍数无意义。两门皆过记「**涨**」，否则记「**不涨**」。

**④ 驱动**：整形前 1060 → 整形中 `STATE 4 RUNNING` → 收尾后 1060，共三个时刻。

**⑤ 收尾**：P40 与 PC 的 RTT 均回基线；进程无残留；设备侧停掉本次启动的一切并复验干净。

## 3. 结果判定表（**跑前写死**，免得把一种红当成另一种）

| P40 RTT | PC RTT | `pkts=` | 判定 | 处置 |
|---|---|---|---|---|
| 抬 +200 | 抬 | 涨 | ✅ **转发可整形** | 战役路径成立 |
| 不抬 | 抬 | **不涨** | **驱动没把转发包交上来** ⇒ 层不对（需 `NETWORK_FORWARD`） | **不是接线错**，别改菜单或 filter；退 gnirehtet 且 loss 档带 D-858 脚注 |
| 不抬 | 抬 | **涨** | 交上来了但**没命中** ⇒ filter/matcher | **可修**：查 `--dst-ip` 匹配的是 NAT 前还是 NAT 后的地址 |
| 不抬 | **不抬** | 不涨 | **VOID：这次整形压根没起** | 查 `sc query` 与 `start.log` 后重跑 |
| **抬** | **不抬** | 任意 | **异常，本份不解释** | 记录原始数据，停下报大脑——不得就地编一个机制 |

**我的预测（跑前写下，可能被推翻）**：第 2 行。依据＝工具 `--help` 与语言包共 **590 个键**里
`forward`／`routed`／`layer`／`hotspot` **全零命中**（键数印出来是为了证明零命中不是读不到）；
整个部署里 `NETWORK_FORWARD` 只出现在 WinDivert 自己的 DLL；`--target`（按**进程**过滤）与
`--narrow-filter` 都是 NETWORK 层概念，而转发包没有本地进程。
⚠ **这是预测不是证明**：工具的 Python 码在压缩档里，字符串检索看不进去。

## 4. 流量账与边界

- 仅 ICMP：两侧各约 60 次 ＋ 信号窗 100 次，量级 **< 100 KB**。**不涉 E-01、不涉那道 200 MB 闸。**
- 命令形态钉死：一律 `powershell -NoProfile -Command "schtasks.exe /Run ..."`
  ——Git Bash 会把 `/Run` 改写成 `C:/Program Files/Git/Run`，任务压根不会被触发。
  **这是形态不是提醒**（文档是检测辅助、不是预防控制）。
- 本份只判「ICS 转发路径能否被本工具命中」这一件。**任何一档整形语义的结论都不由本份出。**
