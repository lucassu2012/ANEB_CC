## 1. 打点事件定义（任务书 ①）

### 1.1 三段式定义法：语义真值 ≠ 可观测判据

每个锚点由三部分定义，**缺一不可**：

```
锚点 := (锚点名, 语义真值, 可观测判据阶梯, 当前可得性)
```

- **语义真值**：物理上想测的那一刻（例如"响应首字的像素出现在屏幕上"）。它不依赖任何观测手段。
- **可观测判据**：我们实际能看见的那一刻（例如"收到一个 `TYPE_WINDOW_CONTENT_CHANGED` 事件"）。
- **两者之差 = `E_anchor`**，是 §3 误差预算的**主项**。

> 这一条是本文最要紧的方法学声明。既有实现把"事件时刻"直接当成"锚点时刻"用，
> 于是 `E_anchor` 从未被命名、也从未被量过——而 M3 门（≤1 帧）恰恰主要卡在这一项上。

### 1.2 五个生命周期锚点（两 App 通用定义）

| 锚点 | 语义真值 | 为什么要它 |
|---|---|---|
| **A0** `send_tap` | 用户手指离屏、发送动作被 App 受理的那一刻 | 交互口径 TTFT 的起点；用户主观等待从此刻开始 |
| **A1** `send_committed` | App 把请求交出去（首字节上网） | 网络口径起点；**只能由通道 D 观测**，与 A0/A2 分标 |
| **A2** `first_response_frame` | 响应首字**上屏**（首帧渲染完成） | Profile 3 主 KPI「端到端 TTFT」的终点 |
| **A3** `streaming_tick_i` | 第 i 次增量上屏 | 流式节奏（cadence）序列 |
| **A4** `answer_complete` | 最后一个增量上屏，且此后不再有新增量 | 主 KPI「RCT（回答完成时长）」的终点 |

**A0′ 的引入（本文新增的命名）**：现役 v3 簇分割的起点**不是 A0**，而是"用户气泡上屏的首个事件"
（D-52 逐字：三段结构 = 用户气泡上屏簇 → 思考静默 → 流式响应簇，`ttftClusterMs = 首簇起→次簇起`）。
本文把这个可观测起点命名为 **A0′ `user_bubble_rendered`**，以便与语义真值 A0 区分。

> ⚠ **由此暴露一处口径缺口（本文发现，待裁定 §6-6）**：
> `spec/portraits/doubao.yaml` 的 `observed_ui_layer.ttft_ui_ms: 1984` 行内注释写
> 「端到端 TTFT 代理(**发送**→响应首字,含渲染)」，`PROFILE3_PORTRAIT` §2 同样写
> 「**发送** → 响应首字上屏」——**而实现测的是 A0′→A2，不是 A0→A2**。
> 两者相差一个**从未被测量过**的量（点击→用户气泡上屏）。
> 该量很可能不大，但"很可能不大"不是证据；在一个 1 帧的门面前，它必须被量出来（§3.3 实验 E3）。
> 本文不改那两处文案（不越 T5 范围），只登记缺口并给出选项。

### 1.5 A4 `answer_complete`：本文新增的判据设计（当前是纯缺口）

现役 v1–v4 四代方法**没有任何一代定义"回答结束"**——`ObsStats` 产出的是 TTFT 与 cadence，
不产出 RCT。而 `SYSTEM_DEV_PLAN` §5.1 把 **RCT 列为 Profile 3 的主 KPI 之一**。这是 M3 的实打实缺口。

判据阶梯（三级，**均未实现、未验证**）：

| 级 | 判据 | 适用 | 风险 |
|---|---|---|---|
| **C-1**（时序） | 事件密度回落至静默基线并持续 ≥ `T_quiet` | 两 App | `T_quiet` 需标定；**取值本身有偏**：定小了把流式中的长停顿误判为结束，定大了把 RCT 系统性拉长 `T_quiet` |
| **C-2**（UI 状态翻转） | 「停止生成」控件消失 / 「重新生成·复制」控件出现 | 取决于该控件在 a11y 树或屏幕上可辨 | 依赖 App UI 结构，改版即失效（§5.1） |
| **C-3**（合取） | C-1 **且** C-2 | 两 App | 最稳；任一不成立 → `null`（R-10） |

**规格规定**：
- 采 **C-3 为主判据**；C-1 单独成立时产出的 RCT 必须带 `rct_method: quiet-only` 标签且置信度**再降一档**；
  C-2 单独成立不足以定时刻（控件变化本身也要等一帧），只作交叉验证。
- `T_quiet` 是**待标定常量**，不在本文给值；标定方法见 §3.3 实验 E4。
- **`T_quiet` 一旦标定，其值必须是单一来源**（一处定义、其余引用）。这是仓内已被反复咬到的形状
  （常量被定义处之外的多处硬编码架空，D-264），适配器侧不重蹈。

### 1.6 降级纪律（对所有锚点生效）

1. 每个锚点声明 **主判据 / 备判据 / 失败即 `null`** 三级，**禁止用备判据的值冒充主判据的口径**。
2. 每个产出值**必须携带 method 标签**（现役已有 `ttft_method: v3-cluster` / `v4-density`，沿用并扩到 A4 的 `rct_method`）。
3. 判据不成立 → `null` + 原因码，**绝不用另一锚点的值顶替**。
4. 不同 method 产出的值**不进同一个统计池**（这是 D-366 已经付过学费的形状：口径不同的轮次必须先退出汇池）。

## 2. 外部观测方法（任务书 ②）

**外部观测**在本文的定义：**不需要修改目标 App、不需要注入操作、不需要解密流量**的观测手段。
四条主通道 + 一条兜底真值源，按能力与代价排列。

### 2.1 通道 A —— 无障碍事件流（现役，已 VALIDATED-OBSERVED）

- **时基**：`elapsedRealtimeNanos()` 单调钟，事件回调线程取时（D-49）。
- **采样率**：**非采样，事件驱动**——这是它与 B/C 的根本区别：没有固定采样周期，
  因而**没有量化误差**，但**有投递延迟与合流**。
- **能锚**：A0′、A2、A3、A4(C-1/C-2)。**不能锚 A0、A1**。
- **逐事件时戳（`t_boot_ns`，2026-08-02 落地，T27 补账）**：`ADAPTER_EVT` 行现携带
  `elapsedRealtimeNanos()` 时戳——**click（`TYPE_VIEW_CLICKED`）与 content-change
  （`TYPE_WINDOW_CONTENT_CHANGED`/`TYPE_VIEW_TEXT_CHANGED`）两类事件均已覆盖**；
  E2 的 v3 簇分割（A2 锚点）只消费 content 类，click 类目前仅服务发送锚定诊断，
  留作未来扩展。**域是 BOOTTIME（含深睡），与通道 C 的 MONOTONIC 域不同源，
  不能直接相减**——须先经 §3.3 E2 的 `clock_pin`/`boot_to_mono_ns` 换算（E1
  双次刺激钉桩测出的 BOOT−MONO 偏移）才可比，这与通道 A 早先"看不见帧"的
  性质无关，是两条独立的口径约束。消费方＝`tools/e1/e1_analyze.py` 的
  `parse_adapter_events()` + `tools/e234/`（`e234_session.py.content_events()`
  → `e2_analyze.py` 的 `|t_A−t_C|` 判读），落地与判读均已完成且各有单测覆盖
  （App 侧 `AnebAccessibilityServiceTest.kt`；判读侧 `tools/e234/tests/`）。
  **当前唯一缺口是真机数据**：需一次真实目标 App 会话同时满足"无障碍观察到
  内容变化事件"与"E1 刺激源完成会话前后双次钉桩"，属排窗问题非代码问题
  （见 §3.3 E2 状态）。
- **误差来源**（本文的分解，逐项待实测）：

  | 来源 | 说明 | 是否有界 |
  |---|---|---|
  | 渲染—事件时序 | 事件在 App 更新视图树时派发，**不保证像素已上屏**（可能早于或晚于呈现） | ✘ 连符号都未知，待实测 |
  | 系统投递延迟 | AccessibilityManagerService 跨进程投递 | ✘ 待实测 |
  | 事件合流/节流 | 同帧多事件被合并（DeepSeek p50 0.1–0.4 ms 即此现象，D-51） | ✘ 待实测 |
  | 前台负载耦合 | 高负载时投递变慢，**与被测量本身相关**（非独立误差，危险） | ✘ 待实测 |

- **红线**：观察 only；不评估 `event.source`（跨进程 `getSource` 开销，R-16 / D-49 偏离 2）。
- **OEM 前提**（每次采集必须满足，否则数据无效）：`deviceidle` 白名单已加（EMUI iAware 会冻结后台进程致全程零观察，D-52）；
  IME 与 systemui 包已豁免（D-51/D-52）；服务已摘除再加回重绑（force-stop 会杀服务且系统不自动重绑，D-50）。

### 2.2 通道 B —— `screencap` 像素帧差（新增，任务书点名）

- **手段**：定周期 `adb shell screencap` 取帧 → 对指定 ROI（响应区/控件区）做像素差 → 差值越阈即判"有变化"。
- **时基**：**取帧完成时刻**，而非"像素上屏时刻"——两者差一个未知的采集管线延迟。
- **采样率**：`adb screencap` 单帧耗时**待实测**（受分辨率、压缩、USB/无线 adb 影响）。
  **[INFERRED, HIGH]** 该耗时以百毫秒量级计的可能性很大；**若成立，则通道 B 的量化误差本身就远大于 1 帧，
  它不能用来判 M3 门**。但它能做两件 A 做不到的事：
  1. **看见 A 看不见的 UI 状态**（C-2 判据的「停止生成」控件），且不依赖 a11y 树结构；
  2. 对 Compose/自绘/WebView 栈**一视同仁**（像素不分 UI 栈）——正是 Kimi 三法皆败的那类场景（D-56）。
- **能锚**：A2（粗）、A4(C-2)。**不能**用于 A3 节奏（采样周期 ≫ 增量间隔）。
- **误差来源**：采集管线延迟 ⊕ 采样周期量化（`±T_sample/2`）⊕ ROI 与阈值选择（内容变化小于阈值即漏检）。
- **红线**：截屏含屏幕内容 = 可能含对话原文。**规格规定：只计算 ROI 的差值标量，
  绝不落盘原始帧、绝不 OCR、绝不导出图像**（与文本红线"只计长度不读内容"同源，`README.md` §发送锚定段）。

### 2.3 通道 C —— 系统渲染时间线（新增；**这是唯一能对"帧"下定义的通道**）

- **手段**：`adb shell dumpsys gfxinfo <package> framestats`（每帧的 VSYNC / 绘制 / 提交时间戳，纳秒）
  与 `adb shell dumpsys SurfaceFlinger --latency <layer>`（每帧的 present 时间戳）。
  **[COMMON, MED]**——Android 平台通用能力，**本方法学未在 P40 上验证过**，故标 MED 而非 HIGH。
- **时基**：系统渲染管线自身的时间戳，与"像素上屏"语义**最接近**。
- **采样率**：逐帧，非外部采样。
- **能锚**：A2、A3、A4 的**帧边界**；配合输入事件时间线可锚 **A0**。
- **为什么它是 M3 门的前置**：

  > **「误差 ≤1 帧」这句话，只有在存在一条能看见"帧"的通道时才可判。**
  > 通道 A 看不见帧（它看见的是内容变化事件）；通道 B 的采样周期本身待实测且很可能远大于一帧；
  > 只有通道 C 直接给出帧的时间戳。
  > **推论**：不接通道 C，M3 门的状态只能是 `NOT_EXECUTED`——既不能报 `PASS`（无证据），
  > 也不宜报 `FAIL`（没测过）。见 §3.4。

- **误差来源**：dumpsys 拉取时刻与帧发生时刻的关联（framestats 是**历史帧缓冲**，需按时戳对齐而非按拉取时刻）
  ⊕ layer 名匹配（App 改版/多窗口时 layer 名会变）⊕ 环缓冲深度（拉取不及时会丢帧，
  与 logcat 环缓冲七分钟冲净同类问题，任务板设备注意条）。
- **红线**：只读 dumpsys，不改任何系统设置；不触碰 App 内容。
- **代价**：需真机；本文**不执行**，列入 §6-5 待裁定 + 排窗申请。

### 2.4 通道 D —— 网络层时戳（现役于画像采集，本文只做口径隔离）

- **手段**：PCAPdroid 免 root 抓包，只读 SNI/IP/端口/方向字节，**不解密**（D-57/D-24）。
- **能锚**：**只锚 A1**。
- **规格规定（隔离红线）**：A1 属**网络传输层口径**，A0/A0′/A2/A3/A4 属 **UI 呈现层口径**。
  **两层的时间戳绝不相减**——`A2 − A1` 看起来像"渲染耗时"，实则跨口径且跨时基，是本项目
  已经立过的那条红线的原样重犯（`README.md` 红线 1；`check_redline` R5 跨层守卫）。

### 2.5 通道 E —— 外部高速相机（兜底真值源，仅用于标定）

- **手段**：外部设备高帧率录制屏幕，判读像素变化帧号 → 反推时刻。
- **用途**：**只做真值标定，不做常规采集**。它是唯一"完全在被测系统之外"的观测者，
  因而是 §3.3 实验 E1/E3 的**独立真值来源**（当通道 C 自身的可信度需要被检验时）。
- **代价**：需额外硬件与判读流程；帧率与快门同步待定。**列为可选支线**，非主路径。

## 3. 误差预算论证（任务书 ③）

### 3.1 先定义"误差 ≤1 帧"是相对**什么**的误差

`SYSTEM_DEV_PLAN` §6 M3 行的原文是「适配器打点误差 ≤1 帧（≈33ms）」，**没有指明参照系**。
三种读法给出三个完全不同的门，必须先裁定（§6-1）：

| 读法 | 误差定义 | 可判性 | 评价 |
|---|---|---|---|
| **(a) 呈现口径**（**推荐**） | 打点时刻 − 该内容**像素上屏**的时刻 | 需通道 C（或 E） | 与 `README.md` 红线 1（"打点=端到端体验代理，含 App 渲染，≈帧级精度上界 16–33ms"）**同一口径**；且"1 帧"这个单位只有在呈现口径下才有物理意义 |
| (b) 网络口径 | 打点时刻 − App 收到首字节的时刻 | 不可得（TLS 下无明文，D-61） | **拒**：跨口径，且违反红线 1 |
| (c) 交互口径 | 打点时刻 − 用户手指离屏的时刻 | 需通道 C/E | 是**用户主观等待**的正确参照，但它包含 App 自身的输入处理耗时——那是被测对象的一部分，不是打点误差 |

**本文推荐 (a)**，并建议把 (c) 作为**单独一项测量**（不叫"误差"，叫 `A0→A0′ 间隔`），
因为它量的是被测 App 的性质，不是我们打点的性质。

**"≈33ms" 的读法**：33 ms ≈ 30 Hz 一帧。P40 实际刷新率**待实测**（若为 60 Hz 则一帧 ≈16.7 ms，
若为 90/120 Hz 更短）。**规格规定：门限用"1 帧"表述，具体毫秒值以实测刷新率换算，
不硬编码 33**——否则在高刷屏上这个门会被悄悄放宽一倍（这正是"一个数被改后，
谁还在用旧基数算它"的形状，D-312）。

### 3.2 误差源分解

```
E_total = E_anchor  ⊕  E_transport  ⊕  E_quant  ⊕  E_clock  ⊕  E_pipeline
```

（⊕ 表示合成；**在各源相关性未知前不得按平方和相加**——相关性本身待实测，见 §7.2 第 8 项。
`E_pipeline` 这一项**不是任何测量口径下都必然出现的独立物理量**——它进入这个等式，
是因为 E1 现在具体选择了用 `t_commit` 代替语义真值 `t0`（见下「这一项从何而来」段）；
若换一种更贴近语义真值的 `t0` 来源，这一项可能被并入 `E_anchor` 或不再单独出现，
这里写作无条件的第五项只是**当前口径下**的记账方式，不是对物理量本身的普适断言，
D-417/D-418 追补。）

| 源 | 定义 | 当前是否有界 | 量法 |
|---|---|---|---|
| **E_anchor** | 语义真值与可观测判据之差（§1.1） | **✘ 无界且从未测过** | 实验 E2（通道对拍）+ E3（A0 缺口） |
| **E_transport** | 判据发生 → 我们的代码拿到时戳 | ✘ 未测 | 实验 E1（已知真值刺激） |
| **E_quant** | 采样/量化：通道 A **无**（事件驱动）；通道 B `±T_sample/2`；通道 C `±0.5 帧` | 通道 C 有界，B 待实测 | 实验 E1 |
| **E_clock** | 时钟源误差 | **✔ 已有界**：全链单一 `elapsedRealtimeNanos` 单调钟，**无跨设备时钟同步依赖**（铁律 3 同构；D-49） | 无需实验 |
| **E_pipeline**（D-417/D-418 新增） | **设备渲染管线固有延迟**：`t_commit`（应用侧提交渲染指令的时刻）到**像素真正上屏**之间的物理间隔——SurfaceFlinger 合成 + 按 vsync 对齐的显示扫描，这段时间即便观测通道零延迟、零量化误差也不会消失，是设备的性质，不是打点方法的性质 | **尚未单独测过**——首次实测到的是**含它在内的总量**（run3，双峰、约 1–2 帧量级），`E_pipeline` 本身还没从中分离出来 | E1（**副产品**，见下）+ E2（把它从 `E_transport⊕E_quant` 里分出去） |

**这一项从何而来（不是凭空新加的，是一处此前没记账的缺口）**：E1 §3.3 的原始设计是
"误差 = `t_obs − t0`"，`t0` 本该是**语义真值**（像素真正出现的那一刻）。但目前唯一
可行的 `t0` 来源是刺激源自报的 `t_commit`（`registerFrameCommitCallback`，见
`tools/e1/README.md` §2）——这是**提交渲染指令**的时刻，不是**上屏**的时刻。
只要 E1 用 `t_commit` 代替真值 `t0`，`t_obs − t_commit` 这个差值里就**必然**混进了
`t_commit → 真正上屏` 这段设备管线固有延迟，**这不是某一次测量失手带进来的噪声，
是这个实验设计的选择本身带进来的一项系统性分量**（D-417 §1 口径审计；D-418 裁定）。

**当前结论（诚实）**：五项里只有 `E_clock` 有界。**主项 `E_anchor` 无界、未测**，
且它恰恰是 §1.2 那个"文案写发送、实现测气泡"的缺口所在；`E_pipeline` 首次在 run3
真机数据上被测到（双峰形状，约 1–2 帧量级，见 `docs/G2_REACHABILITY_MEMO_20260802.md`
§2），但**尚未与 `E_transport⊕E_quant` 分开**——分开需要 E2（见 §3.4 G-2 行的注）。

> 因此：**M3 打点误差门的当前状态 = `NOT_EXECUTED`。**
> 不是 `PASS`（无任何针对打点误差本身的测量）；不是 `FAIL`（从未测过，判 FAIL 是伪精确）；
> 不是 `BLOCKED_EXTERNAL`（不缺外部依赖，缺的是一次我们自己能做的实验）。

### 3.3 验证实验设计（**设计即可，本文不执行**）

#### E1 —— 已知真值刺激实验（**核心，且不碰目标 App**）

- **目的**：量 `E_transport` 与 `E_quant` 的分布。**⚠（D-417/D-418 追补）本节写的是原始设计
  目标，不是实测口径**——见下「原理」段：可行的 `t0` 只有 `t_commit` 代替，故通道 C 实测拿到的
  是含 `E_pipeline` 的**总量**，不是纯 `E_transport⊕E_quant`（§3.2「这一项从何而来」段）。
- **原理**：真实 App 的"真值"我们不知道，所以**不要拿真实 App 量误差**。改用一个
  **我们自己控制、真值已知**的刺激源：本仓 debug 面板（或一个最小刺激 App）在时刻 `t0`
  把屏幕某 ROI 由 A 变 B，同时把 `t0`（`elapsedRealtimeNanos`）打进 logcat。
  适配器与通道 B/C 同时观测该变化，得 `t_obs`。**误差 = `t_obs − t0`**。**⚠（D-417/D-418
  追补）"真值已知"这句对通道 C 不严格成立**：通道 C 实际可行的 `t0` 来源是 `t_commit`
  （应用侧提交渲染指令的时刻），不是像素真正上屏的语义真值——两者之差即 `E_pipeline`
  （§3.2 新增第五项），本段写作时这个缺口还没被记账。
- **自变量**：变化面积（小/中/全屏）、变化频率（稀疏/密集，覆盖合流场景）、前台 CPU 负载（空载/满载）、
  是否处于 `deviceidle` 白名单。
- **判据**：三通道各自的 `t_obs − t0` 分布（p50/p90/p99 + n）。**通道 C 的 p99 ≤ 1 帧** → 该通道在
  `E_transport ⊕ E_quant` 上过门；通道 A 同理各判各的。**⚠（D-417/D-418 追补）这条判法对
  通道 C 不成立，正是 D-418 明令禁止的读法**——通道 C 的 `p99 ≤ 1 帧` 只能判"实测总量 vs
  1 帧"，不能直接读成"在 `E_transport⊕E_quant` 上过门"；后者（G-2 本义）在 E2 把
  `E_pipeline` 分解出去之前恒为 `NOT_EXECUTED`，见 §3.4 G-2 行后的附注。通道 A 不涉
  `t_commit`，不受此条约束，各判各不变。
- **资源**：任一 Android 设备即可（**不必是 P40，不必装豆包/DeepSeek，不消耗任何 App 额度、不碰真实账号**）。
- **状态**：`NOT_EXECUTED`。

#### E2 —— 三通道同轨对拍

- **目的**：量 `E_anchor` 的**可观测下界**（真值仍不知，但三通道互差给出下界）。
- **做法**：同一次真实会话，同时开通道 A / B / C，记录同一锚点（A2）的三个时刻，两两求差。
- **判据**：`|t_A − t_C|` 的 p99 即通道 A 相对呈现口径的锚定偏差估计。
  若该值 > 1 帧 → **通道 A 单独不足以支撑 M3 门**（须以 C 为主判据，A 降为交叉验证）。
- **资源**：P40 + 已装 App + 少量额度（英文 prompt、最少轮次，D-60/D-52 实录）。**需排窗。**
- **状态**：`NOT_EXECUTED`。

#### E3 —— A0 缺口专项（`A0 → A0′` 间隔）

- **目的**：把 §1.2 登记的那个"从未测过的量"测出来。
- **做法**：通道 C 的输入事件时间线取 A0，通道 A 的 v3 首簇首事件取 A0′，求差；
  通道 E（外部相机）作独立校核。
- **判据**：给出 `A0→A0′` 的分布。**它不是"误差"，是被测 App 的输入处理耗时**——
  测出来之后，`ttft_ui_ms` 的文案要么改成 `A0′→A2`，要么把该间隔加上（§6-6）。
- **资源**：P40 + 通道 C。**需排窗。**
- **状态**：`NOT_EXECUTED`。

#### E4 —— `T_quiet` 标定（A4 判据前置）

- **目的**：给 §1.5 的 `T_quiet` 一个有据的值。
- **做法**：采集足量真实会话的完整事件流，画"增量间隔"的分布；
  `T_quiet` 取在**流式中最大停顿**与**结束后静默**之间的分离点。
  **若两者分布重叠**（即不存在干净的分离点）→ 结论是 **C-1 单独不可用，A4 必须走 C-3 合取**，
  这是一个合法且有价值的否定结论，不得为了拿到数值而硬凑（R-10 精神；D-53 已有先例：
  "不硬凑数值，诚实缺席优于错值"）。
- **资源**：P40 + 额度（多轮长回答）。**需排窗。**
- **状态**：`NOT_EXECUTED`。

#### 实验间的依赖序

```
E1（无需 P40，可先做，且能独立证伪"通道 A 够不够"）
  └→ E2（需排窗）──┬→ E3（需通道 C 已验证可用）
                   └→ E4（可与 E3 并行，共用同一批会话录轨）
```

**建议**：E1 先行。它成本最低、不消耗任何 App 额度、不碰真实账号，
却能独立回答"通道 A 的投递延迟够不够一帧"这个决定性问题。

## 4. 画像参数采集口径与 [GUESS] 替换路径（任务书 ④）

### 4.1 先说清楚适配器**不能**替换什么

`spec/portraits/*.yaml` 的 `params:` 七字段是**网络层/token 层**的量；适配器是 **UI 呈现层**观测。
**跨层回填一律拒**（`check_redline` R5 跨层守卫；铁律 3；蓝图 §1.2 第 1 条"同层直采源"）。

具体地：**适配器观测到的 `cadence_ui` 绝不能填 `token_interval_ms_dist`**——
这正是 `doubao.yaml` fit 段已经如实标注的状态（`caliber: ui-proxy`、`keep_pending: true`、
note 逐字 "UI cadence proxy, not network ITL"）。本文不放宽这一条。

### 4.2 逐字段：适配器能翻哪一格

依据 `doubao.yaml` 的 `params_capture_status`（D-348 逐字段门控，PO 2026-07-31 批复）实况：

| params 字段 | 现状态 | 适配器能否翻 | 理由 / 出处 |
|---|---|---|---|
| `request_size_bytes_dist` | PENDING | ✘ | 网络层字节，通道 D 的事（蓝图 §5 C2） |
| `token_interval_ms_dist` | PENDING-BY-CALIBER | ✘ | 需明文 token 时戳，红线外（D-61/D-24） |
| `think_pause_ms_dist` | PENDING-BY-CALIBER | ✘ | 同上 |
| `tool_loop_cadence` | N/A-BY-CALIBER | ✘ | 消费聊天 App 无工具编排，口径上永不可得 |
| `session_duration_s_dist` | PENDING | **✔ 唯一能翻的一格** | 蓝图 §5 C6 逐字："需 a11y 会话开始/结束埋点（非 per-turn 换算），代码未落地" |
| `downlink_media_bytes_dist` | PENDING | ✘ | 需端点级字节隔离；禁文本下行冒充媒体（R15 永久红线） |
| `pop_ip_list` | PENDING | ✘ | 网络层事实 |

**一句话结论**：适配器对画像门控的贡献是**七分之一格**，不是"补上画像"。
把 Profile 3 适配器说成"业务画像采集的主力"是过度宣称——它的主产出是
`observed_ui_layer`（不进 `params` 门控），不是 `params`。

### 4.3 `session_duration_s_dist` 的采集口径（本文定义）

> ⚠ **一个必须先讲清楚的同名不同义陷阱**：现役 `AnebAccessibilityService` 里的"会话"
> 是**按前台包切换分段**的观察会话（D-49/D-54：切到非豁免第三方或 launcher 才结算，HOME 键可靠触发）。
> 它**不是业务会话**——用户在豆包里连问五轮不切前台，是**一个**观察会话、**五轮**业务交互；
> 用户切出去看眼别的 App 再切回来，是**两个**观察会话、**一段**业务会话。
> **直接拿观察会话时长填 `session_duration_s_dist`，是"一个计数冒充另一个量"的原样重犯**（D-340）。

**规格规定**——业务会话的定义与判据：

- **业务会话** := 同一 App 内，相邻两次 A0′ 间隔 ≤ `T_session_gap` 的一串交互；
  起点 = 首个 A0′，终点 = 末次 A4。
- `T_session_gap` 为**待标定常量**，不在本文给值（标定方法同 E4 的分布分离法）。
- **切前台不结算业务会话**（与观察会话解耦）；观察会话仅作为事件流的载体。
- **A4 不可得则该业务会话时长记 `null`**（R-10）——注意这条的连带后果：
  **§1.5 的 A4 判据没落地之前，`session_duration_s_dist` 也翻不了门**。
  这是一条本文新建立的依赖，`params_capture_status` 里现有的 reason 尚未提及它。

**建议（不越范围，只提案）**：把 `doubao.yaml`/`deepseek.yaml` 的
`session_duration_s_dist.reason` 补一句"依赖 A4 判据（`INSTRUMENTATION_SPEC` §1.5）"。
本文**不代改**（改画像文件属另一范围，且 `check_redline` 有守卫），列入 §6-6。

### 4.4 置信度标注规则

三个维度**各标各的，不合并**：

| 维度 | 取值域 | 适配器产出的取值 |
|---|---|---|
| `params_capture_status` | PENDING / PENDING-BY-CALIBER / N/A-BY-CALIBER / CAPTURED | 仅 `session_duration_s_dist` 可能到 CAPTURED |
| `caliber` | direct / order-of-magnitude / ui-proxy / none | **恒 `ui-proxy`**（UI 层观测的本性，非暂时状态） |
| `confidence` | HIGH / MED / LOW / INCONCLUSIVE | **恒 ≤ LOW，直到 §3.4 的 G-5 `PASS`** |

**本文新建立的一条联结**：

> **打点误差门（M3 / §3.4 G-5）是 UI 层置信度的前置条件。**
> `README.md` 红线 2 说"规格 `PENDING-VALIDATION` 撤销前恒 LOW/INCONCLUSIVE"，
> 而两个规格现在已是 `VALIDATED-OBSERVED`——**按字面读，红线 2 已经不再约束它们了**。
> 但打点误差从未被量过。所以本文把约束换到一个不会被"规格状态升级"绕过的判据上：
> **G-5 未 PASS → `confidence` 恒 ≤ LOW，与规格 status 无关。**

### 4.5 `observed_ui_layer` 的分布化（additive 提案）

现状：`observed_ui_layer.ttft_ui_ms: 1984` 是**单值**（豆包两次一致：1984.4 / 1984.6，D-52/D-54）。
两次一致是好信号，但**两次不是分布**。蓝图 §1.2 的证据强度阶梯要求
「至少 p50/p90/p99 + 样本数 + 采集环境」且「≥30 turns / ≥5 sessions × ≥2 网络条件」。

**提案（additive-only，遵 `spec/README.md` 治理规则 3）**：新增子段，不动现有键：

> 治理规则 3 已于 D-397 改写为**严格 loader 通则**（「往既有被加载 JSON 补键默认不可行」）。
> **本提案不受影响，但理由要换一个**：它安全**不是因为它是 additive**，而是因为**它的消费方
> 不是严格 Kotlin loader**——`observed_ui_layer` 落在 portraits 的 YAML 上，由
> `check_redline.py` 与 `portrait.schema.json`（`observedLayer` 无 `additionalProperties: false`）
> 消费。规则 3 的判据是**消费方**，不是变更形状（D-276「动手前先数读者」）。

```yaml
observed_ui_layer:
  ttft_ui_ms: 1984          # 保留，语义不变（首个实测锚点值）
  dist:                     # 新增（additive）；未采够即整段缺席，不放 null 占位
    ttft_ui_ms:    { p50: , p90: , p99: , n: , sessions: , networks: [] }
    cadence_ui_ms: { p50: , p90: , p99: , n: , sessions: , networks: [] }
    rct_ui_ms:     { p50: , p90: , p99: , n: , sessions: , networks: [] }   # 依赖 A4
    method: { ttft: , rct: }      # v3-cluster / v4-density / quiet-only …
    captured_at:                  # YYYY-MM-DD，沿用同目录既有惯例
```

**规格规定**：`dist` 段整段可缺席；**一旦出现，其内字段不得为 null**
——"缺席"与"值为 null"语义不同，这是 `params` 侧已经用 `PENDING` vs `N/A-BY-CALIBER`
区分过的同一个道理（D-348）。样本不足阈值时**整段不写**，而不是写一个 `n: 3` 的分布。

## 5. 风险与缓解（任务书 ⑤）

### 5.1 App 改版脆弱性（`SYSTEM_DEV_PLAN` §8 自认的 M3 最高风险，四条缓解）

| # | 缓解 | 现在能不能做 | 出处/依据 |
|---|---|---|---|
| **R1-a** | **规格 = 数据文件**：改版即改 JSON，不改代码 | **已立**（铁律 1；`README.md` 首行） | D-49 |
| **R1-b** | **版本指纹钉定 + 漂移探测**：每次采集记录目标 App 的 `versionName`/`versionCode`（`dumpsys package <pkg>`，只读），写入规格的 `validated_against_version`；采集时不匹配 → **降级 generic 观察 + 标 `STALE`**，不静默出数 | 需一个 additive 字段 + 宿主一处判断（**未实现**） | 本文新提；对应 §6-4 |
| **R1-c** | **判据阶梯冗余**（§1.6）：每锚点主/备判据，单一判据失效不致全盘失效 | 部分已有（v3/v4 并存），**未系统化** | D-52/D-53/D-55 |
| **R1-d** | **金丝雀语料回归**：固定一组英文 prompt，每次改版后复跑，数值突变即报警——而不是等到某天发现数据早就错了 | 需 §4.5 的 `dist` 有基线后才有意义 | 本文新提 |

> **不采纳的一条**：`SYSTEM_DEV_PLAN` §8 写的「打点走无障碍节点监听为主、**录屏逐帧为兜底**」，
> 其中"录屏逐帧"即本文通道 B——但 §2.2 已论证它的采样量化误差很可能远大于一帧，
> **它不是"兜底"（同等精度的备份），而是"另一种能力"（看得见 UI 状态、不挑 UI 栈）**。
> 按"兜底"用会把一个低精度通道的值混进同一个统计池（§1.6 第 4 条禁止的形状）。
